# NL2SQL 元数据层：标准模板、导入校验、SQLite 元数据库

> 日期: 2026-10-14 | 类别: tech | 关联: [[2026-10-13_design_nl2sql专题库改造]]

---

## 📦 目标

数据字典和血缘清单平时都躺在 Excel 里，人能看，程序不能查。大模型写 SQL 之前，程序必须能回答三个问题：这张表有哪些字段、这个字段是从哪儿加工来的、这两张表靠什么关联。元数据层做的事，就是把这些资料从 Excel 搬进关系表，并且在搬的过程中把有问题的资料拦下来。

交付物是五件：

| 交付物 | 文件 | 作用 |
|--------|------|------|
| 标准模板 | `metadata/template.py` | 规定四张清单各有哪些列，哪些必填 |
| 读取 | `metadata/loader.py` | 把 Excel 或 CSV 读成原始行 |
| 校验 | `metadata/checks.py` | 19 条规则，14 条错误、5 条警告 |
| 入库 | `metadata/store.py` | 落成 SQLite 的四张表，并提供只读访问 |
| 导入总控与报告 | `metadata/importer.py` | 把前四步串起来，提供命令行，输出导入报告 |

数字指标：这一层共 82 项单元测试（模板 8、读取 12、校验 42、入库 8、导入 12），全部不调模型，几秒跑完。

## 📖 讲透

### 1. 四张清单各管什么

| 清单 | 一行代表什么 | 相当于平时的哪份资料 |
|------|--------------|----------------------|
| 表清单 | 一张表：层级、模式名、表名、表类型、粒度字段、数据日期字段 | 数据字典的表级目录 |
| 字段清单 | 一个字段：所属的表、英文名、中文名、类型、是否主键、口径说明、码值说明 | 数据字典的字段明细 |
| 血缘清单 | 一条字段级血缘：目标表的某个字段来自源表的某个字段，由哪个脚本加工 | 字段映射文档（mapping） |
| 关联关系（可选） | 两张表用哪些字段关联，是多对一、一对一还是一对多 | 模型设计文档里的关联说明 |

几个约定：

- **表的唯一标识是 `模式名.表英文名`，全小写。** 相当于给每张表定了一个主键。四张清单之间互相引用表，都用这个标识。
- **层级只有三种**：贴源层、整合层、专题层。
- **表类型有四种**：快照表、流水表、维表、全量表。快照表每个数据日期存一份全量，查询时必须带日期条件，否则会把很多天的数据加在一起；全量表每次清空重装，只有当前状态，不需要日期条件。这个区别后面生成 SQL 时要用到。
- **粒度字段**是能唯一确定一行的字段，也就是业务主键。它的用处是判断关联会不会发散：拿明细表去关联一张粒度更细的表，金额就会被重复计算。粒度字段可以不填，不填就没法做这个判断。

### 2. 导入就是一条带数据质量检核的 ETL

整个导入过程和一条普通的 ETL 作业是同一个结构：

```
读取            标准化               检核             全量装载
load_raw   →   （读取时顺手做）  →   check_mart   →   write_store
Excel/CSV      去空格、转小写        19 条规则        SQLite 四张表
                                        │
                                        └─ 有错误：中止，不装载，只出报告
```

- **读取**对应抽取。支持一个 `metadata.xlsx`（四个 Sheet），也支持四个同名的 CSV 文件。
- **标准化**对应清洗。单元格去掉首尾空格；表名、字段名这类标识符统一转成小写，这样几张清单之间大小写不一致也能对上。
- **检核**对应数据质量检核。检核不通过就不往下走。
- **装载**是全量覆盖，不做增量。

### 3. 错误和警告为什么要分开

| 级别 | 含义 | 处理 |
|------|------|------|
| 错误 | 这份资料入了库，下游一定会出错。例如血缘指向一个不存在的字段 | 中止导入，元数据库不更新，原有的库保持不变 |
| 警告 | 资料不完整，但不妨碍使用。例如表没有填粒度字段 | 照常入库，写进导入报告 |

这和数据质量检核里强规则、弱规则的分法是一回事：强规则不通过就阻断作业，弱规则只告警。

为什么不能全部当成错误：真实的资料里，几百张表没有主键、上千个字段没有类型是常态。如果这些都算错误，资料永远导不进来，工具也就没法用。为什么不能全部当成警告：引用了不存在的表或字段，后面生成的 SQL 一定是错的，这种问题必须在入口拦住。

还有一个细节：**同一类警告要汇总。** 「表没有填粒度字段」这条警告（W04）按层级汇总成一条，只举三个例子，而不是每张表报一条。告警刷出几百行，等于没有告警，没人会看。

19 条规则一览：

| 编号 | 级别 | 含义 |
|------|------|------|
| M01 | 错误 | 清单或必填列缺失，或者表清单里一张表都没有。出现时不再检查其它规则 |
| M02 | 错误 | 必填单元格为空 |
| M03 | 错误 | 表重复 |
| M04 | 错误 | 同一张表内字段重复 |
| M05 | 错误 | 层级或表类型取值非法 |
| M06 | 错误 | 表在字段清单里没有任何字段 |
| M07 | 错误 | 粒度字段或数据日期字段不在该表的字段清单里 |
| M08 | 错误 | 快照表没有填数据日期字段 |
| M09 | 错误 | 血缘的目标表或目标字段不在字段清单里 |
| M10 | 错误 | 血缘的源表在表清单里，但源字段不在字段清单里 |
| M11 | 错误 | 关联关系引用了不存在的表或字段 |
| M12 | 错误 | 关联关系的对应关系取值非法，或左右字段个数不一致 |
| M13 | 错误 | 字段清单里的表不在表清单里 |
| M14 | 错误 | 表名没有带模式名 |
| W01 | 警告 | 血缘的源表不在表清单里，按外部源处理 |
| W02 | 警告 | 血缘存在环 |
| W03 | 警告 | 整合层或专题层的表没有任何血缘记录 |
| W04 | 警告 | 表没有填粒度字段，按层级汇总 |
| W05 | 警告 | 表里有字段没有填数据类型，每张表一条 |

这些规则大多数是引用完整性检查，相当于外键约束：字段清单里的表必须在表清单里（M13），血缘里的字段必须在字段清单里（M09、M10）。数据库里靠外键保证，这里资料来自 Excel，没有外键，只能在导入时自己查。

### 4. 先写临时文件，再替换正式文件

写元数据库时不直接改正式文件，而是先把全部内容写进 `metadata.db.tmp`，全部成功之后再用一次文件替换把它变成 `metadata.db`。

这和数仓里「先写临时表，核对无误再交换分区」是同一个做法。好处有两个：

- 写到一半失败了，正式库一个字节都没动。
- 正在读元数据库的程序，要么看到完整的旧库，要么看到完整的新库，不会看到写了一半的库。

### 5. 幂等：重跑多少次结果都一样

每次导入都是全量重建：不管上次导到什么程度，这次都从头建一个新库。同一套资料导一次和导十次，结果完全相同。

类比全量覆盖的作业和增量追加的作业：全量覆盖的作业可以随便重跑；增量追加的作业重跑之前要先清理，否则数据会重复。元数据只有几万行，全量重建是秒级的，没有理由去做增量。

### 6. M14 这条规则是怎么来的

这是写测试时发现的一个真实隐患。假设血缘清单里有一行，源表写的是 `corp_dep_acct_d`，漏了前面的模式名 `dwd.`。

按原来的规则，源表不在表清单里就当成外部源，只给一条警告（W01）。于是这条血缘悄悄指向了一个并不存在的「外部表」，导入照样成功。后果是血缘链在这一跳断掉：以后要沿着血缘向上溯源时，走到这里就停了，而且没有任何报错。

这就像关联键格式不一致导致关联不上：作业不报错，只是结果里少了数据。这是最难查的一类问题，所以要在入口卡死。

M14 的做法：

1. 表名里没有点号时，先拿它到表清单里按表英文名去找。
2. 唯一对上一张表：报一条 M14 错误，并且直接告诉填表的人正确写法是什么。之后的校验按对上的那张表继续，避免连带报出一串「字段不存在」的无关错误。
3. 对上了多张表（不同模式下有同名的表）：报错并列出所有候选，让人自己选。
4. 同一个表名在一张清单里只报一次，同时说明涉及多少行。

报错信息要告诉人怎么改，而不只是说哪里错了。这一点对一个要交给别人用的导入工具很重要。

## 🔧 选型

| 决策 | 选了什么 | 没选什么 | 原因 |
|------|----------|----------|------|
| 元数据放哪 | SQLite | 只放内存、JSON 文件 | 零部署，一个文件就是一个库；能直接用 SQL 查，排查问题时打开就能看；后面的步骤要做「某张表的全部字段」「某个字段的全部上游」这类查询，关系表最自然。类比：把散落在各处的 Excel 台账收进正式的表里，才谈得上查询和关联 |
| 数据模型 | Pydantic | 字典、普通类 | 字段和类型写在一处，构造时自动校验类型；项目的接口层是 FastAPI，本来就用 Pydantic，后面可以直接当接口的返回结构。类比：相当于建表语句里的字段类型加约束，不合规的数据在插入那一刻就报错，而不是留到查询时才发现 |
| 读 Excel 和 CSV | openpyxl 加标准库 csv | pandas | 只是把单元格读成文本，用不上 pandas 的计算能力；依赖更轻；项目之前踩过 Pandas 3 和 SQLAlchemy 2 不兼容的坑，能不引入就不引入。类比：只是装载几个平面文件，用装载工具就够了，不必为此搭一套分析平台 |
| 找血缘里的环 | networkx | 自己写深度优先搜索 | 一行 `nx.find_cycle` 就够了；第二份计划的血缘图也要用它，不算额外的依赖。类比：调度系统里作业之间的依赖不能成环，上线前要做的就是这种环路检查 |

## 💡 可迁移

**1. 接口表、校验、全量幂等装载。** 外部来的资料先落到一个格式固定的接口（这里是四张清单），过一遍检核，再全量装载。这套做法可以搬到任何「把别人给的资料变成自己系统里的数据」的场景，比如后面要做的历史 SQL 样例库。

**2. 定义只写一处，其它都从它派生。** 四张清单有哪些列、哪些必填、哪些是标识符，只在 `template.py` 里写了一次：

```python
@dataclass(frozen=True)
class ColumnSpec:
    """清单里的一列"""

    header: str                # 清单里的中文列名
    field: str                 # 程序内部使用的字段名
    required: bool = False     # 是否必填
    identifier: bool = False   # 是否标识符（表名、字段名），读取时统一转小写
    help: str = ""             # 填写说明
```

读取时按它找列，校验时按它判断必填，空白模板和填写说明也是照它生成的。以后要给清单加一列，只改这一个地方。类比：表结构只在建表语句里定义一次，接口文档、校验脚本都从它生成，而不是三处各写一遍、改的时候漏掉一处。

**3. 规则分强弱，告警要汇总。** 强规则阻断，弱规则放行并留痕；同类告警合并成一条。

## 👨‍💻 代码

按数据流的顺序走一遍：`load_raw` → `check_mart` → `build_mart` → `write_store`。下面的片段都取自仓库里的代码，为了讲解做了删节。

**读取（`metadata/loader.py`）。** CSV 先按 UTF-8 解码，失败再按 GBK 解码（`CSV_ENCODINGS` 的值是 `("utf-8-sig", "gb18030")`），两种都不行才报错，并且报的是一句人能看懂的话：

```python
data = path.read_bytes()
for encoding in CSV_ENCODINGS:
    try:
        text = data.decode(encoding)
        break
    except UnicodeDecodeError:
        continue
else:
    raise ValueError(f"无法识别 {path.name} 的编码，请另存为 UTF-8 或 GBK 编码的 CSV")
```

转成原始行时保留文件里的真实行号（表头是第 1 行），这样报错能直接指到 Excel 的那一行；标识符在这里统一转小写：

```python
for row_no, cells in enumerate(grid[1:], start=2):
    if not any(cells):
        continue  # 跳过空行
    values: dict[str, str] = {}
    for column in spec.columns:
        index = positions.get(column.header)
        text = cells[index] if index is not None and index < len(cells) else ""
        values[column.field] = text.lower() if column.identifier else text
    rows.append(RawRow(sheet=spec.name, row_no=row_no, values=values))
```

**校验（`metadata/checks.py`）。** 入口函数按固定的顺序调用六组检查。第一组检查清单和必填列在不在，不在就直接返回，因为列都缺了，后面的规则没法查：

```python
def check_mart(raw: RawMart) -> list[Issue]:
    issues: list[Issue] = []
    if not _check_structure(raw, issues):
        return issues
    _check_required_cells(raw, issues)
    tables = _check_tables(raw, issues)
    columns = _check_columns(raw, tables, issues)
    _check_lineage(raw, tables, columns, issues)
    _check_relations(raw, tables, columns, issues)
    return issues
```

M14 的核心在血缘检查里。表名对不上时先按不带模式名去找，唯一对上就换成对上的表继续往下查：

```python
for name in (target_table, source_table):
    matches = [] if name in tables else match_bare_name(name, tables)
    if matches:
        bare_names.add(name, matches, row.row_no)
        if len(matches) == 1:
            name = matches[0]   # 能唯一对上：报一次错，其余校验按对上的表继续
        else:
            undecided = True
    resolved.append(name)
```

**转换成标准模型（`metadata/importer.py` 的 `build_mart`）。** 只在没有错误时调用。血缘的「源表是不是外部源」在这里算出来，后面的步骤直接用：

```python
source_external=row.values["source_table"] not in known_tables,
```

**入库（`metadata/store.py` 的 `write_store`）。** 写临时文件，成功后替换；替换时如果正式文件被别的程序占着，给出明确的提示：

```python
try:
    os.replace(tmp_path, db_path)
except PermissionError as error:
    tmp_path.unlink(missing_ok=True)
    raise RuntimeError(
        f"元数据库文件正被其它程序占用，请先关闭占用它的程序再重试: {db_path}") from error
```

**一次真实的运行。** 用测试里那套最小的合法资料执行导入。这套资料只有三张表，是用 `tests/helpers.py` 里的 `write_mart` 把 `TINY_MART` 写到一个临时目录 `tiny_mart` 得到的。命令的退出码是 0：

## ⚠️ 常见坑

1. **Excel 另存为 CSV，编码是 GBK。** 中文 Windows 上这是 Excel 的默认行为。读取时已经兼容，不需要手工转码。
2. **表名没带模式名。** 最常见的填写错误，对应 M14，报错信息里有正确写法。
3. **合并单元格。** Excel 里把同一张表的几十行字段的「表名」合并成一个单元格，读出来只有第一行有值，其余行是空的，会报一串 M02，还会连带报出 M07、M09、M10、M11 这类「字段不在字段清单里」的错误，因为这些行的字段找不到所属的表。先把 M02 修掉，连带的错误会一起消失。模板的填写说明里专门写了「每一行都要填，不能用合并单元格」。
4. **Windows 上元数据库文件被占用。** 开着数据库查看工具时，文件替换会失败。程序会提示「正被其它程序占用」，并且原来的库完好无损，关掉工具重跑即可。
5. **中文文件名的排序不直观。** Python 对中文按编码排序，不按拼音，「血缘清单」排在「表清单」前面。凡是顺序有意义的地方不要依赖中文名的排序，像加工脚本那样用数字前缀（`01_`、`02_`）来定顺序。

## 面试话术

> 「做自然语言转 SQL，我先把元数据管起来。设计了一套标准模板，四张清单：表、字段、字段级血缘、关联关系。导入就是一条带数据质量检核的 ETL，19 条规则分两级，错误阻断，警告留痕；装载时先写临时文件再替换，保证原子性，全量重建保证幂等。这一层有 82 个单元测试，不依赖模型。」

被追问时可以展开的三点：

- 为什么分错误和警告：真实资料里几百张表没有主键，全当成错误就永远导不进来；引用了不存在的表或字段则必须拦住。
- M14 这条规则的由来：血缘里的表名漏了模式名，会被悄悄当成外部源，血缘链断了却不报错。
- 为什么全量重建：元数据只有几万行，全量是秒级的，换来的是可以随便重跑。
