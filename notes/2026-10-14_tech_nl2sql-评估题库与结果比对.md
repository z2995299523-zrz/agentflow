## 📖 讲透

### 1. 七类题各考什么

| 类别 | 题数 | 考的能力 | 例子 |
|------|------|----------|------|
| 基础时点余额 | 8 | 单表、口径明确，能不能选对表、带对日期 | 某日全行对公贷款余额 |
| 口径区分 | 6 | 名字相近的字段能不能选对 | 不含保证金的存款余额，和含保证金的存款余额 |
| 维度关联 | 6 | 会不会关联维表，粒度有没有搞错 | 按行业、按一级分行、余额最高的十个客户 |
| 时间口径 | 5 | 较年初、较上月、日均、相对日期 | 较年初的增量，年日均 |
| 向上溯源 | 5 | 专题层没有的维度，能不能上溯到整合层并还原加工条件 | 按币种、按贷款产品、按五级分类 |
| 反问 | 5 | 口径没说清时，会不会先问再生成 | 只说「存款余额」，没说含不含保证金 |
| 追问 | 5 | 第二轮能不能接着第一轮继续问 | 先查全行余额，再说「按一级分行拆开」 |

前五类对应模拟库里的五类埋点，后两类对应「反问一次再生成」和「连续追问」这两个功能。

### 2. 执行准确率：比结果，不比 SQL 文本

判一条生成的 SQL 对不对，有两种比法：

| 比法 | 问题 |
|------|------|
| 和标准 SQL 比文本 | 同一个查询有无数种写法：关联的先后、用不用公共表表达式、别名怎么起。写法不同但结果相同的会被误判为错；只差一个字段名、结果完全不同的，文本却非常相似 |
| 各自执行，比查出来的结果 | 只认结果。写法不同没关系 |

这里用的是第二种，叫执行准确率：两条 SQL 在同一个库上执行，结果一致就算对。

这和改造一个加工作业之后的验证方法是一回事：没有人靠对比新旧脚本的文本来确认改对了，都是新旧两个版本对同一天的数据各跑一遍，比对结果。

### 3. 四条比对规则

| 规则 | 理由 |
|------|------|
| 数值四舍五入到 2 位小数后再比 | 金额的精度就是分。浮点数计算会带来 0.1 + 0.2 ≠ 0.3 这类误差，不能让这种误差导致误判 |
| 不看列名、不看列顺序，生成结果允许多出列 | 别名怎么起、列怎么排是风格问题。多查一个客户名称出来，也不算错 |
| 标准结果的每一列都要在生成结果里找到对应的列，并且要按行对应 | 只有每一列的取值都对上还不够，同一行里的值必须是配套的。否则把两个客户的余额互换，每一列的取值集合都没变，却会被判成对 |
| 题目要求排序时按顺序逐行比较，否则不计行顺序 | 只有「前十名」这类题才关心顺序。其它题没写排序，行的顺序本来就是不确定的 |

### 4. 埋点的区分度测试

这是这套题库里最重要的一组测试。

一道「口径区分」题，如果用错的字段和用对的字段查出来的结果恰好一样，那这道题就白出了，它分辨不出模型到底有没有选对口径。所以给口径、溯源和日均这几类埋点，各配了一条**看上去合理的错误写法**，测试要求它的结果必须和标准答案不同（关联、选表，以及日期类里除年日均以外的几种情况，还没有配，已记入待办）：

| 题 | 错误写法错在哪 |
|----|----------------|
| K01 | 该用不含保证金的字段，用成了全口径的字段 |
| K06 | 把各机构的客户数直接相加，跨机构开户的客户被重复计数 |
| T03 | 该取年日均，取成了时点余额 |
| U01、U02、U03 | 上溯到整合层，但没有还原「剔除无效客户」这个加工条件 |
| U01（另一种） | 上溯时带上了客户维表，却忘了「不含保证金」的条件 |

一次真实的对比（在模拟库上分别执行两条 SQL，再调用 `compare_results`）：

```text
题目 K01：查 2026 年 9 月末全行不含保证金的对公存款余额
标准 SQL，取不含保证金的字段 dep_bal_rmb：         2,011,120,088.23
错误写法，取全口径的字段 dep_bal_tot_rmb：         2,056,988,290.29
compare_results 的判定：不一致
```

类比写数据质量检核规则时要做的一件事：故意造一条脏数据，确认规则真的能把它查出来。一条从来不报警的规则，没法知道它是数据没问题，还是规则本身不起作用。

### 5. 反问题和追问题的结构

**反问题**没有标准 SQL。它的题面故意少说一个口径，例如「查 2026 年 9 月末各开户机构的对公存款余额」，没说含不含保证金。期望的行为是工具先反问，判分看的是工具有没有反问，而不是它生成的 SQL。类比：需求方只说「存款余额」时，开发要先问清口径再写 SQL，而不是自己猜一个。

**追问题**有两轮输入，标准 SQL 是第二轮的答案：

```yaml
- id: F01
  category: 追问
  turns:
    - "查 2026 年 9 月末全行不含保证金的对公存款余额"
    - "按一级分行拆开，列出一级分行名称和余额"
  expect: sql
  gold_tables: [ads.org_corp_dep_bal_d, dim.org]
  gold_columns: [ads.org_corp_dep_bal_d.dep_bal_rmb, dim.org.lvl1_org_nm]
  gold_sql: |
    SELECT o.lvl1_org_nm, SUM(b.dep_bal_rmb) AS dep_bal_rmb
    FROM ads.org_corp_dep_bal_d b
    JOIN dim.org o ON b.org_no = o.org_no
    WHERE b.data_dt = DATE '2026-09-30'
    GROUP BY o.lvl1_org_nm
```

第二轮那句「按一级分行拆开」单独看是不完整的，要把第一轮的日期和口径继承过来，才是一个完整的需求。类比：需求方在同一张需求单上补一句「按分行拆开」，前面定好的口径和日期都不变。

除了标准 SQL，每道题还登记了标准用表（`gold_tables`）和关键字段（`gold_columns`）。它们用来算另外两个指标：选表对不对、关键字段选得对不对。执行准确率只能告诉你这道题错了，这两个指标能告诉你错在哪一步。类比：对账不平时，先看差在哪张表、哪个字段，再去翻明细。

### 6. 题面为什么要写明列出哪些列

「查各一级分行的存款余额」，结果里列机构号还是机构名称？两种都说得通。如果题面不写，模型列了机构号、标准答案是机构名称，判成错就有争议。

所以凡是涉及维度的题，题面都写明「列出一级分行名称和余额」。这样结果对不上就是真的错，不是出题不严谨。类比：报表需求要写清楚输出哪些字段、什么格式，验收时才有标准可依。

另外，评估时把「今天」固定成 2026-10-13，这样题面里的「上月末」永远是 2026-09-30，题目不会因为哪天跑而变。类比：跑批用的是批量日期参数，而不是系统当前时间，哪天重跑都能得到同样的结果。

## 🔧 选型

**题库用 YAML，不用 JSON。** 标准 SQL 是多行文本。JSON 里多行文本要写成一行、换行写成 `\n`，没法读也没法审。YAML 有块文本的写法（`gold_sql: |`），SQL 可以原样分行写，还能加注释。题库是要给人审核的，可读性比什么都重要。类比：加工脚本是分行、带注释地存成 `.sql` 文件，而不是把整段 SQL 塞进配置表的一个字段里。

**列对应用「先按取值找候选，再搜索一种不重复的对应方式」。** 生成结果的列名和列顺序都不可信，只能靠内容把列对上。做法分两步：

1. 对标准结果的每一列，在生成结果里找出取值完全相同的列，作为候选。一个都找不到，直接判错。
2. 候选可能不止一个（两列的取值可能恰好一样），所以要搜索：每个标准列选一个候选，互相不重复，并且选出来之后整行也对得上。

为什么不直接取第一个候选：两列取值相同的时候，取第一个可能取错，导致本来正确的结果被判错。列数一般只有几列，搜索的开销通常可以忽略；不过同值的列很多时，搜索量按排列数增长（实测 11 个同值列约 15 秒），这是已知的局限。

类比两张没有约定字段名的表做对账：先看哪些字段的数据分布一样，把字段对上，再逐行核对。

## 💡 可迁移

**1. 标准答案加自动判分。** 任何生成类的任务都可以这样评估：先准备一批有标准答案的题，定好判分规则，写成一条命令能跑完的程序。之后每一次改动都有数字可以对比。类比：口径调整上线前，新旧口径并行跑数、逐项比对差异。

**2. 评估集和样例集必须不重叠。** 后面要给模型看一批历史 SQL 样例。如果样例里有题库里的题，等于开卷考试，测出来的准确率是虚高的。类比：开发调试时用过的数据不能再拿来做验收，否则问题测不出来。

**3. 给评估本身写测试。** 判分规则有 17 项测试，题库有 84 项测试。尺子不准，量出来的东西没有意义。类比：对账程序本身也要先用一份已知有差异的数据验一遍，确认它真能报出差异。

## 👨‍💻 代码

本节的片段取自仓库里的代码，做了删节。

**一道题的结构（`eval/questions.py`）。** 用 Pydantic 定义，题目写错了在读取时就会报出来：

```python
class EvalQuestion(BaseModel):
    """一道评估题"""

    id: str
    category: str
    turns: list[str] = Field(min_length=1, max_length=2)    # 一轮或两轮用户输入
    expect: Literal["sql", "clarify"]                       # 期望得到 SQL，还是期望被反问
    gold_sql: str = ""                                      # 标准 SQL，目标库方言
    gold_tables: list[str] = Field(default_factory=list)    # 标准用表
    gold_columns: list[str] = Field(default_factory=list)   # 关键字段，写成 表.字段
    ordered: bool = False                                   # 结果是否要求行顺序

    @model_validator(mode="after")
    def _check_consistency(self) -> "EvalQuestion":
        has_sql = bool(self.gold_sql.strip())
        if self.expect == "sql" and not has_sql:
            raise ValueError(f"{self.id}: 期望得到 SQL 的题必须有标准 SQL")
        if self.expect == "clarify" and has_sql:
            raise ValueError(f"{self.id}: 期望被反问的题不应有标准 SQL")
        return self
```

例子：一道期望得到 SQL 的题如果忘了写标准 SQL，读取题库时直接报「期望得到 SQL 的题必须有标准 SQL」。相当于给题库这张表加了检查约束。

**读取（`load_questions`）。** 除了逐题校验，还检查编号有没有重复，相当于主键唯一：

```python
items = yaml.safe_load(Path(path).read_text(encoding="utf-8"))
questions = [EvalQuestion(**item) for item in items]
ids = [question.id for question in questions]
duplicated = sorted({item for item in ids if ids.count(item) > 1})
if duplicated:
    raise ValueError(f"题目编号重复: {duplicated}")
```

例子：题库里如果有两道题都叫 A01，读取时直接报「题目编号重复: ['A01']」，不会等到评估跑到一半才发现。

**比对（`eval/compare.py` 的 `compare_results`）。** 先把每个单元格规范化，数值统一成保留两位小数的十进制数：

```python
if isinstance(value, (int, float, Decimal)):
    number = value if isinstance(value, Decimal) else Decimal(str(value))
    if not number.is_finite():
        return str(number)
    return number.quantize(TWO_PLACES, rounding=ROUND_HALF_UP) + 0     # 加 0 把 -0.00 规范成 0.00
```

然后分两步找列的对应关系。第一步找候选：

```python
pred_signatures = [column_signature(pred, index) for index in range(pred_width)]
candidates: list[list[int]] = []
for gold_index in range(gold_width):
    signature = column_signature(gold, gold_index)
    matches = [index for index in range(pred_width) if pred_signatures[index] == signature]
    if not matches:
        return False
    candidates.append(matches)
```

第二步搜索一种不重复的对应方式，并确认整行对得上：

```python
def search(gold_index: int, chosen: list[int]) -> bool:
    if gold_index == gold_width:
        projected = [tuple(row[index] for index in chosen) for row in pred]
        return (projected if ordered else Counter(projected)) == target
    return any(search(gold_index + 1, chosen + [index])
               for index in candidates[gold_index] if index not in chosen)
```

例子：标准结果是（客户号, 余额）两列；生成结果是（余额, 客户名称, 客户号）三列。第一步，标准的「客户号」列对上生成结果的第 3 列，「余额」列对上第 1 列。第二步，从生成结果里按（第 3 列, 第 1 列）取出来，和标准结果逐行相同，判为一致。多出来的客户名称不影响结果。

不计顺序时用的是 `Counter`，也就是按「每种行出现几次」来比，所以重复的行也会被正确计数。

## ⚠️ 常见坑

1. **生成结果多出列，或者列的顺序不同。** 这不算错，比对规则已经容许。反过来，标准结果里有的列，生成结果里没有，就是错。
2. **浮点数舍入。** 直接用浮点数比较，`0.1 + 0.2` 和 `0.3` 不相等。先转成十进制数，四舍五入到两位小数再比。负的零（`-0.00`）也要规范成零。
3. **空值不等于零。** 没有数据时合计是空值，不是 0。比对时空值就是空值，不会和 0 混为一谈。测试还要求每道题的标准答案里不能有空值，避免题目本身建立在一个空结果上。
4. **前 N 名出现并列。** 第 10 名和第 11 名余额相同时，取谁是不确定的，标准 SQL 和生成的 SQL 可能取到不同的行。目前要求排序的只有两道题，模拟数据里它们的第 10 名和第 11 名不并列（D03 的第 10 名是 74,357,916.30、第 11 名是 57,779,394.06；F04 的第 10 名是 4,579,802.00、第 11 名是 3,917,125.90）。将来换数据时要重新确认，或者在题面里写明并列时的第二排序依据。
5. **YAML 里带冒号的中文句子要加引号。** YAML 用冒号加空格表示键值对，题面里如果出现这种写法而没加引号，会被解析成一个字典。题库里所有的题面都用双引号括了起来。

## 面试话术

> 「我是先建评估再做功能的。题库四十道分七类，覆盖模拟库里埋的五种易错点，加上反问和追问。判分看执行结果：生成的 SQL 和标准 SQL 都在模拟库上跑，比结果不比文本，就像新旧作业并行跑数对账。我还写了区分度测试：关键埋点各配一条看似合理的错误写法，结果必须和标准答案不同。」

被追问时可以展开的三点：

- 四条比对规则：金额四舍五入到分；不看列名和列顺序并允许多出列；每一列都要找到对应列而且整行对得上；只有要求排序的题才比顺序。
- 为什么要测区分度：一道题如果用错的口径也能得到同样的结果，它就分辨不出模型有没有答对。
- 评估集和样例集不重叠，否则等于开卷考试。
