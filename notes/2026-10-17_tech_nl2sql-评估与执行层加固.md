## 📦 目标

模型生成的 SQL 是不可信的输入：可能是笛卡尔积，可能在注释里夹带语句。批量跑它之前，先把「执行」和「判分」这两把尺子加固；再写评估程序，对 A（仅模型结构）、B（加血缘）、C（加血缘和样例）三组各跑 40 题，量出血缘和样例各带来多少提升，错题归因到具体步骤。

| 交付物 | 文件 | 要点 |
|--------|------|------|
| 执行层 | `nl2sql/executor.py`、`dialect.py` | 超时中断、只取需要的行、去注释、去 ANSI 转义 |
| 比对 | `eval/compare.py` | 大数、日期时间、同值列合并成组 |
| 题库 | `eval/questions.py`、`nl2sql_questions.yaml` | 其它正确答案、K06 换门槛、区分度与并列检查 |
| 评估程序 | `eval/nl2sql_eval.py` | 并发、归因、断点续跑、报告、真实库静态评估 |

数字指标：全量 1085 项测试通过（新增 222 项）；0.5 秒的超时实际 0.56 秒中断；12 个同值列比对 1.4 毫秒（原实现 5 秒没跑完）；10 道题登记了其它正确答案，逐条结果一致、校验 0 错误。评估程序用假流水线测，没有调模型。

## 📖 讲透

### 1. 执行：到点打断，只读需要的行

工作线程里执行并读取结果，主线程等 `timeout_s` 秒，到点调 `interrupt()`。读取只取 `max_rows + 1` 行，多的那一行用来判断后面还有没有，所以 `row_count` 是实际返回的行数。类比：调度平台给作业设超时、到点杀会话；分页多取一行就知道有没有下一页，不必 `COUNT(*)`。

### 2. 注释夹带语句

sqlglot 默认把注释原样塞进输出，不转义正文。`SELECT 1 -- */ ; SELECT 2; SELECT 3 /*` 在 PostgreSQL 里只有一条语句，转成 DuckDB 方言却变成 `SELECT 1 /* */ ; SELECT 2; SELECT 3 /* */`，DuckDB 执行三条、返回最后一条的结果。改成 `comments=False`，注释不进输出。类比：质检脚本只数分号，注释里写的分号照样骗得过它。

### 3. 比对：取值相同的列合并成组

生成结果里取值完全相同的列可以互换，合并成组，列对应只在组间做；每选一列就拼出行核对，对不上的分支立刻放弃。12 个同值列由 12!（约 4.8 亿）种排列降成一步。类比：对账前先给每个字段算取值指纹，指纹相同的字段不必逐个比。

### 4. 其它正确答案

机构汇总表能答的 10 道题（B03、B06、K01、K02、K03、D01、T02、T03、F01、F03），客户汇总表按机构 GROUP BY 也得同样的结果。题里登记 `alternatives`，选表、字段准确率按「标准答案和各条其它写法」中任一组算对，其它写法的用表取自校验器。类比：同一个指标既能从明细加工也能从汇总层取，验数时两个来源都认。

### 5. 题库的条件要在数据里真的起作用

K06 的「大于零」去不掉任何一条记录，去掉条件、换字段都得 120，正好是客户维表的行数。改成 100 万元并写明「逐条记录比较」（否则「先按客户汇总再比」也说得通），各写法的结果两两不同：

| 写法 | 结果 |
|------|------|
| 标准：去重计数，全口径 > 100 万 | 96 |
| 去掉金额条件 / 换成不含保证金的字段 | 120 / 94 |
| 不去重 `COUNT(*)` / 先按客户汇总再比 | 102 / 98 |

D05（上级机构名归并、层级选错）、T02（拿 1 月 1 日当年初）、T04（对行求平均）也配了错误写法；D03、F04 的第 N 名与第 N+1 名不并列写成测试。U05 的 `cust_type` 条件仍然不起作用，不改数据，写进报告的局限。类比：检核规则上线前造一条脏数据，确认它真会报警。

### 6. 评估程序

追问题第二轮带上第一轮的需求，第一轮反问了就再带反问，以最后一轮计分。错题按八条规则取第一条命中的归因：失败停在哪一步、多余的反问或该问没问、召回漏表、选表不对、字段或口径不对、执行失败（单列一节）、修正两次仍未通过校验、结果不一致。每题完成立刻追加到 `{配置}.jsonl`，`--resume` 跳过已做的，类比调度作业的断点重跑。

## 🔧 选型

| 决策 | 选了什么 | 没选什么 | 原因 |
|------|----------|----------|------|
| 超时 | 工作线程执行，主线程等，到点 `interrupt()` | 信号、子进程 | 信号在 Windows 上没有；子进程要重开库、再把结果传回来 |
| 取行 | `fetchmany(max_rows + 1)` | `fetchall` 后切片 | 万亿行的交叉连接整个读回来会耗尽内存 |
| 去注释 | `comments=False` | 正则剔除注释 | 注释正文里可以写 `*/`，正则判断会失效 |
| 并发 | 每次执行各开只读连接 | 共享连接加锁 | 超时要打断的就是这一个连接 |
| 判分 | 三项指标各自「任一组」 | 要求同一组 | 契约如此，也便于看是哪一步错 |

## 💡 可迁移

**1. 不可信的输入在入口限时限量。** 外部文件、第三方接口进数仓前先限行数、设超时，别等落地后再发现撑爆。

**2. 判分规则别被「顺序」「别名」卡住。** 把等价的写法归并成组再比，比枚举所有排列便宜得多。

**3. 给判分本身造反例。** 区分度测试、并列检查、归因的每条规则各有一例，和给检核规则造脏数据是一回事。

## 👨‍💻 代码

多取一行判断是否截断，超时打断：

```python
rows = cursor.fetchmany(limit + 1)
return columns, rows[:limit], len(rows) > limit        # 多取的一行只用来判断后面还有没有

worker.join(timeout_s)
if worker.is_alive():
    con.interrupt()
    worker.join(INTERRUPT_GRACE_S)                     # 最多再等 5 秒
```

列合并成组后边选边剪枝：

```python
if comparable(extended) != target(depth + 1):          # 已选的列拼出的行，必须是标准结果对应几列的行
    continue
```

例子：标准结果 13 列，前 12 列取值相同，第 13 列是金额；生成结果的金额列行对应不上。以前先试完 12 个同值列的全部排列才发现，现在选完同值列组、核对金额列时就剪掉，1.4 毫秒返回 False。

## ⚠️ 常见坑

1. **`interrupt()` 不是瞬间的，也不管内存。** 带 `ORDER BY` 的交叉连接要 0.77 秒才停，所以打断后最多再等 5 秒，仍没退出就报「中断未生效」；超时只管时间，读回内存的行数还得靠 `max_rows + 1` 限住。
2. **Decimal 默认 28 位。** 取整到两位小数时，绝对值 ≥ 1e26 的数会抛 `InvalidOperation`，精度要按数的位数现算。
3. **空集合是任何集合的子集。** 其它写法读不出表时若成了空组，召回会被判成全对，所以不成组。
4. **断点续跑遇到残缺的最后一行。** 进程被打断时最后一行可能没写完，续跑前先补换行，否则新记录粘在残缺行后面。
5. **现算的日均和现成的日均字段差几分钱。** 逐行四舍五入造成，T03、T04 因此只认现成字段，写在报告的局限里。

## 面试话术

> 「批量执行模型生成的 SQL 前我先加固了尺子：执行层有超时和限量读取，注释里的 `*/` 加分号不能让单语句检查失效；比对把取值相同的列合并成组，12 个同值列从阶乘级降到毫秒；题库里机构表能答的题登记了客户表的写法，选表准确率不会把对的判错。」

被追问时可以展开的两点：

- 为什么 K06 要换门槛：条件在数据里去不掉任何一条，错误写法也会得到同样的 120，题就分辨不出对错。
- 为什么读取只取 `max_rows + 1` 行：多的一行判断是否截断，又不会把笛卡尔积读回内存。
