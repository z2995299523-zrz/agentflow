# NL2SQL 向量索引：字段与样例的向量化、存进元数据库、全量相似度检索

> 日期: 2026-10-15 | 类别: tech | 关联: [[2026-10-13_design_nl2sql专题库改造]]、[[2026-10-14_tech_nl2sql-元数据层]]

---

## 📦 目标

用户问「各机构的不良贷款余额」，库里有两万多个字段。程序要先回答：哪些字段、哪几张表可能跟这句话有关？关键字匹配只能抓字面上的重叠，用户说「存款规模」、字段叫「存款余额」就漏了。向量检索补的就是这一块：把一段文字变成一串数，意思相近的文字，数也相近。

交付物都在 `metadata/index.py` 一个文件里，向量存在元数据库的 `meta_vector` 和 `meta_info` 两张表里：

| 交付物 | 作用 |
|--------|------|
| 向量器接口 `Embedder` | 把一批文本变成 L2 归一化的 float32 向量，自带名称和维度 |
| `BgeEmbedder` | 正式用的：本地 BGE 模型，延迟加载、进程内单例、优先离线、有 GPU 就用 |
| `HashEmbedder` | 测试用的：哈希向量器，不需要模型，结果确定，对中文字词敏感 |
| `build_vectors` | 导入时为全部字段和样例算向量，并给出一节导入报告 |
| `VectorIndex` | 查询时的全量相似度检索，支持「只在这些编号里找」 |

数字指标：这一层共 44 项单元测试（哈希向量器 8、文本与编号 3、建向量 7、入库与导入 8、检索 9、向量器选择与 BGE 加载 9），全部不加载模型，几秒跑完。真实专题库上的结果：22728 条字段向量、512 维；模型已加载时构建 13.7 秒，新进程从零开始整个导入 31.9 秒（文件缓存是热的）；加载元数据库约 0.7 秒；单次检索平均 4.5 毫秒。

## 📖 讲透

### 1. 向量是什么，为什么一次矩阵乘就能找最像的

向量模型把一段文字映射成一个 512 维的定长数组。可以把它理解成：给每个字段生成一行 512 列的特征数据，意思相近的文字，特征值也相近。

判断两段文字像不像，就是比较两个数组的夹角，叫余弦相似度。如果每个数组的长度都先缩放成 1（L2 归一化），夹角的余弦就等于两个数组逐位相乘再求和（点积）。这样，「查询向量」和「全部字段向量组成的矩阵」做一次矩阵乘，就一次性得到查询和每个字段的相似度。

### 2. 每个字段存什么文本

字段向量的文本是 `表中文名 字段中文名`，用空格连接。例子（模拟库）：

```text
对公客户贷款余额日汇总 不良贷款余额
```

为什么要带表中文名：「余额」「客户号」这样的字段名在几十张表里都有，不带表名，向量里就分不出是哪张表的字段。样例的文本是 `需求 口径`。

**为什么不放口径说明。** 设计文档 4.6 节的原文是 `表中文名 + 字段中文名 + 口径说明`，实现时有意去掉了口径说明，设计文档由控制者在收尾时修订。原因：真实库里的口径说明多是加工过程的描述（「加工：……」「按某某汇总」），属于血缘信息，不是字段的含义。把它混进向量文本，一个很短、很干净的「表名加字段名」就被一堆加工术语冲淡了，相似度被稀释。在真实库的专题层上用 4 个手写查询对比过：去掉口径说明之后，第一名的得分普遍高 0.07 到 0.10，混进来的干扰项（字段中文名里没有查询词、只是说明里提到相关词）明显减少。口径说明没有丢，它还在元数据库的 `meta_column` 里，留给后面的证据环节，连同血缘一起交给模型读。

每条向量的编号是 `模式.表.字段`（样例是 `文件名#序号`）。后面召回时要按表归组，从编号里截掉最后一段就是表标识。

### 3. 导入流程里的位置

```
读清单 → 校验 → 补全（脚本、血缘、关联、样例） → 算向量 → 写临时文件（元数据 + 向量） → 一次替换 → 报告
                                                  │
                                                  └─ 加 --no-index：跳过这一步，不加载模型，召回只能走关键字
```

向量和元数据写进同一个临时文件，全部成功之后再整体替换正式文件。这和元数据层那篇讲的做法一致：好比把索引和数据放在同一个库、同一个事务里刷新，不会出现「数据换了、索引还是旧的」。

导入报告里多出一节：

```text
## 向量

- 向量器：hash-bigram-512
- 维度：512
- 字段向量：93 条
- 样例向量：0 条
- 耗时：0.01 秒
```

### 4. 为什么不用 Chroma

项目里原来的 RAG 模块用 Chroma。这一次没有沿用，原因有三条：

1. **Windows 上目录被占用就无法替换。** Chroma 的持久化目录里有常驻打开的 SQLite 和索引文件，Windows 上文件被占用就不能删、不能改名。而我们的导入靠「写临时文件、再整体替换」保证原子性，必须随时能把旧库换掉。
2. **导入要求原子性。** 元数据在 SQLite 里，向量在 Chroma 里，是两个存储，中间没有跨库事务。换到一半失败，就会出现「元数据是新的、向量是旧的」，而且不报错。向量放进同一个 SQLite 文件，一次替换，要么全新要么全旧。
3. **读取时整库载入内存、不占文件。** `MetadataStore` 构造时把整个库读进内存、立刻关掉连接，向量也一起读成 numpy 矩阵。之后重新导入不会被正在读的程序挡住。Chroma 是常驻打开的目录，做不到这一点。

### 5. 全量相似度，就是没有索引时的全表扫描

22728 条 × 512 维 × 4 字节 ≈ 46 MB。一次扫描在本机上平均 4.5 毫秒。

这就像几万行的表不用建索引：全表扫描比走索引还快，建了反而多一份维护成本。近似检索索引（HNSW 之类）还有一个副作用：同样的查询，两次的结果可能不完全一样，对要求「可复现」的评估不利。

检索 `VectorIndex.search(查询向量, k, allowed)` 的规则：

- 结果按相似度降序；相似度相同的，按编号升序。
- `allowed` 是「只在这些编号里找」，先过滤再取前 k 条，不是先取前 k 条再过滤。召回时用它把范围限制在某几张表的字段里。
- k 比总条数大就全部返回；查询向量的维度和索引对不上就报错，多半是换了向量器。

### 6. 记录向量器的名称，防止新旧混用

`meta_info` 里存两行：向量器名称和维度。不存时间戳，所以同一套资料重复导入，库逐字节相同。

查询向量必须和库里的向量出自同一个向量器，否则两个空间里的数没有可比性。维度不同，`search` 直接报错；但两个向量器恰好都是 512 维时（比如 BGE 和 512 维的哈希向量器），程序不会报错，只是结果毫无意义。所以查询前要先比对 `store.embedder_name`。这就像两个口径不同的指标不能直接相减，口径版本号必须跟着数据走。

### 7. 哈希向量器：测试用的替身

单元测试不能加载 BGE：导入模型库要好几秒，还依赖 GPU。可测试又需要「相似度有意义」，随机向量测不出这一点。所以做了一个哈希向量器：

1. 文本先做 NFKC 归一（全角转半角）并转小写。
2. 拆成三类特征：汉字单字（权重 0.5）、相邻两个汉字的二元组（权重 1.0）、ASCII 整词（权重 1.0）。
3. 每个特征用 `crc32` 算出落进 512 个桶的哪一个，另一个 `crc32` 的最高位决定加还是减。
4. 把桶里的数累加起来，最后做 L2 归一化。空文本得到零向量。

这就是哈希分区：把无限多的特征词压进固定的 512 个桶，难免有碰撞，但一份文本只有几十个特征，碰撞很少。加减号的作用是让碰撞的噪声一半为正、一半为负，大致互相抵消。

它对中文字词的重叠敏感：「贷款余额」和「不良贷款余额」共用二元组「贷款」「款余」「余额」，相似度约 0.78；和「机构号」没有任何共同的字词，相似度是 0。但它不懂同义词，所以只能用来测程序逻辑，不能拿来评价召回效果，召回效果要在 BGE 上评估。

### 8. BGE 的加载策略

- **延迟加载。** `sentence_transformers` 要好几秒才能导入，所以模块顶层不导入它，第一次真正调用 `embed` 时才加载。创建对象、传空列表都不触发加载。
- **进程内单例。** 加载一次，之后复用。
- **优先离线。** 先用 `local_files_only=True` 只看本地缓存；缓存里没有，再联网下载（走 `HF_ENDPOINT` 镜像）；两条路都不通，抛 `RuntimeError`，提示导入时可以加 `--no-index`。不静默降级，因为悄悄换成别的向量器，等于悄悄让召回变差。
- **有 CUDA 就用 CUDA。**

### 9. 环境变量切换

`default_embedder()` 每次调用都重新读环境变量 `METADATA_EMBEDDER`：`hash` 返回哈希向量器，`bge` 或没设置返回 BGE，其它值抛 `ValueError`。`tests/conftest.py` 顶部设了 `METADATA_EMBEDDER=hash`，所以测试里无论哪条路径（包括子进程、导入期）拿到的都是哈希向量器。这就像 ETL 里生产和测试靠连接配置切换数据源，而不是改代码。

## 🔧 选型

| 决策 | 选了什么 | 没选什么 | 原因 |
|------|----------|----------|------|
| 向量模型 | 本地 BGE-small-zh-v1.5 | 云端 Embedding 接口、更大的 bge-large | 项目的 RAG 模块已经在用，模型已缓存；中文效果好；512 维、体积小；本地免费，数据不出本机。字段文本很短，更大的模型收益有限。类比：能用本地的工具，就不依赖外部服务 |
| 存哪里 | 元数据库里的 BLOB | Chroma、单独的向量文件 | 和元数据在同一个文件里，一次替换；读取时整库进内存，不占文件。见上面三条理由 |
| 怎么检索 | numpy 全量扫描 | HNSW 之类的近似索引 | 两万多条，扫一遍只要几毫秒；近似索引还会让结果带随机性。类比：几万行的表不建索引 |
| 向量精度 | float32 | float16、int8 量化 | 体积本来就不大；量化会让「存进库再读出来逐位相同」这条校验失效 |
| 字段文本放什么 | 表中文名加字段中文名 | 再加上口径说明 | 真实库的口径说明多是加工过程的描述，属于血缘信息，混进去会稀释相似度（实测第一名得分低 0.07 到 0.10）。口径说明留给后面的证据环节，交给模型读 |
| 测试替身 | 哈希向量器 | 随机向量、加载真模型 | 随机向量没有语义，测不出「相似度有意义」；真模型慢，还依赖 GPU 和网络 |
| 同分怎么排 | 按编号升序 | 不规定 | 结果必须确定，评估才能复现 |

## 💡 可迁移

**1. 重资源加可替换的接口。** 向量模型又慢又重，所以只依赖一个 `Embedder` 协议（名称、维度、`embed` 方法），正式环境用 BGE，测试用确定性的假实现，靠环境变量切换。任何依赖慢的、贵的、外部服务的组件（模型、第三方接口）都可以这样隔开。类比：ETL 里给上游接口表造测试数据，不去连生产库。

**2. 派生数据和源数据同进同出。** 向量是从元数据派生出来的，所以和元数据写进同一个文件、同一次替换。凡是「由 A 算出来的 B」，A 和 B 要么一起换，要么都不换。

**3. 给派生数据打上「生成方式」的标签。** 向量器名称和维度跟着数据存起来，使用前先比对。类比：数据血缘里记加工版本，口径变了，下游要知道。

**4. 先量一下，再决定要不要建索引。** 全表扫描只要几毫秒，就不用建索引。

**5. 把随机因素管起来。** 哈希种子、并行汇总的顺序、GPU 的浮点误差，都会让结果不确定。要做回归测试，就得在设计里把它们逐个管住，并且写进测试。类比：对账，并行汇总的顺序不同，合计会差一分钱，对不平又找不到原因。

**6. 检索的文本只放「是什么」，不放「怎么算出来的」。** 语义检索比的是含义；加工过程是另一类信息（血缘），有自己的查询办法。混在一起，含义被冲淡，两类信息都用不好。类比：报表的字段名只写指标名称，计算口径另放一份说明文档。

## 👨‍💻 代码

下面的片段都取自仓库里的代码，为了讲解做了删节。

**哈希向量器（`metadata/index.py`）。** 特征落桶用 `crc32`，不用 Python 内置的 `hash()`：

```python
@lru_cache(maxsize=1 << 16)
def _slot(feature: str, dim: int) -> tuple[int, float]:
    data = feature.encode("utf-8")
    bucket = zlib.crc32(data) % dim
    sign = -1.0 if zlib.crc32(SIGN_SALT + data) >> 31 else 1.0      # 另一个 crc 的最高位决定正负
    return bucket, sign
```

拆特征：二元组只在连续的汉字之间取，标点、空格、英文都会把它隔断：

```python
for run in TOKEN_PATTERN.findall(unicodedata.normalize("NFKC", text).lower()):
    if run.isascii():
        yield run, WORD_WEIGHT                      # ASCII 整词
        continue
    for char in run:
        yield char, CHAR_WEIGHT                     # 汉字单字
    for start in range(len(run) - 1):
        yield run[start:start + 2], BIGRAM_WEIGHT   # 汉字二元组
```

累加进桶，再归一化：

```python
weights: dict[int, float] = {}
for feature, weight in _features(text):
    bucket, sign = _slot(feature, self.dim)
    weights[bucket] = weights.get(bucket, 0.0) + sign * weight
norm = math.sqrt(sum(value * value for value in weights.values()))
if norm > 0.0:                                      # 空文本没有特征，保持零向量
    for bucket, value in weights.items():
        matrix[row, bucket] = value / norm
```

**字段文本（`field_text`）。** 只有表中文名和字段中文名，口径说明有意不放：

```python
def field_text(table: TableMeta, column: ColumnMeta) -> str:
    return " ".join(part for part in (table.table_cn, column.column_cn) if part)
```

**建向量（`build_vectors`）。** 顺序与资料里的字段顺序一致，所以同样的资料每次得到同样的结果；分批向量化，并检查向量器返回的形状：

```python
for column in mart.columns:
    table = tables.get(column.table_id)
    if table is not None:
        field_ids.append(field_ref_id(column.table_id, column.column_name))
        field_texts.append(field_text(table, column))
...
for start in range(0, len(texts), batch_size):
    batch = texts[start:start + batch_size]
    part = np.asarray(embedder.embed(batch), dtype=np.float32)
    if part.shape != (len(batch), embedder.dim):

```

**检索（`VectorIndex.search`）。** 先算全部得分，再过滤，再取前 k 条；平局压在第 k 名的边界上时，也按编号取：

```python
scores = np.einsum("ij,j->i", self._matrix, vector)
...
if k < count:
    threshold = np.partition(scores, count - k)[count - k]      # 第 k 名的得分
    candidates = np.flatnonzero(scores >= threshold)            # 包括与第 k 名同分的
else:
    candidates = np.arange(count)
chosen = candidates[np.lexsort((ranks[candidates], -scores[candidates]))][:k]   # 先按得分降序，再按编号名次升序
```

| 加载 `MetadataStore` | 带向量约 0.7 秒，不带向量 0.3 到 0.5 秒 |
| 建 `VectorIndex` | 8.5 毫秒 |
| 单次检索（k=30） | 全量平均 4.5 毫秒，最大 14.2 毫秒；限定在 1667 个字段内平均 4.8 毫秒 |
| 查询文本向量化 | 单条约 10 毫秒 |

## ⚠️ 常见坑

1. **不要用 Python 内置的 `hash()`。** 它的种子每个进程都不同，同一段文本，两次运行得到的向量不一样，测试结果会飘，重复导入的库也不会相同。哈希向量器用 `crc32`，并且有一条测试专门在另一个进程里、换一个哈希种子，比对向量是否逐位相同。类比：用随机数做分区键，同一条数据每次落在不同分区。
2. **相同的两个向量，矩阵乘出来的得分可能差最后一位。** 矩阵乘向量（`矩阵 @ 向量`）走 BLAS，不同位置的行累加的顺序可能不同。本机实测：两行完全相同的向量，得分有时不一样。结果是「同分按编号排」的规则失效，排序会抖动。所以检索用了 `einsum`，它对每一行用同一种累加顺序。有一条测试专门造了高维的重复向量来锁住这一点。类比：并行汇总金额，顺序不同，浮点合计差一分钱。
3. **导入模型库很慢。** `import sentence_transformers` 要十几秒，所以模块顶层不能导入它，否则所有测试都变慢。BGE 的加载策略用一个假的 `sentence_transformers` 来测，整个测试文件不加载真模型。本机项目所在的 D 盘是机械盘：文件缓存是热的时候，导入这个库约 13 到 20 秒，加载模型不到 1 秒；隔夜之后第一次导入，这一步用过 342 秒（推测是 torch、transformers 的一大堆文件要从机械盘重新读）。看上去像卡死，其实是在读盘，等一等就好。
4. **Windows 上的导入顺序。** 实测：进程里已经导入了 openpyxl 时，如果先初始化 CUDA（比如调用 `torch.cuda.is_available()`），再导入 `sentence_transformers`，导入 pyarrow 那一步会内存访问冲突，进程直接退出，没有任何 Python 异常。必须先导入 `sentence_transformers`，再探测设备。加载策略里有一条测试锁住这个顺序。
5. **国内连不上 huggingface.co。** 所以优先用 `local_files_only=True` 读本地缓存；联网下载走镜像。镜像地址通过环境变量 `HF_ENDPOINT` 设置，它必须赶在导入 `huggingface_hub` 之前设好，晚了不生效。
6. **SQLite 默认的 4 KB 页，装不下两条向量。** 一条向量约 2 KB，加上编号和文本约 2.2 KB，4 KB 的页放不下第二条，每页只放一条，将近一半空间浪费。实测向量让库增大了 91 MB，而不是向量本身的 47 MB。把页大小设成 16 KB，整个库降到 59 MB 左右，加载时间没有变差。这是建库那一层的事，建库前加一句 `PRAGMA page_size`。
7. **口径说明不进向量文本。** 原因见「讲透」第 2 节：真实库里的口径说明多是加工过程的描述，混进来会稀释相似度。真实专题库里只有专题层的字段有口径说明，而且每个字段都有，整段字段文本平均约 84 个字符、最长 684 个字符，里面夹着「加工：……」；其它层的字段文本平均只有十几个字符。用 4 个手写查询对比，去掉口径说明之后，专题层的第一名得分普遍高 0.07 到 0.10，混进来的干扰项明显减少。副作用：文本变短之后，查询词恰好是某张表的名字时，这张表里的通用字段（比如「数据日期」）也会得到不低的分数，按表归组召回时没问题，但命中字段的列表里会有这类噪声。
8. **哈希向量器的相似度只反映字面重叠。** 它不懂同义词，不能拿来评价召回效果。召回的质量要在 BGE 上评估。
9. **GPU 算出来的向量不保证逐位相同。** 真实库重复导入时，只比较表、字段、血缘、关联，不比较 BGE 向量；用哈希向量器的话，可以比较到每一个字节。
10. **向量器返回的东西要检查。** 向量器声明的维度和实际返回的形状对不上、含有 NaN，都直接报错；长度明显不是 1 的向量，建库时会重新归一化。否则写进库的向量悄悄有问题，召回变差却不报错。

## 面试话术

> 「NL2SQL 要先从两万多个字段里召回候选。我用本地 BGE 模型把『表名加字段名』向量化，口径说明不放进去，因为真实库里它多是加工过程，会稀释相似度。向量和元数据放进同一个 SQLite 文件，一次替换，导入是原子的。检索用 numpy 全量扫描，几毫秒，不用向量数据库。」

被追问时可以展开的四点：

- 为什么不用 Chroma：Windows 上目录被占用就没法替换；元数据和向量分在两个存储，没有跨库事务，没法保证原子；读取时我要整库进内存、不占文件。
- 为什么口径说明不进向量：真实库里的口径说明多是加工过程，属于血缘，不是字段含义；实测去掉之后第一名的得分高 0.07 到 0.10，干扰项少了。口径说明没丢，还在元数据库里，后面交给模型读。
- 哈希向量器怎么做、局限在哪：汉字单字、二元组、英文整词散列到 512 个桶，对字词重叠敏感，但不懂同义词，只用来测程序逻辑。
- 同分排序为什么要特别处理：矩阵乘走 BLAS，相同的向量得分会差最后一位，排序就抖；换成逐行同序累加，并用测试锁住。
