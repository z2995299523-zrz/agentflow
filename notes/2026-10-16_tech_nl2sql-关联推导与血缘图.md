## 📦 目标

模型设计文档里的「关联关系」，相当于 ER 图上的连线：哪两张表能 JOIN、用哪几个字段、是多对一还是多对多。真实专题库没有这份清单（模板里它本来就是可选的），但生成 SQL 离不开它：

- **选 JOIN 字段**：模型要知道两张表该用哪个字段关联；
- **静态校验 R6**：SQL 里的等值关联不在已知关联里，就警告「乱关联」；
- **防发散**：关联的对应关系决定会不会出现「明细表关联维表时没带全主键，金额翻倍」。

人填不现实（真实库 833 张表），但线索散落在三处：加工脚本里写过的 ON 条件、血缘里直取的字段、表的粒度字段。这一步把三处线索变成关联，并在此之上做一个血缘图，提供确定性的查询。

交付物是两个文件：

| 交付物 | 文件 | 作用 |
|--------|------|------|
| 关联推导 | `metadata/relations.py` | 手工、脚本、血缘传递、同名粒度键四种来源合并，定向、去重、排序，输出报告节 |
| 血缘图 | `lineage/graph.py` | 字段上下游链路（带每一跳的加工条件）、同源差异、上下游表闭包、关联路径、是否唯一 |

导入时由 `enrich_mart` 在「解析脚本、合并血缘」之后调用 `derive_relations`，报告里多出「关联关系推导」一节；血缘图在启动时由元数据库建出，之后只做查询。

数字指标：

- 单元测试 151 项（关联推导 107、血缘图 44），全量 708 项；只用模拟库和手写的小资料，不调模型、不加载向量模型，几秒跑完。我还对两个文件做了 17 处人为改动（去掉层级规则、传递出的 N:N 不丢、BFS 不防环等），每一处都至少有一个测试失败。
- 模拟库推导出 41 条关联：手工 1、脚本 7、血缘传递 15、同名粒度键 18。35 道标准 SQL 在推导之前有 14 条 R6 警告（全是缺关联），现在 0 错误 0 警告。
- 真实专题库（只读验证，在内存里跑，只记数字）：1971 条关联、1909 对表，脚本 114、血缘传递 656、同名粒度键 1201；推导 0.8 秒，建血缘图 0.8 秒。用 45 个脚本自己的 SELECT 校验，R6 警告从 249 条降到 21 条，这 21 条全部能解释，推导漏掉的为 0。

## 📖 讲透

### 1. 四种来源和优先级

| 优先级 | 来源 | 证据 | 模拟库里的例子 |
|:------:|------|------|----------------|
| 1 | 手工 | 关联关系清单里人填的 | 存款汇总与贷款汇总按（日期、客户、机构）一对一 |
| 2 | 脚本 | 加工脚本里实际写过的等值关联，追溯到实体表字段 | 存款快照关联客户维表（`cust_no`）；机构信息表自关联（`up_org_no = org_no`） |
| 3 | 血缘传递 | 脚本里写过的关联，顺着直取血缘换成同一批值的其它表 | 专题层存款汇总的 `cust_no` 直取自整合层，所以它也能关联客户维表 |
| 4 | 同名粒度键 | 表 S 含有表 T 的全部粒度字段（按字段名），S 就能关联 T | 机构汇总表按 `org_no` 关联机构维表 |

同一个映射（同一对表加同一组字段）被几个来源同时推出时，**只留优先级最高的**，另一个当旁证丢掉。类比对账：同一笔账既有银行流水又有内部记账，以银行流水为准。

### 2. 对应关系：用粒度判断一侧是否唯一

粒度字段就是业务主键。判断规则是三值的：

| 一侧的状态 | 含义 |
|------------|------|
| `True` | 表有粒度，关联键覆盖了全部粒度字段：这一侧每个键值最多一行 |
| `False` | 表有粒度，但关联键没覆盖全：这一侧一个键值可能对上多行 |
| `None` | 表没填粒度：**判断不了**，不能当成「不唯一」 |

两侧合起来：两侧都 `True` 是 1:1；只有右侧 `True` 是 N:1（左侧填没填粒度都一样，右侧唯一就足够了）；只有左侧 `True` 是 1:N；两侧都 `False` 是 N:N；其余（缺粒度，判断不了）记为「未知」。

类比关联发散：汇率表的粒度是（数据日期，币种）。账户表只用币种去关联汇率，键没覆盖全部粒度，右侧不唯一，一个币种对上一年的汇率，金额就翻几百倍；加上数据日期，才是 N:1。

**统一定向。** 推导结果一律写成「多的一侧在左、唯一的一侧在右」：1:N 把左右对调翻成 N:1。1:1、N:N、未知本来就对称，规定下游层的表放左边，同层按表名排。这样同一个映射不会正反各出现一条，去重才做得准，用的人也只需要记一条规则：左边的表每行最多对上右边的一行，不会发散。

手工填写的关联不翻、不改：那是人的意思，原样保留。

### 3. 键域：同一批值的字段

同一个客户号从贴源层账户表一路直取到整合层、专题层，这些表里的 `cust_no` 说的是同一批客户。把被「直取」边连在一起的字段归成一个**键域**，用并查集求连通分量：

- 直取对来自两处：合并后血缘里 `is_passthrough` 为真的边，以及脚本里类别为直取的目标字段（清单与脚本不一致时两边都算）；
- 凡是出现在脚本关联键里的字段都要建节点，没有直取边的字段自己单独成一个键域；
- 键域编号按每个键域里最小的字段排序、从 0 开始，和输入顺序无关。

模拟库有 29 个键域，最大的 4 个字段。真实库 6978 个，最大 17 个字段。

### 4. 血缘传递：同一键域里的表互相能关联，但要有界

脚本里出现过「A.a = B.b」，那么 A.a 所在键域里的其它表，和 B.b 所在键域里的其它表，也能按对应的字段关联。

模拟库的例子：21 号脚本写了 `dwd.corp_dep_acct_d.cust_no = dim.corp_cust.cust_no`。

```
键域 X：ods.core_dep_acct.cust_no ─直取→ dwd.corp_dep_acct_d.cust_no ─直取→ ads.corp_cust_dep_bal_d.cust_no
键域 Y：ods.ecif_corp_cust.cust_no ─直取→ dim.corp_cust.cust_no
```

X 里有 3 张表，Y 里有 2 张表，组合起来 6 对，去掉脚本里写过的那一对，传递出 5 条，其中就有 `ads.corp_cust_dep_bal_d → dim.corp_cust`。它的说明写明依据：`键域传递：21_ads_corp_cust_dep_bal_d.sql 中 dwd.corp_dep_acct_d.cust_no = dim.corp_cust.cust_no`。

规则和限制：

- **一张表在键域里恰好有一个字段才算候选。** 一张表里有两个字段在同一键域（比如两个字段都直取自同一个源字段），不知道该用哪个，不猜。
- **复合键：每个键域都要有字段落在同一张表里**，k 个键域取交集。模拟库的 `(ccy_cd, data_dt)` 关联汇率表，整合层存款快照两个字段都有，就能传递；专题层存款汇总只有 `data_dt`，不行。
- **组合要排除**：两侧是同一张表的、和脚本里写过的映射相同的。
- **字段清单里没有的字段、不在表清单里的外部表**，可以在键域里把别的字段连起来，但自己出不了候选（关联里不能出现清单里没有的字段）。

三道闸，为的是传递出来的东西有界：

| 上限 | 值 | 挡的是什么 |
|------|----|------------|
| 键域大小 `MAX_DOMAIN_SIZE` | 50 个字段 | 键域太大，说明连错了或者是一个泛滥的通用字段，不从它传递 |
| 单次传递 `MAX_PROPAGATION_PER_JOIN` | 400 对 | 两侧各有十几张表时，组合是平方级的，整条跳过 |
| 传递出的 N:N | 丢掉 | 团里两侧都不唯一的组合没有任何证据，留着只会让 SQL 发散。脚本里实际写过的 N:N 有人这样用过，保留 |

### 5. 同名粒度键

表 T 的粒度字段是 G。表 S 按名字含有 G 的全部字段，S 就可以按这些字段关联 T，对应关系是 N:1（G 同时覆盖 S 自己的粒度时是 1:1）。这是最弱的证据：只是同名。所以限制最多：

- **排除通用键名**：`id`、`uuid`、`guid`、`row_id`、`rowid`、`pk_id`。粒度全是这些名字的表不参与（只要有一个字段不是通用名就参与）。不加这条，真实库探针能推出上万对：整合层有 32 张表的粒度就是 `id`，近三百张表都有 `id`。
- **层级规则**：S 的层级不低于 T，即同层，或者下游表去关联上游表。查询从下游的事实表出发去关联上游的维表和明细，反过来（上游表去关联下游表的粒度）没有业务含义，还会让候选翻倍。
- **被关联次数上限 `MAX_GRAIN_FANIN`**：一张表被超过 150 张表按同名粒度键关联，整张跳过，写进报告请人看。这样的表多半粒度字段是个泛滥的名字。

模拟库按这个规则生成 38 条候选，其中 20 条与更高优先级的来源重复被合并，留下 18 条。

### 6. 合并、去重、每对表最多三种映射

流程：手工、脚本、血缘传递、同名粒度键依次产生候选 → 按**规范写法**去重（无序表对加字段映射，与左右顺序、键对顺序无关；同一映射先到的留下，所以优先级高的赢）→ 每对表按排序键取前三种 → 全部关联按排序键排序。

**每对表最多三种，而不是设计文档原来写的「只留一条」。** 同一对表之间可能真的有多种关联方式。模拟库里机构维表和机构信息表之间：

```
lineage    机构信息表.up_org_no → 机构维表.org_no     (按上级机构号：机构维表的 org_no 直取自机构信息表)
grain_key  机构维表.org_no      → 机构信息表.org_no    (按机构号，1:1)
```

只留一条会丢掉其中一种真关联。上限取 3 是经验值：真实库里 1853 对表只有一种映射，50 对两种，6 对三种，没有一对超过。手工关联不受这个上限限制。

**排序键 `relation_rank`**（越小越优），依次比较：来源优先级；对应关系安全度（N:1 和 1:1 最安全，其次未知，N:N 最后）；两侧字段是否同名；左表层级（下游在前）；表名、字段名的字典序，最后是对应关系和说明。要是**全序**，输出才确定：同样的输入，顺序必须一样，测试里打乱表、字段、血缘的顺序，结果必须逐条相等。

### 7. 血缘图：确定性查询，不碰模型

`LineageGraph` 启动时从元数据库一次建好：字段的出入边、每张表的脚本片段、表一级的上下游、按表对归组的关联。

| 查询 | 做法 |
|------|------|
| `upstream` / `downstream` | 广度优先，**每条边只报一次、每个字段只展开一次**，所以成环、菱形都不会重复或死循环；`depth` 限制跳数 |
| 每一跳的 `Hop` | 除了来源、加工逻辑，还带这一跳**目标表**的过滤条件和关联条件，以及脚本里展开后的表达式。上溯到更低的层查数时，必须带上专题层加工时的过滤，数才对得上 |
| `compare` | 两个字段各自的来源（含自己）取交集，得到共同上游；有共同上游、但两条链路上每一跳的来源、表达式、过滤、关联条件不完全一致，就是「同源但口径不同」 |
| `upstream_tables` / `downstream_tables` | 表一级求闭包，近的在前，可按层级过滤；**边有两个来源**：血缘边，以及「目标表的脚本语句里引用到的实体表 → 目标表」 |
| `join_path` | 直连优先；没有直连时最多经过一张中间表，在能连通的中间表里先选不发散的；两张以上中间表返回 `None` |
| `is_unique` | 一组字段覆盖全部粒度为 `True`，否则 `False`；表没有粒度字段时 `None` |

**为什么上游表要把脚本里的表算进来。** 维表往往只出现在 JOIN 里，不是任何字段的血缘来源：例如「关联客户维表，剔除客户号无效的记录」，客户维表没有一个字段流进汇总表，但汇总表的数是少了无效客户之后的数。只看血缘边，召回时上溯就漏掉了这张表。所以闭包的边要加上脚本语句里引用到的实体表（取自 `joins` 和自包含查询 `select_sql` 里的全部实体表，后者能覆盖子查询和逗号连接里的表）。

**`join_path` 的方向。** 路径上每一步的对应关系按行进的方向写：存的是 `汇总表 → 维表` 的 N:1，反过来从维表走向汇总表就是 1:N，会让行数变多，`fan_out` 为真。方向不翻，发散就判错。

**同一张表被几个脚本写入**：每条血缘边带着自己的脚本名，取条件时优先取这个脚本里的语句；脚本名对不上时才取这张表的全部语句。

### 8. 导入报告里的「关联关系推导」怎么读

模拟库上的输出：

```text
## 关联关系推导
- 关联 41 条，涉及 40 对表：手工 1、脚本 7、血缘传递 15、同名粒度键 18
- 对应关系：N:1 36、1:1 5、1:N 0、N:N 0、未知 0
- 每对表的映射数：1 种 39 对、2 种 1 对、3 种 0 对
- 去重和每对上限之前的候选：脚本 7、血缘传递 15、同名粒度键 38；与更高优先级的来源映射相同、合并掉 20 条
- 脚本里的等值关联 8 处，去重后 7 种映射；其中 0 种有一侧不在表清单里、0 种用到字段清单里没有的字段，没有计为脚本关联
- 键域 29 个，最大 4 个字段；超过 50 个字段的键域挡掉 0 种脚本映射的传递（这些映射的候选共 0 对）
- 单次传递的候选超过 400 对而整条跳过 0 种脚本映射（这些映射的候选共 0 对）
- 同名粒度键：0 张表被超过 150 张表关联，整张跳过（少生成 0 条）
- 传递出的 N:N 丢掉 0 条
- 每对表超过 3 种映射而去掉 0 条
- 被关联次数最多的 5 张表（涉及的表数 / 关联条数）：ods.org_info（8 张 / 10 条）、dim.corp_cust（8 张 / 8 条）、…
```

各行回答的问题：来源是否均衡（只有同名粒度键，说明脚本和血缘线索太少）；未知多不多（多就是缺粒度）；各道闸挡了多少（挡得多说明数据有问题，要看被挡的是什么）；**被关联最多的 5 张表是给人看的**：它们是关联图里的枢纽，多半是主数据表，也可能是被一个泛滥的字段名误连起来的，人一眼就能看出来。

## 🔧 选型

| 决策 | 选了什么 | 没选什么 | 原因 |
|------|----------|----------|------|
| 同一对表保留几种 | 按「无序表对 + 字段映射」去重，最多 3 种，最优排第一 | 设计文档原文：只留一条 | 同一对表可能真有几种关联（按上级机构号、按机构号）；只留一条会丢掉真关联 |
| 去重的键 | 规范写法：每个键对两端排序，再取集合 | 直接比较左右表和列表 | 同一映射正着写、反着写、键对换顺序，都应该是同一个 |
| 推导结果的方向 | 统一成 N:1，对称的把下游层的放左边 | 保留脚本里的写法 | 写法依赖脚本里谁写在前面，没有稳定的含义；统一后「左边每行最多对上右边一行」 |
| 手工关联 | 原样保留，不翻方向，不受每对上限限制 | 一起定向、一起限制 | 人写的就是人的意思；手工的对应关系仍用 N:1、1:1、1:N 三种校验 |
| 传递出的 N:N | 丢掉 | 保留 | 键域里的团，两侧都不唯一，没有证据；脚本里写过的才有 |
| 键域 | 并查集求连通分量 | 建 networkx 图 | 只要连通分量，并查集几行代码，还能保证编号确定 |
| 键域里的候选 | 恰好一个字段的表 | 随便挑一个 | 一张表里两个字段在同一键域，选错就是错关联 |
| 脚本里字段清单缺口、外部表 | 不计为脚本关联，但照常参与键域和传递 | 一律丢掉，或一律保留 | 关联里不能出现清单里没有的字段（校验器 R4 会报错，R6 又说放行，自相矛盾）；但键域里的事实不会因此作废 |
| 上限 | 键域 50、单次 400、被关联 150、每对 3 | 不设限 | 同名粒度键不设限能推出上万对，团的组合是平方级 |
| 血缘链路防环 | 每条边报一次、每个字段展开一次 | 枚举全部路径 | 路径数在菱形、多来源下指数增长；只要知道有哪些边、各在第几跳 |
| 上游表的边 | 血缘边加脚本里引用的实体表 | 只看血缘边 | 维表常常只出现在 JOIN 里 |
| 关联路径 | 直连优先，最多一张中间表 | 任意最短路径 | 两张以上中间表的路径，每一步的不确定性叠加，没有可信度，宁可返回 `None` |
| 输出顺序 | 全序排序键，输入顺序无关 | 依赖遍历顺序 | 重复导入的结果必须逐条相同，测试里打乱输入验证 |

## 💡 可迁移

**1. 「值域相同」比「名字相同」可靠，所以先找键域。** 数据建模里判断两个字段能不能关联，最可靠的是它们取值来自同一个源（直取），其次才是名字相同。做数据治理时，用血缘把字段聚成「同源字段簇」，再在簇上传递已知的关联，比逐表猜字段名准得多。

**2. 推断出来的东西一定要有闸。** 传递会产生团：键域里 12 张表对 12 张表就是 144 对。凡是「由 A 推出 B」的规则，都要预先想好最坏情况下会推出多少，设上限，并把被挡掉的数量写进报告，不然规则越对，噪声越大。

**3. 统一方向和规范写法，是去重的前提。** 关联、血缘、依赖这类对称或半对称的关系，先定一个规范写法（方向、排序），再比较，否则「同一件事被记了两遍」永远清不干净。

**4. 有三值的判断就保留第三个值。** 「粒度没填」不等于「不唯一」。把未知当成否，是把没有信息伪装成有信息，下游会据此做出错误的判断（这里是把没填粒度的表都判成会发散）。

```python
def _covers(table, columns):
    if not table.grain_columns:
        return None                                   # 没填粒度：判断不了
    return set(table.grain_columns) <= set(columns)

def cardinality(left, left_cols, right, right_cols):
    left_unique, right_unique = _covers(left, left_cols), _covers(right, right_cols)
    if left_unique and right_unique:
        return "1:1"
    if right_unique:
        return "N:1"
    if left_unique:
        return "1:N"
    if left_unique is False and right_unique is False:
        return "N:N"
    return "未知"
```

**血缘链路：每条边一次，每个字段展开一次。**

```python
def _walk(self, start, depth, forward):
    edges = self._outgoing if forward else self._incoming
    hops, seen, queue = [], {start}, deque([(start, 0)])
    while queue:
        node, level = queue.popleft()
        if level >= depth:
            continue
        for edge in edges.get(node, ()):
            hops.append(self._hop(level + 1, edge))                # 边：每次展开自己的出入边，各报一次
            following = (edge.target_table, edge.target_column) if forward else (edge.source_table, edge.source_column)
            if following not in seen:                              # 字段：只展开一次，成环、菱形都不会重复
                seen.add(following)
                queue.append((following, level + 1))
    return hops
```

**关联路径：直连优先，其次选不发散的中间表；反向走要翻对应关系。**

```python
direct = self._best_step(a, b)
if direct is not None:
    return self._path([direct[0]])
best = None
for middle in sorted(self._neighbors.get(a, set()) & self._neighbors.get(b, set())):
    first, second = self._best_step(a, middle), self._best_step(middle, b)
    path = self._path([first[0], second[0]])                       # fan_out：任何一步是 1:N、N:N、未知
    score = (path.fan_out, max(first[1], second[1]), min(first[1], second[1]), middle)
    if best is None or score < best[0]:
        best = (score, path)
return best[1] if best else None
```

## ⚠️ 常见坑

1. **1:N 不翻成 N:1，同一映射会正反各一条。** 去重的键必须与方向无关，输出还要统一方向，否则报告里「关联多少条」是虚的。
2. **同一键域里一张表有两个字段，不要随便挑一个。** 两个日期字段都直取自同一个源日期，选错就是错关联；恰好一个才算候选。
3. **复合键传递要对每个键域取交集。** 只有一个键域里有字段的表，不能算候选，否则把（币种、日期）的关联传递成只按币种，立刻发散。
4. **自关联的方向。** `up_org_no = org_no`：多的一侧（上级机构号）在左，唯一的一侧在右。写成反的，R6 用的是与方向无关的字段对，不受影响，但「左边每行最多对上右边一行」的约定就破了。
5. **字段清单里没有的字段，不能出现在关联里。** 脚本补出来的血缘边，来源字段可能不在字段清单里（清单缺这个字段）。让它入键域是对的（它确实把别的字段连起来了），让它出现在关联里就错了：校验器 R4 会说字段不存在，R6 又说关联已知，自相矛盾。真实库里有一个字段造成了 11 条这样的情况，报告里写明了，补全清单后重新导入就会变成关联。
6. **组合是平方级的。** 键域里 12 张表对 12 张表就是 144 对，其中大多是 N:N 或未知。上限要在设计时就定，并把挡掉的数量写进报告；这次真实库的最大值是 144，离 400 还远，但换一个数据快照就不一定。
7. **粒度是代理键（`id`）的表，业务键关联会被判成 N:N 或未知。** 粒度字段如果记录的是自增代理键，用业务键关联时「键没覆盖粒度」，判成不唯一，哪怕这个业务键事实上也唯一。这是资料的问题，不是算法的问题；报告里的未知和 N:N 偏多时，先检查粒度字段填的是不是业务主键。
8. **拿脚本自己的 SELECT 测 R6，脚本来源的关联天然通过。** 关联是从脚本里来的，再拿脚本去检验，等于自己对自己。真正能测出推导质量的，是和脚本无关的标准 SQL（模拟库 35 题，0 警告），以及传递出的关联是否合理。
9. **条件的一侧追溯到 UNION 时，键对是来源的笛卡尔积。** 一侧是 UNION 的几个分支时，每个分支各与另一侧关联，都是真的；两侧都是 UNION 时，一半是交叉的假键对（分支 1 的列对分支 2 的列）。真实库里有一个脚本里两处这样的写法，产生了两种假映射。关联推导没有办法区分，需要脚本解析给出分支序号才能过滤。
10. **去重后别忘了每对上限的计数要取非负。** 每对表的映射数少于上限时，「去掉多少条」是 0，不是负数；我一开始写成了「映射数减上限」直接累加，模拟库上报告出现了「去掉 -79 条」。
11. **用全序排序键。** 排序键只比较来源、安全度、字段名，遇到两条只有说明不同的关联时顺序就不确定。最后一项要加上对应关系和说明。
12. **血缘链路里菱形不是环。** A 由 B、C 加工，B、C 都来自 D：D 要报两条边（B←D、C←D），但只展开一次。遇到走过的字段就连边一起跳过，会丢掉第二条边；每次都展开，又会重复展开 D 的上游。

## 面试话术

> 「真实库没有关联关系清单，我从四处推：手工填的、加工脚本里写过的等值关联、顺着直取血缘在同一个键域里传递，还有同名粒度键。高优先级的覆盖低的，每对表最多留三种映射。同名键不设限能推出上万对，所以加了键域大小、单次传递、被关联次数三道上限。再配一个血缘图，查上下游和关联路径，全是确定性代码。」

被追问时可以展开的三点：

- 为什么每对表留三种而不是一条：同一对表可能真有几种关联方式，比如机构表既按机构号、也按上级机构号；只留一条会丢真关联。
- 键域怎么保证传递是对的：只沿直取血缘连，值是同一批；一张表在键域里恰好一个字段才算候选；传递出的 N:N 没有证据，直接丢。
- 关联发散怎么判：靠粒度，关联键覆盖了某一侧的全部粒度，这一侧就唯一；没填粒度就是未知，不当成不唯一。
