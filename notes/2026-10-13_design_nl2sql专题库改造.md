# NL2SQL 改造设计：基于专题库模型结构与血缘的自然语言转 SQL

> 日期: 2026-10-13 | 类别: design | 状态: 待评审
> 关联: [[2026-10-13_discuss_nl2sql改造需求澄清]]

---

## 1. 目标与范围

### 1.1 目标

把 AgentFlow 从「通用 AI 助手」改造成一个查数副驾驶：使用者用自然语言描述查数需求，
工具结合专题库的**模型结构**（数据字典）和**血缘关系**（血缘清单 + 加工脚本），生成可审核的查询 SQL。

工具不替人做决定。它输出 SQL 的同时说明「为什么用这张表、这个字段、这么关联」，由人审核后拿去执行。

### 1.2 已确认的决策

| 事项 | 决策 |
|------|------|
| 使用场景 | 先用模拟专题库做通并出评估指标；资料格式标准化，之后可换真实专题库资料 |
| 可获得的资料 | Excel/Word 数据字典、字段级血缘清单（不带加工逻辑）、ETL 加工脚本 |
| 血缘的作用 | 搞清字段口径、选对表、找关联路径、向上溯源查数，四项都要 |
| 运行方式 | 只生成不执行；执行层可插拔，模拟库上可执行 |
| SQL 方言 | GaussDB / PostgreSQL 系 |
| 主要需求类型 | 余额/规模统计（时点余额、日均、较年初与较上月增量） |
| 技术方案 | 元数据库 + 血缘图 + 分步流水线 |
| 旧功能 | 下线替换：先打标签保留旧版本，评估后切换并删除旧模块 |
| 口径歧义 | 反问一次再生成 |
| 连续追问 | 纳入 v1，合并进需求解析，流水线无状态 |
| 历史 SQL 样例库 | 纳入 v1，`.sql` 文件加注释头 |
| 真实专题库与模拟库 | 真实库为主，模拟库保留。真实库本机没有数据、无法执行，可执行的评估只能在模拟库上做 |
| 真实资料的接入方式 | 专用转换器，读生成设计文档的元数据库、标准层索引库和当前加工脚本；转换器与转换结果都放在不入库的本地目录 |

沿用的假设（讨论中提出，未被否定）：使用者是懂 SQL 的数据开发人员；模拟专题库按银行对公存贷款业务构造；真实元数据不进入本仓库。

真实专题库属于另一个业务领域，本文档不记录它的任何具体内容，只记录它对设计提出的要求。

### 1.3 成功标准

1. 模拟专题库导入报告 0 错误，造数后的对平检核全部通过。
2. 不依赖模型的单元测试全部通过，`python run_tests.py --quick` 全程不调用模型。
3. 三组对照实验跑完并产出评估报告。主指标目标：完整配置下执行准确率 ≥ 80%。这是目标而非承诺，首次实测值记为基线，其余指标只记录基线。
4. 界面两页、接口 4 个可用。
5. 把 `MART_DIR` 指向另一套按模板整理的资料即可使用，不改代码。
6. 旧模块下线，README、CLAUDE.md、bridge.md 更新。

### 1.4 v1 不做

- 连接真实库执行 SQL
- 自动识别任意版式的 Word/Excel 数据字典（真实资料通过专用转换器接入，见 4.7 节）
- 清单与脚本的一致性核对

原先列在这里的「血缘清单缺失时从脚本解析血缘」已经改为要做：真实资料里约三成专题层字段没有记录标准层血缘，而加工脚本全部可以解析，所以放进第二份计划。清单里有记录的以清单为准，没有的从脚本解析补上并标注来源。
- 业务术语表
- 图表
- 权限与多用户
- 界面上一键把生成结果存为样例

## 2. 总体架构

### 2.1 两条线

和数仓一样分离线、在线两条线。离线把资料加工进元数据库，在线跑查询流水线。

```
【离线：元数据入库】
表清单/字段清单 ──┐
血缘清单 ─────────┤
关联关系(可选) ───┼→ 导入器(先校验后入库) → 元数据库 metadata.db
加工脚本 *.sql ───┤                          ├ 表、字段
样例 *.sql ───────┘                          ├ 字段血缘边(带加工表达式)
                                             ├ 表关联关系(四种来源)
                                             ├ 加工脚本片段(按目标表)
                                             └ 样例
                                           → 向量索引(字段和样例的中文描述)

【在线：查询流水线】
本轮输入 + 上一轮完整需求
   ↓
①需求解析 → ②候选召回 → ③血缘展开 → ④选表定口径 → ⑤生成SQL → ⑥静态校验 → ⑦输出 → 执行层(可选)
  模型         代码         代码          模型           模型         代码        代码
               ↑ 上溯回路                    │              ↑ 修正回路   │
               └─────────────────────────────┤              └────────────┘
                                             └→ 反问（结束本轮，等用户回答）
```

七个步骤里只有 ①④⑤ 调用模型。血缘遍历、候选召回、校验都是确定性代码，同样输入必然得到同样结果。

### 2.2 模块划分

| 模块 | 职责 | 依赖 |
|------|------|------|
| `metadata/` | 标准格式定义、读取、校验、脚本解析、样例解析、关联关系推导、元数据库读写、向量索引 | 无（底层） |
| `lineage/` | 血缘图与关联图的确定性查询 | `metadata/` |
| `nl2sql/` | 流水线七个步骤的业务逻辑、模型调用封装、执行层 | `metadata/`、`lineage/` |
| `graph/` | LangGraph 编排：状态、节点、连线、回路 | `nl2sql/` |
| `prompts/nl2sql.py` | 三个模型步骤的提示词和方言规则 | 无 |
| `data/mock_mart/` | 模拟专题库的资料与造数 | `metadata/` |
| `eval/` | 题库、评估、对照实验 | 全部 |

每个模块只通过明确的接口对外。`lineage/` 不知道模型的存在，`nl2sql/` 的每一步都可以用假模型和小型夹具资料单独测试。

## 3. 元数据标准格式

这是模拟资料和真实资料共用的「接口表」。一套资料放在一个目录里，包含四张清单：表清单、字段清单、血缘清单、关联关系。四张清单可以是一个 `metadata.xlsx` 里的四个 Sheet，也可以是四个 CSV 文件（`表清单.csv` 等，UTF-8 带 BOM，Excel 可直接打开；Excel 另存出来的 GBK 编码也能读），两种形式的列完全相同。模拟专题库用 CSV，便于版本对比；真实资料用 Excel 更顺手。

表的唯一标识是 `模式名.表英文名`，全小写，例如 `ads.corp_cust_dep_bal_d`。字段清单、血缘清单、关联关系里的表名一律写这个全名。

### 3.1 表清单

| 列 | 必填 | 说明 |
|----|------|------|
| 层级 | 是 | 只能取 `贴源层`、`整合层`、`专题层`。真实环境层级更多时，映射到最接近的一档 |
| 模式名 | 是 | 数据库模式名 |
| 表英文名 | 是 | |
| 表中文名 | 是 | |
| 表类型 | 是 | 只能取 `快照表`、`流水表`、`维表`、`全量表` |
| 粒度字段 | 否 | 能唯一确定一行的字段，逗号分隔，例如 `data_dt,cust_no`。不清楚可以留空，留空后无法判断关联是否会发散 |
| 数据日期字段 | 快照表必填 | 例如 `data_dt` |
| 表说明 | 否 | |

快照表是每个数据日期保存一份全量，查询必须带日期条件。全量表是每次清空后全量重装，只有当前状态，查询不需要日期条件。

表类型、粒度字段、数据日期字段这三列在数据字典里一般没有现成的，需要尽量补上。它们用来防统计类查询的两个经典事故：快照表忘加数据日期导致数值跨日累加，关联发散导致金额翻倍。真实资料里有相当一部分表查不到主键，所以粒度字段是选填，缺失时导入给警告。

### 3.2 字段清单

| 列 | 必填 | 说明 |
|----|------|------|
| 表名 | 是 | 全名 |
| 字段英文名 | 是 | |
| 字段中文名 | 是 | |
| 数据类型 | 否 | 不清楚可以留空，缺失时导入给警告 |
| 是否主键 | 否 | `是` 或留空 |
| 口径说明 | 否 | 数据字典里对该字段的说明 |
| 码值说明 | 否 | 例如 `1=对公;2=个人` |

### 3.3 血缘清单

| 列 | 必填 | 说明 |
|----|------|------|
| 目标表 | 是 | 全名 |
| 目标字段 | 是 | |
| 源表 | 是 | 全名。不在表清单里的源表视为外部源 |
| 源字段 | 是 | |
| 加工逻辑 | 否 | 有则优先使用；没有则从加工脚本解析回填 |
| 加工脚本 | 否 | 脚本文件名 |

一个目标字段有多个来源时写多行。

### 3.4 关联关系（可选）

| 列 | 必填 | 说明 |
|----|------|------|
| 左表、左字段 | 是 | 复合键的多个字段用逗号分隔 |
| 右表、右字段 | 是 | |
| 对应关系 | 是 | `N:1`、`1:1`、`1:N` |
| 说明 | 否 | |

只用来补充自动推导不出来的关联。自动推导见 4.4。

### 3.5 加工脚本

`scripts/` 目录下的 `.sql` 文件原样放入，PostgreSQL/GaussDB 方言。批量日期等参数写成带引号的 `'${参数名}'` 时可以被结构化解析，其它写法退化为只保存原文。

### 3.6 样例

`examples/` 目录下的 `.sql` 文件，一个文件可放多条。每条以 `-- 需求:` 开头，`-- 口径:` 可选，之后是 SQL，到下一个 `-- 需求:` 或文件末尾结束。

```sql
-- 需求: 查 2026 年 6 月末各二级分行对公贷款余额
-- 口径: 折人民币
SELECT ...
```

## 4. 元数据入库

### 4.1 导入流程

命令行入口：`python -m metadata.importer [资料目录]`，不带参数时用 `MART_DIR`。

```
读取四张清单 → 标准化(标识符小写、去空格) → 校验 → 解析加工脚本 → 回填加工表达式
→ 推导关联关系 → 解析并校验样例 → 算向量 → 写入元数据库（向量与其余内容在同一个文件里）→ 输出导入报告
```

每次全量重建。先写临时文件，全部成功后再替换，所以失败时原有元数据库不受影响，重复执行结果相同。
导入报告同时打印到终端并写入 `build/import_report.md`。

### 4.2 校验规则

错误会让整次导入中止，警告只记入报告。

| 规则 | 级别 |
|------|------|
| 清单或必填列缺失，必填单元格为空 | 错误 |
| 表重复，或同一张表内字段重复 | 错误 |
| 层级、表类型取值不在允许范围内 | 错误 |
| 表清单里的表在字段清单里没有任何字段 | 错误 |
| 字段清单里的表不在表清单里 | 错误 |
| 表名没有带模式名（字段清单、血缘清单、关联关系） | 错误，并给出正确写法。不会被当成外部源放过 |
| 粒度字段、数据日期字段不在该表的字段清单里 | 错误 |
| 快照表没有填数据日期字段 | 错误 |
| 血缘的目标表或目标字段不在字段清单里 | 错误 |
| 血缘的源表在表清单里，但源字段不在字段清单里 | 错误 |
| 手工关联关系引用了不存在的表或字段 | 错误 |
| 手工关联关系的对应关系取值非法，或左右字段个数不一致 | 错误 |
| 血缘的源表不在表清单里 | 警告，记为外部源 |
| 血缘存在环 | 警告，遍历时有防重入保护 |
| 整合层或专题层的表没有任何血缘记录 | 警告 |
| 表没有填粒度字段 | 警告，按层级汇总成一条。真实资料里这类表有几百张，逐张列出没人看 |
| 表里有字段没有填数据类型 | 警告，每张表一条 |
| 脚本语句无法结构化解析 | 警告，只保存原文 |
| 脚本的目标表不在表清单里 | 警告 |
| 样例 SQL 未通过静态校验 | 只拒收该条样例，写入报告，不中止导入 |

### 4.3 脚本解析

用 sqlglot 按 PostgreSQL 方言解析。对每条 `INSERT ... SELECT` 或 `CREATE TABLE ... AS SELECT` 提取：

- 目标表
- 来源表及其别名
- 关联：关联的表、关联类型、关联条件、其中的等值键对
- 过滤条件：`WHERE` 的原文
- 每个目标字段对应的 `SELECT` 表达式

同一个脚本文件里，目标表语句引用的临时表，其建表语句一并归入该目标表的脚本片段。

**回填。** 血缘清单里没有加工逻辑的边，用脚本里目标字段的表达式回填。过滤条件和关联条件按目标表保存，作为该表所有字段共用的口径证据。

**解析失败的降级。** 整个文件解析失败时（例如存储过程包装），按分号切开逐条解析。单条仍失败的，用正则找 `INSERT INTO 表名` 确定归属，只保存原文并在报告里标注。原文仍会作为证据交给模型阅读。

已用一次性探针验证：sqlglot 能从 `INSERT ... SELECT` 中提取目标表、关联条件、过滤条件、各字段的来源字段和表达式。

### 4.4 关联关系推导

关联关系有四种来源，按下面的优先级合并，并记录来源，输出时会说明依据。同一对表按「表对 + 字段映射」去重，同一种映射保留优先级最高的来源；一对表最多保留 3 种映射，最优的排第一（第二份计划实施时修订：原文是每对表只留一条，但同一对表确实可能有几种都对的关联方式，例如机构维表与机构信息表之间按上级机构号和按机构号两种）。

| 优先级 | 来源 | 说明 |
|--------|------|------|
| 1 | 手工 | 关联关系清单里填写的 |
| 2 | 脚本 | 加工脚本里实际出现过的等值关联 |
| 3 | 血缘传递 | 见下 |
| 4 | 同名粒度键 | 表 S 含有与表 T 的全部粒度字段同名的字段，则 S 可按这些字段关联 T |

**血缘传递**是「用血缘推断关联路径」的落地方式。如果一条血缘边的加工表达式只是单个字段的直接引用，称为直取。被直取边连在一起的字段取值范围相同，构成一个**键域**。只要脚本里出现过键域 X 的某个字段与键域 Y 的某个字段的关联，那么 X 里的任一字段都可以和 Y 里的任一字段关联。

举例：加工脚本里出现过「整合层存款快照.客户号 = 客户维表.客户号」。专题层汇总表的客户号是从整合层快照直取的，所以专题层汇总表也可以按客户号关联客户维表，尽管没有任何脚本直接这样写过。

没有表达式可用时（脚本未能解析），目标字段与源字段同名且只有一个来源的，也按直取处理。

**对应关系的判定。** 关联键覆盖了某一侧表的全部粒度字段，则该侧唯一。右侧唯一为 `N:1`，两侧都唯一为 `1:1`，左侧唯一为 `1:N`，都不唯一为 `N:N`。某一侧的表没有粒度字段时判断不了，记为「未知」。推导结果统一写成 `N:1` 方向。

**规模控制。** 不加限制时，同名粒度键会在真实库上推出上万对关联，所以实施时加了几道闸：粒度字段全是 `id`、`record_id` 这类行编号常用名的表不参与同名粒度键；同名粒度键只允许同层或下游表关联上游表；一张表被超过 150 张表关联时跳过；键域超过 50 个字段、单次传递超过 400 对时不传递；传递出的 `N:N` 丢掉。被挡掉的数量都写进导入报告。

### 4.6 向量索引

沿用现有的本地 BGE 模型。向量不放 Chroma，而是作为一张表写进元数据库，查询时整体载入内存，用 numpy 算全量相似度（第二份计划实施时修订）：真实库约 2.3 万个字段，一次全量计算只要几毫秒；向量和元数据在同一个临时文件里写好再替换，导入失败不会留下半截索引；读取时不占文件，重新导入不会被正在运行的界面挡住。两类文档：

| 集合 | 每条文档的文本 | 用途 |
|------|----------------|------|
| 字段 | 表中文名 + 字段中文名 | 召回候选字段，再按表归组得到候选表 |
| 样例 | 需求 + 口径 | 召回相似样例 |

字段文档的文本里已经带了表中文名，所以不再单独为表建一类。口径说明不放进字段文本（实施时修订）：真实库的口径说明多是加工过程的描述，混进去会稀释相似度，实测去掉后排第一的命中得分普遍高 0.07 到 0.10。口径说明仍留在元数据库里，由证据环节交给模型读。查询时会比对向量器名称，与建库时不一致就只走关键字路。

向量化通过一个可替换的接口提供。单元测试使用假的向量器，不加载 BGE 模型。

### 4.7 真实资料转换器

真实资料不是按标准模板整理的，而且本身不规范。设计上的取舍是：**标准模板和导入校验保持严格，另写一个宽容的转换器负责清洗**，而不是把导入校验放松。脏数据在入口处拦住并留痕，下游才能放心使用。

转换器是针对某一套来源资料专门写的，放在 `data/real_mart/`，和转换结果一样不入库。它以只读方式打开来源资料，输出一套标准格式的清单、加工脚本的副本，以及一份转换报告。

来源资料有三样：

- 记录专题层表、字段、以及字段到标准层血缘的元数据库。设计文档的 Excel 是由它生成的，所以直接读它，不读 Excel
- 记录标准层与贴源层的表、字段、两层之间映射的索引库
- 当前版本的加工脚本

清洗规则都来自对真实取值的统计：

| 真实情况 | 处理 |
|----------|------|
| 表名有的带模式名、有的不带 | 以加工脚本里实际写的模式为准，脚本里没出现过的用配置里的默认模式 |
| 一个单元格里并列写多张表、多个字段，分隔符不止一种 | 拆开后配对：个数相同按位置对应；只有一张表则全算它的；配不上的到列出的每张表里去找；仍找不到而恰好只有一张结构未知的外部表，就算它的。结构已知的表，字段必须真的存在才算数 |
| 来源栏写的是「待确认」「系统生成」之类的说明，或者表名带通配符 | 不生成血缘，记入报告 |
| 专题层字段只记录了业务库来源 | 业务库表能唯一对应到一张贴源层表时，生成直达贴源层的血缘并注明；否则留给加工脚本解析来补 |
| 重复字段、空表名、不是合法写法的字段名、没有字段的表 | 去重或跳过，逐条记入报告 |
| 没有中文名 | 用英文名代替，记入报告 |
| 没有主键、没有类型 | 留空，由导入校验给警告 |

转换报告列出跳过了什么、哪些血缘对不上、哪些是推断出来的。它同时是来源元数据的一份质量检核结果。

这次不纳入的内容会在血缘里表现为外部来源：手工录入的表、设计文档里没有的维表、尚未启用的汇总层、码值表。

## 5. 血缘图

`lineage/graph.py` 在内存里维护两张图，启动时从元数据库加载：

- **字段血缘图**：节点是 `表.字段`，边从源字段指向目标字段，边上带加工表达式、是否直取、脚本名。
- **表关联图**：节点是表，边是关联键和对应关系。

对外只提供确定性查询，不调用模型：

| 查询 | 返回 | 服务于 |
|------|------|--------|
| 字段上游链路 | 逐跳的源字段、加工表达式、该跳目标表的过滤条件与关联条件，深度可限 | 搞清口径 |
| 同源差异 | 两个字段是否有共同上游，以及各自路径上加工与过滤的差别 | 搞清口径 |
| 表的上游表、下游表 | 表清单，带层级、粒度 | 选对表、向上溯源 |
| 关联路径 | 两张表之间的最短关联路径，最多经过一张中间表，带键和对应关系 | 找关联路径 |
| 是否唯一 | 给定一组字段，判断是否覆盖某表的粒度 | 判断是否发散 |

**向上溯源时还原加工条件。** 上溯到整合层查数时，必须把专题层加工时用过的过滤条件一并带上，否则查出来的数和专题层对不上。所以上游链路里每一跳都带着该跳的过滤条件和关联条件，由第 ④ 步写进查询方案。

## 6. 查询流水线

### 6.1 状态

流水线本身无状态，会话上下文由调用方显式传入。

| 字段 | 方向 | 含义 |
|------|------|------|
| `question` | 输入 | 本轮用户输入 |
| `prev_requirement` | 输入，可空 | 上一轮的完整需求 |
| `prev_clarify` | 输入，可空 | 上一轮提出的反问 |
| `today` | 输入，可空 | 换算相对日期用的「今天」，默认系统日期。评估时固定，保证可复现 |
| `use_lineage`、`use_examples` | 输入 | 对照实验开关，默认都开 |
| `requirement`、`intent` | ① 产出 | 完整需求复述、结构化要素 |
| `scope_level` | 中间 | 当前上溯层数，0、1、2 |
| `candidates` | ② 产出 | 候选表、命中字段、相似样例 |
| `evidence` | ③ 产出 | 证据包 |
| `plan` | ④ 产出 | 查询方案 |
| `sql`、`retry_count` | ⑤ 产出 | SQL、已修正次数 |
| `validation` | ⑥ 产出 | 校验报告 |
| `status` | 输出 | `ok`、`need_clarify`、`unvalidated`、`failed` |
| `result`、`clarify`、`exec_result`、`error` | 输出 | 最终结果、反问内容、执行结果、错误说明 |
| `trace` | 输出 | 每一步的耗时和摘要 |

### 6.2 各步骤

**① 需求解析（模型）。** 输入本轮内容、上一轮完整需求、上一轮反问、今天的日期。输出固定结构：

- 是否查数需求。不是则以 `failed` 结束并说明工具能做什么
- 完整需求复述，一句自包含的话
- 指标、维度、过滤条件、排序与条数
- 时间：时点、区间或日均；具体日期；对比方式（较年初、较上月）及对比日期
- 需求里明确提到的口径线索，例如「不含保证金」

**② 候选召回（代码）。** 对每个指标、维度、过滤要素，在当前范围内的表里用向量相似度和中文名关键字两路找字段，合并后按表归组，保留最多 8 张候选表。同时按完整需求找最相似的 3 条样例，样例用到的表直接加入候选，不占这 8 张的名额。

候选范围由上溯层数决定。这里的事实表指候选表中表类型不是维表的表。

| 层数 | 范围 |
|------|------|
| 0 | 专题层全部表 + 整合层的维表 |
| 1 | 再加入候选事实表的全部上游表中属于整合层的 |
| 2 | 再加入属于贴源层的 |

上溯时加入的上游表无条件成为候选，同样不占 8 张的名额，再在这些表里找命中的字段。

**③ 血缘展开（代码）。** 为候选组装证据包：

- 每张候选表的层级、类型、粒度、数据日期字段、字段清单
- 命中的指标字段的上游链路，深度不超过 3 跳
- 对应同一个指标的多个候选字段之间的同源差异。同源但口径不同的字段会被标成一组，提示第 ④ 步注意
- 候选表之间的上下游关系，例如「机构汇总表由客户汇总表汇总而来」
- 候选表之间的关联路径及对应关系
- 还可以继续上溯到哪些表
- 相似样例

**④ 选表定口径（模型）。** 依据证据输出查询方案，包含一个结论：

| 结论 | 含义 | 去向 |
|------|------|------|
| `ok` | 给出表、字段、关联、过滤条件，每项带理由；写明口径说明、假设、溯源说明、参考了哪些样例 | ⑤ |
| `need_clarify` | 候选字段口径不同而需求没有说明。给出一个问题和各选项的含义 | 结束本轮 |
| `need_upstream` | 当前范围缺维度、缺字段或粒度不够。说明缺什么 | 回到 ② |
| `cannot_answer` | 元数据范围内无法满足。说明原因 | 结束 |

代码会核对方案里的每张表、每个字段都在候选之内，不在则视为输出不合格，带着错误重试一次。

**⑤ 生成 SQL（模型）。** 输入完整需求、查询方案、选定表的结构、方言规则、相似样例的 SQL，修正时还有上一次的校验错误。只输出 SQL。

方言规则写在提示词里：只用 PostgreSQL 与 GaussDB 共有的标准语法；表名带模式名；日期字面量写 `DATE 'YYYY-MM-DD'`；不用 `SELECT *`；快照表必须带数据日期条件。

**⑥ 静态校验（代码）。** 见第 7 节。

**⑦ 输出组装（代码）。** 把 SQL 排版，连同各项说明和校验报告组装成结果。配置了执行层且校验通过时调用执行层。

### 6.3 回路与终止

| 回路 | 触发 | 上限 | 到上限后 |
|------|------|------|----------|
| 上溯 | ④ 结论为 `need_upstream` | 上溯 2 层 | 以 `failed` 结束，如实说明元数据范围内找不到什么 |
| 修正 | ⑥ 有错误 | 修正 2 次 | 照常输出，状态为 `unvalidated`，列出未通过的原因 |
| 格式重试 | ①④ 的输出结构不合格 | 各 1 次 | 以 `failed` 结束，指出停在哪一步 |

### 6.4 追问与反问

追问和对反问的回答走同一套机制：调用方把上一轮的完整需求（以及上一轮的反问，如果有）连同本轮输入一起传入，由 ① 合并成新的完整需求。之后各步不知道这是追问。

```
上一轮完整需求：查 2026-09-30 各一级分行对公存款余额（不含保证金）及较年初增量
本轮输入：      再按行业拆一下
本轮完整需求：  查 2026-09-30 各一级分行、各行业对公存款余额（不含保证金）及较年初增量
```

完整需求复述会展示给用户，模型把「再按行业拆」理解成追加维度还是替换维度一眼可见。本轮输入本身就是完整需求时，① 忽略上一轮。

反问只在口径确实有分岔时发生，一次只问一个问题。其它不确定之处按默认处理并写进假设。「最新」按上一自然日处理并写进假设。

### 6.5 模型调用约定

- 统一经 `config.get_llm_kwargs()` 取配置，三次调用都用温度 0。现有函数把温度固定为 0.7，需要增加一个可选的温度参数。
- ①④ 用 JSON 模式输出，用 Pydantic 校验，不合格时带着校验错误重试一次。
- 模型调用封装成一个接口，测试时替换为按脚本返回的假模型。

### 6.6 输出示例

需求：查 9 月末各一级分行对公存款余额（不含保证金）及较年初增量

```sql
SELECT o.lvl1_org_no,
       o.lvl1_org_nm,
       SUM(CASE WHEN b.data_dt = DATE '2026-09-30' THEN b.dep_bal_rmb ELSE 0 END) AS cur_bal,
       SUM(CASE WHEN b.data_dt = DATE '2026-09-30' THEN b.dep_bal_rmb ELSE 0 END)
     - SUM(CASE WHEN b.data_dt = DATE '2025-12-31' THEN b.dep_bal_rmb ELSE 0 END) AS inc_vs_year_begin
FROM ads.org_corp_dep_bal_d AS b
JOIN dim.org AS o ON b.org_no = o.org_no
WHERE b.data_dt IN (DATE '2026-09-30', DATE '2025-12-31')
GROUP BY o.lvl1_org_no, o.lvl1_org_nm
ORDER BY cur_bal DESC;
```

- **口径说明**：存款余额取机构汇总表的 `dep_bal_rmb`。依据血缘，它由客户汇总表的同名字段按机构汇总而来，后者的加工表达式是 `SUM(CASE WHEN is_margin = '0' THEN bal_rmb ELSE 0 END)`，即不含保证金、已折人民币；再上游的整合层已限定对公客户和正常账户。
- **用表依据**：需求只到机构粒度，机构汇总表已满足，不必用客户级汇总表。
- **关联说明**：机构汇总表的机构号关联机构维表的机构号，多对一，不发散。依据：同名粒度键。
- **假设**：「较年初」按对比上年末余额计算。
- **校验结果**：通过。

## 7. 静态校验

不执行 SQL，用 sqlglot 解析后对照元数据检查。错误必须修正，警告展示给人判断。

| 编号 | 规则 | 级别 | 防什么 |
|------|------|------|--------|
| R1 | 按目标方言能解析，且只有一条语句 | 错误 | 语法写错 |
| R2 | 只能是查询语句，语法树里不得出现增删改、建表、`SELECT ... INTO` | 错误 | 写操作 |
| R3 | 每张表都存在于元数据 | 错误 | 编造的表 |
| R4 | 每个字段都存在于它所属的表 | 错误 | 编造的字段 |
| R5 | 每张快照表在所在查询层的 `WHERE` 或关联条件里有数据日期字段的条件 | 错误 | 余额跨日累加 |
| R6 | 表之间的等值关联属于已知关联关系 | 警告 | 乱关联 |
| R7 | 查询含汇总时，除了被汇总字段所在的表，其余被关联的表的粒度字段应全部被等值条件约束 | 警告 | 发散、金额翻倍 |
| R8 | 实际使用的表和指标字段与查询方案一致 | 警告 | 写 SQL 时跑偏 |

R5 只针对快照表。全量表只有当前状态，不要求日期条件。R7 需要粒度字段，没有填粒度字段的表无法判断，这条规则对它不生效。

R3 不通过时跳过 R4。错误信息里附上可用的表名或字段名，方便模型修正。

实施时补充的判定：R5 把「日期字段 = 日期字段」归成一组，组里至少要有一个具体的日期条件，两张快照表只互相对齐日期仍算缺；快照表在一层里只取日期的最大值、最小值或去重值（「取最新日期」）时豁免。R4 也检查在 SELECT 列表、窗口、表达式里引用同一层输出别名的写法：PostgreSQL 会报错，DuckDB 却能执行，评估时发现不了。已知局限（函数副作用、NATURAL JOIN、少见伪列等）见静态校验的笔记。

校验报告同时给出 SQL 实际使用的表和字段，评估时用来计算选表准确率和字段准确率。

R2 取代现有的关键词黑名单。现有做法按空格分词找 `DELETE` 之类的词，换行或注释就能绕过；按语法树判断语句类型既绕不过，也不会误伤含关键词的字段名。

探针验证的结论：sqlglot 的字段限定功能能查出不存在的字段，但查不出不存在的表，所以 R3 需要自己遍历语法树里的表节点来实现。

## 8. 执行层

统一接口，输入 SQL，返回是否执行、列名、限行后的数据、行数、耗时或错误。

| 实现 | 行为 | 何时使用 |
|------|------|----------|
| 不执行 | 返回「仅生成模式，未执行」 | 默认，真实场景 |
| DuckDB | 把 PostgreSQL 方言用 sqlglot 转成 DuckDB 方言，以只读方式在模拟库上执行，最多返回 200 行 | 模拟专题库的演示和评估 |

以后接真实库时再加一个实现（只读账号、超时、限行），流水线不用改。

评估固定使用 DuckDB 实现来比对结果，不受 `EXECUTOR` 配置影响。

探针验证的结论：按 PostgreSQL 写的较年初增量、`to_char`、窗口函数都能转换后在 DuckDB 上得到正确结果。

### 9.1 界面（Streamlit，两页）

**查数页。** 输入需求后实时展示七步进度，沿用现在的 `wf.stream()` + `st.status()` 做法。完成后展示完整需求复述、SQL、口径说明、用表依据、关联说明、溯源说明、假设、参考样例、校验结果。需要反问时展示问题和选项，点选即作为回答发送。配置了执行层时展示结果表格。会话里保存上一轮的完整需求用于追问。

## 10. 异常处理

原则：宁可说不知道，不编。

| 情况 | 处理 |
|------|------|
| 不是查数需求 | 说明工具能做什么，不进入后续步骤 |
| 召回不到候选 | 告知元数据里没有找到，列出最接近的几个字段 |
| 模型调用失败或超时 | 明确报错并指出停在哪一步，不输出半成品 SQL |
| 模型输出结构不合格 | 重试一次，仍不合格则报错 |
| 上溯 2 层仍无法满足 | 说明缺什么 |
| 修正 2 次仍未通过校验 | 输出 SQL，但标注未通过及原因 |
| 元数据库不存在 | 提示先运行导入命令 |

每一步的输入摘要、输出摘要和耗时写入日志，出问题能定位到是哪一步。日志只含元数据，不记录执行结果里的数据。

## 11. 数据安全

- 发给模型的只有元数据：表名、字段名、中文名、口径说明、加工脚本片段、样例。不含业务数据行。
- 真实样例 SQL 里的字面值（客户号、客户名称、账号）属于业务数据，整理时需要脱敏替换。
- 模型地址通过 `.env` 配置，换成内网可用的模型不需要改代码。
- 真实资料的转换器、转换结果及其生成的元数据库、向量索引都放在 `data/real_mart/`，已被 `.gitignore` 排除。来源资料只读，不复制到这个目录以外的地方。
- 真实的表名、模式名、路径、单位名称不出现在任何入库的文件里，包括代码、测试、笔记、文档和提交说明。转换器的测试用结构相同的虚构资料。
- 接入真实资料前，需要先确认表结构、血缘、脚本能否发给外部模型。不能的话换内网模型。

### 12.2 埋点

模拟库刻意构造了五类容易出错的情况，让题库能测出血缘的作用。

| 类别 | 构造方式 |
|------|----------|
| 口径 | 「存款余额」不含保证金，「全口径存款余额」含保证金。字段清单的口径说明只写「折人民币」，区别只存在于加工脚本的表达式里 |
| 选表 | 机构汇总表和客户汇总表都能回答各分行余额，但按行业只有客户级的表加客户维表能回答 |

### 12.3 造数

`data/mock_mart/build_mock.py` 生成 `build/mock.duckdb`：

1. 按字段清单建表。物理表结构直接来自元数据，保证字典与库一致。
2. 用固定随机种子生成贴源层数据：1 个总行、3 个一级分行、6 个二级分行、12 个支行；约 120 个对公客户和少量个人客户；约 250 个存款账户，含保证金账户、外币账户、销户账户，以及少量客户号在客户信息表里不存在的账户（让加工脚本里「关联客户维表剔除无效记录」这一步真正起作用，上溯查数时不还原这个条件就对不平）；约 150 笔贷款借据；数据日期从 2025-12-31 到 2026-09-30 每日一份。
3. 按依赖顺序、逐日执行 `scripts/` 里的加工脚本，生成整合层和专题层。脚本既是口径证据，也是实际的加工程序。
4. 对平检核：专题层余额合计等于整合层对应口径的合计；机构汇总表等于客户汇总表按机构的合计。

模拟数据从 2025-12-31 开始，这一天的日均字段没有完整的年度数据，题库不考 2025 年的日均。

造数完成后记录一份输入指纹（四张清单、加工脚本、造数程序、日期范围、随机种子）。指纹没变时直接复用已生成的库，测试和评估不必每次重新造数。

## 13. 评估

### 13.1 题库

`eval/nl2sql_questions.yaml`，共 40 题。评估时固定「今天」为 2026-10-13。用 YAML 而不是 JSON，是因为标准 SQL 可以按多行原样书写，便于审核。

| 类别 | 题数 | 例子 |
|------|------|------|
| 基础时点余额 | 8 | 查 2026 年 9 月末全行对公贷款余额 |
| 口径区分 | 6 | 查 9 月末各支行含保证金的对公存款余额 |
| 维度关联 | 6 | 查 9 月末各行业不含保证金的对公存款余额 |
| 时间口径 | 5 | 查 9 月末各一级分行对公贷款余额较上月末的增量 |
| 向上溯源 | 5 | 查 9 月末各币种不含保证金的对公存款原币余额 |
| 反问 | 5 | 查 9 月末各分行对公存款余额（没有说明是否含保证金） |
| 追问 | 5 | 第一轮查余额，第二轮「再按行业拆一下」 |

每题包含：编号、类别、一轮或两轮输入、期望结果是 SQL 还是反问、标准 SQL、标准用表、关键字段、是否要求顺序。标准 SQL 必须能在模拟库上执行，由单元测试保证。

### 13.2 指标

| 指标 | 定义 |
|------|------|
| 执行准确率（主指标） | 生成的 SQL 与标准 SQL 在模拟库上的结果集一致的题目占比 |
| 候选召回率 | 标准用表全部出现在候选表中的题目占比 |
| 选表准确率 | SQL 实际使用的表与标准用表完全一致的占比 |
| 字段准确率 | 关键字段全部被使用的占比 |
| 校验通过率 | 一次通过的占比，以及修正后通过的占比 |
| 反问准确率 | 该反问的题反问了、不该反问的题没反问的占比，在全部 40 题上统计 |
| 追问准确率 | 追问题第二轮的执行准确率 |
| 平均耗时、平均模型调用次数 | |

### 13.3 对照实验

同一套题跑三组配置，得出血缘和样例各自的贡献。

| 配置 | 提供给模型的信息 | 候选范围 |
|------|------------------|----------|
| A 仅模型结构 | 表清单、字段清单；手工和同名粒度键两种关联关系 | 所有层级的表一次给全，没有上溯机制 |
| B 加血缘 | A 的全部，加上游链路、加工表达式、过滤条件、同源差异、表的上下游、脚本和血缘传递两种关联关系 | 从专题层起，按需上溯 |
| C 加血缘和样例 | B 的全部，加相似样例 | 同 B |

血缘贡献 = B 减 A，样例贡献 = C 减 B。

### 13.4 结果比对规则

- 数值四舍五入到 2 位小数后比较
- 不要求列名和列顺序一致，允许生成结果多出列
- 标准结果的每一列都必须能在生成结果里找到对应列，并且按行对应
- 标准 SQL 要求顺序时按顺序比较，否则不计行顺序
- 方言转换失败或执行报错的题记为不正确，并在报告里单列，和逻辑错误区分开

### 13.5 报告

`eval/reports/` 下生成 Markdown 报告：三组配置的指标对比表、分类别的执行准确率、每道错题的生成 SQL 和标准 SQL 以及归因到哪一步。评估可以按配置单独运行，也可以限制题数。

### 13.6 局限

模拟专题库和题库是为这个项目专门构造的，口径信息被刻意放在加工脚本里而不是字段说明里，以模拟真实字典说明不全的情况。因此血缘贡献的数值反映的是这种情况下的增益，不代表真实环境里的绝对水平。

真实专题库是主要的使用目标，但本机没有它的数据，生成的 SQL 无法执行。所以在真实库上只能做静态评估：选表是否正确、关键字段是否用对、静态校验是否通过，再加上使用者的人工判断。真实库的题目和标准答案需要使用者提供，放在不入库的目录里。模拟库和真实库的业务领域不同，模拟库上的执行准确率说明的是流水线本身的能力，不能直接当成真实库上的准确率。

## 17. 风险与应对

| 风险 | 应对 |
|------|------|
| DeepSeek 的结构化输出不稳定 | JSON 模式加 Pydantic 校验加一次重试；查询方案里的表和字段再由代码核对是否在候选之内 |
| 向量召回漏掉关键字段 | 向量与关键字两路召回；样例把用过的表带入候选；候选召回率单独成为指标 |
| sqlglot 不支持 GaussDB 的特有语法 | 脚本解析失败时降级为只保存原文；生成侧限定使用两者共有的标准语法 |
| DuckDB 与 PostgreSQL 语义有差异 | 经 sqlglot 转换；转换或执行失败在评估报告里单列，不与逻辑错误混在一起 |
| BGE 模型加载慢 | 进程内只加载一次；单元测试使用假向量器 |
| 自己出题自己考 | 样例与题目不重叠；报告写明局限；真实环境另行评估 |
| 真实数据字典比模拟的更乱 | 导入报告暴露缺失项；口径判断依赖脚本证据而不是字段说明 |
| 单次查询耗时偏长 | 基线是 3 次模型调用；界面实时展示每一步进度 |

## 18. 概念与 ETL 类比

| 概念 | 类比 |
|------|------|
| 元数据标准格式 | 接口表：上游不管是什么系统，都按约定的格式供数 |
| 导入器 | 带数据质量检核的 ETL 作业，检核不过不入库 |
| 元数据库 | 把数据字典和血缘落成关系表，随时可以用 SQL 查 |
| 血缘图 | 把 mapping 文档连成一张网，可以顺着查上游、逆着查下游 |
| 键域 | 同一个客户号从贴源层一路直取到专题层，这些字段说的是同一批值 |
| 查询流水线 | 有上下游依赖、每步有检核点的调度作业流 |
| 候选召回 | 接到需求先翻数据字典，圈出可能用到的表和字段 |
| 血缘展开 | 对圈出来的字段翻 mapping 和脚本，看它到底怎么算的 |
| 静态校验 | 上线前的脚本评审：不跑数，只看表名字段名对不对、有没有漏日期条件 |
| 修正回路 | 作业失败后带着报错信息重跑，有重跑次数上限 |
| 对照实验 | 新旧口径并行跑数做比对，用差异说明改动的效果 |
| 样例库 | 团队里积累的常用查数脚本 |
