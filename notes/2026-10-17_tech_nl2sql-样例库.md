# NL2SQL 样例库：需求加 SQL 的文本格式、入库前过静态校验、拒收只影响单条、防止与题库撞车

> 日期: 2026-10-17 | 类别: tech | 关联: [[2026-10-13_design_nl2sql专题库改造]]、[[2026-10-16_tech_nl2sql-静态校验]]

---

## 📦 目标

团队里老手写过的查数脚本，是新人最好的参考：同样的需求，上次是怎么选表、怎么取口径、怎么关联维表。样例库就是把这些脚本收进系统，生成 SQL 时挑几条最像的放进提示词，让模型照着写。收进来的每一条都必须是对的，所以入库前要过一遍静态校验。

| 交付物 | 文件 | 作用 |
|--------|------|------|
| 解析与入库 | `metadata/examples.py` | 把 `.sql` 文件切成多条样例，逐条校验，收下或拒收 |
| 模拟样例 | `data/mock_mart/examples/` | 3 个文件、12 条样例，覆盖常见写法 |
| 测试 | `tests/test_examples.py` | 32 项：切分、拒收、编号、模拟样例能校验能执行、不与题库撞车 |

数字指标：12 条样例全部收下，W08 为 0，全部在模拟库上执行成功；与题目的文本相似度最高 0.36（门槛 0.5）；没有一条与题目的「用表加字段」签名相同。

## 📖 讲透

### 1. 一个文件放多条，格式只有两个标记

```sql
-- 需求: 2026 年 6 月末各二级分行含保证金存款比年初多了多少
-- 口径: 含保证金用 dep_bal_tot_rmb；年初指上年末
SELECT ...;
```

`-- 需求:` 开头一条，`-- 口径:` 可有可无，之后全是 SQL，到下一个 `-- 需求:` 或文件末尾为止。全角冒号也认，因为中文输入法下常常打成全角。第一条需求之前的纯注释当作文件说明，但如果有 SQL 就报警告并忽略，因为它不属于任何一条样例。

### 2. 入库就是一道接口表检核

每条样例交给校验函数，**有错误就拒收这一条，报 W08，其余照常收下，导入不中断**。只有警告（比如关联不在已知关系里）的照样收下，让人去判断。相当于数据装载时，不合格的记录进错误表，合格的照常入库，不会因为一条脏数据让整个批次失败。拒收说明的格式和脚本解析的 W06、W07 一致：`文件名 第 N 条样例：` 开头，后面是前三个校验错误。收下的样例，`tables` 直接取校验报告里「实际用到的表」（穿过 CTE 追到实体表），召回时用它把样例用到的表带进候选。

### 3. 编号是「文件名#序号」，序号就是它在文件里的位置

被拒收的那条也占着位置，所以拒收或修好某一条，其余样例的编号不变；报告里的「第 N 条」和编号对得上。代价是：在文件中间插一条会让后面的编号整体后移，新样例追加在文件末尾即可。

### 4. 样例不能和题库撞车

评估要比较「有样例」和「没样例」的差别。如果样例就是题目换个日期，模型是抄答案，样例的贡献会被虚高。所以设两道防线，都写成测试：

- **签名**：「用表集合 + 用到的非日期字段集合」不能等于任何一道题标准 SQL 的签名。日期字段按数据类型认，只换日期的样例签名必然相同，会被拦下。
- **文本**：需求去掉日期和数字后，和每道题首轮问题的汉字二元组 Jaccard 要小于 0.5。

两道防线自己也要有测试：拿 D05 换个日期，签名相同、文本相似度 1.0，证明防线能拦住「只换日期」。

## 🔧 选型

| 决策 | 选了什么 | 没选什么 | 原因 |
|------|----------|----------|------|
| 样例存什么 | 带注释标记的 `.sql` 文件 | Excel、YAML | 业务人员平时就在查询工具里写 SQL，复制进来就行；文件能直接拿去跑。类比：团队共享目录里的取数脚本，不必先录进台账 |
| 怎么校验 | 调用方传入校验函数 | 在 `metadata` 里直接 import 校验器 | `metadata` 是底层，`nl2sql` 在它上面，反过来依赖会成环。类比：公共函数库不能反过来调用业务作业 |
| 校验没过 | 拒收这一条加警告 | 整个导入报错 | 样例是辅助材料，一条写坏不该挡住元数据导入 |
| 编码 | 先 utf-8（带不带 BOM 都行），再 gb18030 | 只认 utf-8 | Windows 上另存的文件常是 GBK，和加工脚本的读取保持一致 |

## 💡 可迁移

**1. 来料先检核，坏的隔离，好的照收。** 历史脚本、别人给的字典、外部接口文件都可以这样处理，关键是错误能定位到「哪个文件第几条」。

**2. 评估用的标准答案不能混进被评估的东西里。** 和机器学习里训练集、测试集要隔离是一回事；ETL 里对账用的标准结果，也不能写进被测的加工逻辑。凡是「用历史数据提升效果，再用历史数据评估」的场景，都要先想防泄漏，并且把防线写成自动测试，不靠自觉。

## 👨‍💻 代码

切分只扫一遍：遇到 `-- 需求:` 开新的一条，其余行归当前这条；还没读到 SQL 的时候，`-- 口径:` 算口径，读到 SQL 之后就只是 SQL 里的注释。

```python
for line_no, line in enumerate(lines, start=1):
    marked = _REQUIREMENT_LINE.match(line)
    if marked:
        drafts.append(_Draft(marked.group(1), line_no))
        continue
    if not drafts:
        if not stray_line and _is_sql(line):
            stray_line = line_no          # 第一条需求之前的游离 SQL
        continue
    draft = drafts[-1]
    caliber = None if draft.in_sql else _CALIBER_LINE.match(line)
    ...
```

收样例时，缺需求、缺 SQL 的不送去校验，校验函数万一抛异常也只拒收这一条：

```python
report, reason = _defect(raw, validate)
if reason:
    issues.append(Issue(WARNING, "W08", "样例", raw.line_no, f"{path.name} 第 {index} 条样例：{reason}"))
    continue
accepted.append(Example(example_id=f"{path.name}#{index}", ..., tables=list(report.tables), ...))
```

## ⚠️ 常见坑

1. **只换日期的样例看起来不一样，其实是同一个需求。** 判重不能只看文本，要看用表和字段的签名；日期字段要先剔除。
2. **日均字段不能再按日期求平均。** `mtd_avg_bal_rmb` 已经是月初到当天的累计日均，只取目标那一天的值；机构之间、客户之间可以直接相加。样例的口径里写明了，模型才不会跨日期再平均。
3. **客户数不能直接相加。** 同一客户可能在多个机构开户，要对客户号去重，不能把机构汇总表的 `dep_cust_cnt` 加起来。
4. **上溯到整合层要还原专题层的加工范围。** 专题层剔除了客户维表里不存在的客户，整合层的查询不关联 `dim.corp_cust`，数就对不上专题层。

## 面试话术

> 「做 NL2SQL 我建了一个样例库，把团队积累的查数脚本收进来当提示词里的参考。入库前每条都过静态校验，没过的只拒收这一条，导入不中断；编号用文件名加位置，拒收不影响别的编号。评估时我特别防样例和考题撞车：用『用表加字段』的签名加文本相似度两道防线，并且写成自动测试，证明只换日期的样例能被拦下。」

被追问时可以展开的两点：

- 为什么校验函数由外面传入：底层元数据包不能反过来依赖上层的校验器，传回调就解开了循环依赖，测试时还能用假的校验函数单独测切分和拒收逻辑。
- 为什么两道防线：文本相似度防「照抄题面」，签名防「换个说法的同一个查询」，单靠一道都能被绕过。
