# 用户问题到回答：当前 AgentFlow 的整体流程

> 日期：2026-10-21。依据当前工作区代码核对；示例均为虚构的银行查数需求。不调用外部模型，不查询真实业务库。

> 核对期间有其他工作区改动持续写入。最后一次核对时，“追问复用上一轮 SQL”和“按缺失要素横向补召回”已在入口、历史和流水线实现中接线；本文说明其代码逻辑，但本次尚未完成对这批改动的完整回归或模型验收，不能等同于已部署行为。

## 📦 目标：把业务提问变成可审核的查数方案和 SQL

输入是自然语言，输出可能是 SQL、一次反问，或者明确的失败原因。正常回答包含完整需求、SQL、口径说明、用表依据、关联说明、假设与校验结果；配置执行层且静态校验通过时，还可以包含查询结果。

可以把它理解成一条查数需求加工流水线：需求登记 → 数据源检索 → 血缘与口径调查 → 查询方案 → SQL 开发 → 质量检查 → 交付。

## 📖 讲透：先准备知识，再处理一轮问题

### 提问之前：准备元数据

表清单、字段清单、血缘清单、关联关系、加工 SQL 和历史样例先经过导入。程序校验资料、解析加工脚本、补字段血缘、推导关联、校验历史样例，并计算字段与样例的向量，存入 SQLite 元数据库。

服务启动时根据资料目录装配只读元数据入口、血缘图、检索器、校验器、模型客户端和执行层。这里相当于预先整理数据字典、加工映射和作业依赖，用户提问时再按需查阅。

### 一轮请求的入口与上下文

前端会话提问进入 `main.py` 的 `ask_in_conversation`。服务端从会话历史中取最近一个有完整需求的轮次，带上其完整需求；该轮停在反问上时，也带上未回答的反问。最后核对时的新增实现还会在上一轮 SQL 校验通过时，带上 SQL 和实际用表清单。不会把整段聊天、上轮完整候选集、证据和方案直接塞进新一轮。

① 模型判断本轮是补充需求、回答反问，还是一个新问题。补充需求时合并成自包含的完整需求；新问题按新需求解析。检索词仍从本轮解析结果生成。新增实现以 `follows_up` 表示追问；只有它为真、且请求中有上一轮通过校验的 SQL 时，才把上轮实际用表补进候选，并把上轮 SQL 作为④、⑤的修改底稿。新问题不启用这条底稿路径，新建会话没有上轮上下文。

### 七步主流程

| 步骤 | 输入与处理 | 输出 | 调用大模型 |
|---|---|---|---|
| ① parse 需求解析 | 本轮问题、上轮完整需求、待答反问、参考日期；拆指标、维度、过滤、排序、时间、口径限定 | `ParsedRequest` | 是 |
| ② recall 候选召回 | 按指标、维度、过滤字段，用中文关键字与向量两路检索，融合排名后按表归组；找相似样例 | `RecallResult` | 否；向量模型负责语义编码 |
| ③ evidence 证据组装 | 展开候选表结构、粒度、日期字段、加工表达式、过滤条件、血缘、同源口径差异、关联路径与样例 | `Evidence` | 否 |
| ④ plan 选表定口径 | 模型结合需求和证据，决定用表、字段、关联、过滤、统计口径，并给出理由 | `QueryPlan` | 是 |
| ⑤ generate 生成 SQL | 按已定方案、方案中表的结构和参考样例写 SQL；修正时加上旧 SQL 与校验错误 | SQL 文本 | 是 |
| ⑥ validate 静态校验 | 用 SQL 语法树、元数据和查询方案检查规则 R1–R9 | 错误、警告、实际用表用字段 | 否 |
| ⑦ output 输出 | SQL 排版、合并假设、组装结果；满足条件时交执行层查询 | `QueryResult` | 否 |

正常不重试、不上溯时调用大模型三次。①、④ 的结构化输出还要经过 JSON 解析、Pydantic 结构校验和业务检查，不合格最多尝试两次。真实调用次数会因重试、上溯、SQL 修正而增加；提前反问或失败时也可能少于三次。

例如用户问“查 9 月末各一级分行制造业客户不含保证金的对公存款余额，按余额降序”。以 2026-10-21 为参考日期，① 会把时点解析为 2026-09-30，指标为对公存款余额，维度为一级分行，过滤为制造业，口径限定为不含保证金。② 找候选字段与表；③ 查这些余额字段的加工表达式、是否已剔除保证金、行业名称字段和关联路径；④ 确定方案；⑤ 按方案写 SQL；⑥ 检查；⑦ 连同依据交付。具体选哪张表取决于导入的资料，此例不预设某张表一定存在。

### 三类分支

1. **需要反问**：① 缺少无法默认的对象或指标时可问；④ 看见证据后发现口径分岔时可问。流程在本轮结束，用户回答后发起新一轮。① 的 `answers_clarify` 判断本轮是否在回答上一轮反问：是回答时①、④不能再次反问；用户跳过反问问新问题时，新问题照常可以反问。只说“日均”没说统计区间还有代码兜底。
2. **需要上溯**：默认先找专题层和整合层维表；④ 判断缺所需信息时，回到②扩大范围到候选表的整合层上游，第二次再加入贴源层，最多上溯两层。缺失要素会变成检索词；最后核对时的新增实现还会把每个缺失要素单独在第 0 层排名补表，每项最多补 2 张、合计最多 6 张，寻找血缘路径之外的横向表。上溯找的是元数据与加工依据，不等于已查询上游业务数据。
3. **需要修 SQL**：⑥ 有错误时带原 SQL 与错误回⑤，最多修正两次，即初稿加两次修正；仍有错误则标记 `unvalidated`，返回供人工检查，不执行。警告本身不会触发修正。

④ 判定可以回答后，代码还会精简用不到的表，记住移除列表，防止⑤照样例把多余关联抄回来。没有候选表、证据不足且无法继续上溯、模型失败或程序异常，会返回明确失败状态。

### 校验与最终显示

R1 语法及单语句；R2 只允许查询；R3 表存在；R4 字段及作用域正确；R5 快照表有具体数据日期；R6 已知关联关系；R7 聚合关联的粒度约束；R8 SQL 与方案一致；R9 代码字段不能直接和纯中文名称比较。R6、R7 是警告，R8 通常是警告，但重新使用明确移除的表为错误。

输出有 `ok`、`need_clarify`、`unvalidated`、`failed` 四种状态。`ok` 表示通过静态校验，执行情况另看 `exec_result`；执行失败时 SQL 状态仍可为 `ok`。`EXECUTOR=none` 只生成，`duckdb` 执行模拟库，默认最多取回 200 行、超时 30 秒。真实库执行器未接入当前这一套执行实现。

界面每收到一步完成事件就更新进度，最后展示结构化回答。⑦ 不再调用模型撰写一篇额外的业务分析。SSE 是步骤事件流，SQL 不是按模型 token 逐字推送。完成后这一轮存入 SQLite 会话历史，供下一轮计算上下文。

## 🔧 选型：各工具对应什么工作

- LangGraph 相当于带条件分支的 ETL 调度 DAG，负责节点、共享状态和有限回路；当前没有配置检查点，会话由独立历史库保存。
- DeepSeek 处理语言理解、证据下的方案选择与 SQL 编写。
- BGE 将需求词与字段、样例转成可比较的向量，负责语义检索；没有可用的匹配向量器时降级为关键字检索并记录原因。
- SQLite 保存元数据与会话运行记录；血缘图负责确定性的链路遍历。
- sqlglot 解析 SQL 语法树，相当于编译检查和质量规则，不是执行数据库。
- FastAPI 与 SSE 把运行步骤和最终结果传给前端。

## 💡 可迁移：把模型放在需要判断的步骤

其他 AI 数据应用也可复用这套分工：把自然语言转成标准需求，以本地资料提供证据，先定方案再生成代码，再用确定性规则验证。业务判断不全压给提示词，输出也不直接信任；数据契约、错误分类、有限重试和评估同样重要。

## ⚠️ 常见坑

1. 静态通过不能保证口径正确；例如日期条件存在，不代表日期一定选对。关联发散规则也可能只产生警告。
2. “不含保证金”可能已在字段加工时处理，需要先看血缘，不能凭名字又减一次。
3. 快照表漏日期或维表关联粒度不完整，可能多天累加、重复汇总。
4. 代码值和中文名称不能直接比较，应看名称字段、枚举或码值表。
5. 历史样例只是参考，方案、当前字段与过滤条件仍要重新核对；样例不会因每次对话而自动变成训练数据。
6. 上下文是否延续、反问是否已回答依赖①模型判断，简短模糊输入仍可能误判。
7. 旧笔记是历史记录。2026-10-20 那篇换话题笔记所写“有待答反问就禁止新问题反问”的限制，当前已由 `answers_clarify` 修复。
8. 当前工作区存在其他会话进行中的代码改动，本文解释代码逻辑，不宣称这批新增追问逻辑已经完成模型评估或线上发布。
