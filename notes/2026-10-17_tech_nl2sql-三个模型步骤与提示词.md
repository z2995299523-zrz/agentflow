## 📦 目标

流水线里确定性的步骤（召回、校验、执行）已经就位，剩下三个必须靠「人脑」判断的工序：① 把一句话读成结构化需求，④ 在证据里选表定口径，⑤ 按方案写 SQL。就像 ETL 里的人工审核岗：模型负责判断，但每个岗位前后都有代码把关，输出不合格不往下流。

| 交付物 | 文件 | 作用 |
|--------|------|------|
| ① 需求解析 | `nl2sql/parser.py` | 解析、核对、转召回检索词 |
| ④ 选表定口径 | `nl2sql/planner.py` | 出方案、核对方案里的表字段关联都在证据里 |
| ⑤ 生成 SQL | `nl2sql/generator.py` | 出 SQL、从回复里取出 SQL |
| 提示词与证据文本 | `prompts/nl2sql.py` | 三组系统提示词、方言规则、消息拼装、证据渲染与收缩 |
| 测试 | `tests/test_parser.py` 等四个文件、`tests/step_fixtures.py` | 183 项，假模型驱动，不调模型 |

数字指标：全量 1046 项测试通过（新增 183 项）。手工冒烟用 DeepSeek 共 20 次调用：① 解析 14 种说法共 16 次，第一次就合格 16 次；④ 3 次、⑤ 1 次，方案一次合格，生成的 SQL 过静态校验器 0 个问题。这是冒烟，不是评估；正式数字等三组对照评估。

## 📖 讲透

### 1. 提示词分两层：固定规则 + 本次参数

系统提示词只放固定规则，用户消息放这次的内容（今天、上一轮需求、证据、方案）。DeepSeek 的前缀缓存按「消息开头的相同部分」命中，所以系统提示词里不能有今天的日期，修正轮追加的内容也放在用户消息末尾。类比 SQL 里的**绑定变量**：SQL 文本固定、参数另传，共享池才能复用；每次把日期拼进 SQL 文本就是硬解析。

### 2. 相对日期由代码先算好

「上月末」「年初」让模型心算，遇到闰年、跨年会错。做法是代码按今天算出一份参考日期（上一自然日、上月末、上季末、去年末、本月初、本年初）贴在用户消息里，模型只做选择。类比 ETL 里的日历维表：谁都不要心算，查表。

### 3. 模型的输出过三道关

1. JSON 模式，保证是 JSON；
2. Pydantic，保证结构和类型；
3. 代码核对业务规则（`check_parsed`、`check_plan`）。

每一条问题都写成「照着能改」的话，再带着它重试一次，不是只报「校验失败」。类比数据质量检核：好的检核报告写的是「第几行哪个字段应该是什么」。

### 4. 方案里的表字段必须在证据里

`check_plan` 逐条核对：表在候选里、字段在所属的表里、关联两侧的表和字段存在且个数相同、样例编号真实存在。写成大小写不对或漏了模式名的，直接告诉应写成什么。类比作业编译时的数据字典校验：引用了不存在的表字段，作业根本不让上线。

### 5. 反问只在口径分岔时发生

「同源不同口径」的字段而需求没说清，才反问；其它不确定一律按默认处理、写进假设。对反问的回答这一轮，`allow_clarify=False`，`check_plan` 直接拦住再次反问，免得用户被问两遍。

### 6. 证据文本分节，超长按价值逐级收缩

候选表、四节血缘（只有 B、C 组）、关联路径、样例（只有 C 组）、说明。超过 4 万字按「信息价值从低到高」砍：非命中字段的码值 → 第 9 张以后的表只留命中和粒度字段 → 每跳条件截到 120 字 → 样例 SQL 截到 1500 字。每砍一级在「说明」里记一句，模型和人都看得到哪些被省略。类比报表的明细降级为汇总：先丢最不重要的，并且留痕。

后来在真实库上实测：表动辄五六十个字段、加工脚本的表达式和条件很长，四级收完最长还有 9.4 万字。于是又往后加了五级：关键字段（命中、粒度、数据日期、主键）以外不写口径说明 → 表达式截到 200 字、条件截到 60 字 → 第 4 张以后的表只留关键字段 → 每个字段的加工链路最多 1500 字（至少留第一跳） → 关联路径只留直连。11 道真实题都压到 4 万字以内，最多用到第 8 级。

## 🔧 选型

| 决策 | 选了什么 | 没选什么 | 原因 |
|------|----------|----------|------|
| 日期换算 | 代码算好参考日期放进消息 | 全靠模型心算 | 月末天数、闰年、跨年容易错，代码算一次永远对 |
| 输出约束 | JSON 模式 + Pydantic + 业务核对，带问题重试一次 | 只靠提示词叮嘱 | 三道关各管一类错误，重试时模型知道改哪里 |
| 示例 | 虚构的 `demo_` 表，示例里的今天是 2026-05-20 且声明以用户消息为准 | 用模拟库的真表和评估用的今天 | 模型会照抄示例；示例讲规则，不能变成评估题的答案 |
| 修正轮的内容 | 追加在用户消息末尾 | 放在开头 | 前面的需求、方案、表结构不变，前缀缓存才命中 |
| 超长证据 | 九级收缩并记说明 | 直接截断 | 截断会悄悄丢掉关键信息，收缩是按价值有序降级 |
| 取 SQL | 优先 sql 块，其次无标记块，再取全文，容忍没有结束围栏 | 只认标准写法 | 模型输出被截断时仍能交给校验去报错 |

## 💡 可迁移

**1. 绑定变量的思想。** 固定文本 + 变化参数，凡是有缓存的地方（共享池、执行计划缓存、提示词前缀缓存）都适用。

**2. 校验返回「修复指引」，不返回「错误码」。** 数据质量检核、接口校验、配置检查，报告里写清「应该写成什么」，下游才能自动修。

**3. 降级链加留痕。** 资源超限时按价值从低到高逐级降级，每级记一笔。日志分级、报表钻取、监控采样都是这个模式。

## 👨‍💻 代码

三个步骤都是一行：消息 + 结构 + 核对函数。

```python
def parse_request(llm, request, today):
    return structured_call(llm, "parse", parser_messages(request, today), ParsedRequest, check_parsed)
```

核对要把「怎么改」写进去，表名写错时给出确切写法：

```python
if table.lower() in lowered:
    hint = f"（表名要和证据里完全一致，应写成 {available[lowered.index(table.lower())]}）"
return f"表 {table} 不在候选里{hint}，可用的表：{_join(available) or '（没有）'}"
```

证据收缩是一个循环，每一级都从头渲染，所以同样的输入必然同样的输出：

```python
text = _render(evidence, 0)
for level in range(1, len(SHRINK_ACTIONS) + 1):
    if len(text) <= EVIDENCE_CHAR_LIMIT:
        break
    text = _render(evidence, level)
```

## ⚠️ 常见坑

1. **说明里写着上限的数字。** 测试里逐级压低上限时，上限从五位变四位，说明文字短了一个字，刚好装下，少收缩了一级。测试补一段填充，让各级文本都是五位数。
2. **示例被照抄。** 示例里用真表名，模型会在别的需求里直接写出来；改成 `demo_` 虚构名，`check_plan` 也能拦住。
3. **冒烟里发现两处提示词缺陷。** ① 「10 个对公客户」被臆造成「客户类型 = 对公客户」的过滤条件，后面要去找专题层没有的字段；加了「范围词不是过滤条件」。② 模型照搬样例，把用不到的维表也关联上；加了「没用到维表字段就不要关联，也不要写进 tables」。复测后关联没了，维表仍列在 tables 里（调用预算用完，没再调），先靠 R8 警告兜着，留给评估看。
4. **JSON 模式对提示词有要求。** 提示词里必须出现 json 字样和格式示例，否则接口报错。
5. **日期校验别用 `fromisoformat`。** Python 3.11 起它认 `20260930` 这类写法，用「正则 + `date()`」才严格。
6. **一次性脚本改文件。** Windows 下 `Path.write_text` 会把 LF 写成 CRLF，整份文件的换行悄悄变了；写字节，或者用编辑工具。

## 面试话术

> 「NL2SQL 里三个模型步骤我都做成同一个模式：JSON 模式出结构，Pydantic 管类型，再用代码核对业务规则，核对出的每条问题都写成能照着改的话，带着问题重试一次。提示词把固定规则放在系统消息里，把今天、证据这类变量放在用户消息里，这样 DeepSeek 的前缀缓存能命中，道理和 SQL 的绑定变量一样。相对日期不让模型心算，代码先按今天算好参考日期。」

被追问时可以展开的两点：

- 证据太长怎么办：按信息价值从低到高分九级收缩，每级在说明里记一句。不是简单截断，因为截断会悄悄丢信息。
- 怎么防模型编表编字段：方案出来后逐个核对表、字段、关联键都在证据里，不在就带着正确写法让它重写，两次都不对就如实报失败，停在这一步。
