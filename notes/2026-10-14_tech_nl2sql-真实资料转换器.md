# NL2SQL 真实资料转换器：严格的接口表加宽容的转换器

> 日期: 2026-10-14 | 类别: tech | 关联: [[2026-10-14_tech_nl2sql-元数据层]]、[[2026-10-13_design_nl2sql专题库改造]]

---

## 📦 目标

元数据层的标准模板要求很规范：表名带模式名、一行一条血缘、取值在允许范围内。真实专题库的资料做不到这么规范：它是多年积累下来给人看的文档，一个单元格里会并列写几张表，来源栏里会写「待确认」，同一张表在不同地方的写法还不一样。

转换器负责把前者变成后者，并且把清洗过程中丢掉了什么、改了什么，一条一条说清楚。

交付物：

- 一个转换程序。读三样资料（生成模型设计文档的元数据库、标准层与贴源层的索引库、加工脚本目录），写出标准格式的表清单、字段清单、血缘清单，外加一份转换报告。
- 15 项测试。测试不碰真实资料，而是在临时目录里造一套结构相同的小型资料，把每一种不规范的情况都放进去。
- 验证结果：真实资料转换之后，按标准流程导入，没有任何错误。

转换器和转换结果都放在不入库的本地目录里，原因见选型一节。本文的例子全部用虚构的表名。

## 📖 讲透

### 1. 为什么不直接把导入校验放松

真实资料导不进来，有两条路：

| 做法 | 结果 |
|------|------|
| 放松校验，让不规范的资料也能直接导入 | 元数据库里混进各种写法，后面每一个步骤（召回、血缘展开、生成 SQL）都要自己再处理一遍脏数据 |
| 校验保持严格，另写一个转换器做清洗 | 脏数据只在一个地方处理，元数据库里的内容下游可以放心用 |

这里选的是第二条：**严格的接口表，加一个宽容的转换器**。

类比数仓分层：贴源层接什么是什么，源系统多乱它就多乱；到了整合层必须是干净、统一的模型。脏数据要在进入整合层之前清洗，并且清洗规则要留痕。如果把整合层的约束放松来迁就源系统，上面的专题层、应用层全都要跟着遭殃。标准模板就是这里的整合层模型，转换器就是清洗作业。

### 2. 十一条清洗规则

每一条都对应真实资料里实际存在的情况，不是凭想象加的。

| # | 资料里的情况 | 处理 |
|---|--------------|------|
| 1 | 三层的名字是 DM、DWD、ODS | 对应成专题层、整合层、贴源层。这套数仓的表都是清空后全量重装，表类型一律记成全量表 |
| 2 | 表名有的带模式名，有的不带 | 以加工脚本里写的模式为准；脚本里没出现过的表，用配置文件里的默认模式 |
| 3 | 一个单元格里并列写了多张表、多个字段，分隔符有斜杠、分号、逗号、顿号好几种 | 拆开之后按四条规则配对，见下一小节 |
| 4 | 来源栏里写的是「待确认」「系统生成」「None」这类说明 | 不生成血缘，在报告里按写法分组计数 |
| 5 | 表名里带通配符，例如 `dwd_demo_process_*` | 这一部分忽略，其余照常处理，记入报告 |
| 6 | 字段名后面带括号批注，例如 `dept_id（需转码）` | 去掉批注 |
| 7 | 专题层字段只记了业务库的来源，没记标准层的来源 | 业务库的表能唯一对应到一张贴源层表时，生成一条直达贴源层的血缘，并在加工逻辑里注明；对应不上的记入报告，留给后面的加工脚本解析来补 |
| 8 | 标准层字段的来源表写的是业务库的表名 | 能唯一对应到贴源层表的，换成贴源层表 |
| 9 | 重复登记的字段、空的表名、拿中文当字段名、没有任何字段的表 | 去重或跳过，逐条记入报告 |
| 10 | 字段没有中文名 | 用英文名代替，记入报告 |
| 11 | 表没有主键，字段没有类型 | 留空。标准模板允许这两项为空，导入校验会给警告 |

第 11 条值得多说一句：没有的信息就留空，不要编。转换器不去猜主键是什么，而是如实留空，让导入校验的警告把这个缺口暴露出来。

### 3. 源表和源字段怎么配对

资料里一个字段的来源经常写成这样：来源表一栏并列写几张表，来源字段一栏并列写几个字段。标准模板要求一行一条「目标字段 ← 源表.源字段」，所以要把它们配成对。`pair_sources` 按下面四条规则依次尝试。

**规则一：个数相同，按位置一一对应。**

| 来源表 | 来源字段 | 配对结果 |
|--------|----------|----------|
| `dwd_demo_project / dwd_demo_dept` | `project_name / dept_name` | `dwd_demo_project.project_name`、`dwd_demo_dept.dept_name` |

**规则二：只有一张源表，所有字段都算它的。**

| 来源表 | 来源字段 | 配对结果 |
|--------|----------|----------|
| `dwd_demo_project` | `budget_amt, paid_amt` | 两个字段都来自 `dwd_demo_project` |

**规则三：前两条配不上的字段，到列出的每一张结构已知的表里去找。**

| 来源表 | 来源字段 | 配对结果 |
|--------|----------|----------|
| `dwd_demo_project / dwd_demo_dept` | `project_id, dept_id, dept_name` | 两张表、三个字段，个数对不上。逐个字段去两张表的字段清单里找，在哪张表里就算哪张表的 |

这条规则还能纠正写反了的情况：按位置对应时，如果字段在对应的那张表里并不存在，就不认这个配对，改为到其它表里去找。**结构已知的表，字段必须真的存在才算数。**

**规则四：还是找不到，而列出的表里恰好只有一张结构未知的外部表，就算它的。**

| 来源表 | 来源字段 | 配对结果 |
|--------|----------|----------|
| `dwd_demo_project / ext_dim_region` | `project_id, region_name` | `ext_dim_region` 不在清单里，结构未知。`region_name` 在 `dwd_demo_project` 里找不到，而结构未知的表只有这一张，就算它的 |

四条都配不上的字段不会生成血缘，而是记进转换报告。宁可少一条血缘，也不生成一条错的。

### 4. 转换报告为什么重要

转换器每丢掉、每修改一处，都按类别记进 `转换报告.md`：哪些字段的来源表和来源字段对不上，哪些只对上了一部分，哪些来源字段在来源表里根本不存在，哪些表和字段被跳过、原因是什么。

这份报告相当于**给源系统的元数据做了一次数据质量检核**。它有两个用处：

- 对工具：清楚地知道元数据库里缺了什么。比如哪些专题层字段还没有血缘，后面就知道要靠解析加工脚本来补。
- 对维护资料的人：这是一份现成的问题清单，照着就能回去修设计文档。

类比数据质量检核的结果不只是给作业看的，更是要反馈给源系统去整改的。

## 🔧 选型

| 决策 | 选了什么 | 没选什么 | 原因 |
|------|----------|----------|------|
| 读哪份资料 | 生成设计文档的那个元数据库 | 设计文档的 Excel | Excel 是导出来给人看的，有合并单元格、有排版；元数据库是它的源头，结构化、没有格式噪声。类比取数要从源系统的表里取，而不是从导出的报表里抠 |
| 怎么打开来源库 | 一律只读 | 普通方式打开 | 转换器绝不能改动别人的资料。类比抽取作业对源系统只有只读权限 |
| 路径和模式名放哪 | 配置文件 | 写在代码里 | 资料在哪、模式叫什么属于环境信息，换一套环境只改配置不改代码。类比：作业的连接串和库名放在参数文件里，不写死在脚本里 |
| 转换器和转换结果放哪 | 不入库的本地目录 | 仓库里 | 真实的表结构是单位的资料，而仓库是公开的。入库的只有标准模板和通用的导入逻辑；转换器这一层专门隔离真实资料。类比：生产数据不出生产环境，开发库里只放模拟数据 |
| 怎么确定表的模式名 | 用 sqlglot 解析加工脚本 | 靠表名前缀猜 | 脚本是真正在库里执行的东西，里面写的模式名最可信。解析不了的脚本记入报告，不影响其它脚本。类比：核对口径时以实际跑批的脚本为准，而不是以设计文档为准 |

## 💡 可迁移

**1. 每个源系统各写各的转换器，下游的标准模型不变。** 这和数仓里的分工一样：各个源系统到贴源层的抽取作业各写各的，整合层的模型只有一套。以后要接另一套专题库的资料，再写一个转换器即可，元数据层和后面的全部流程都不用动。

**2. 清洗规则要来自对真实取值的统计。** 写转换器之前，先把来源栏的全部取值按写法分组计数，看看到底有哪些分隔符、哪些占位说明、哪些奇怪的写法，再按出现的情况定规则。凭想象写的清洗规则，要么漏掉真实存在的情况，要么处理一堆根本不存在的情况。类比开发接口之前先做数据探查。

**3. 清洗要留痕。** 丢掉的每一条数据都要有去处。清洗规则一旦写错，只有靠留痕才能发现。

## 👨‍💻 代码

转换分五步，顺序固定。转换器的代码不在仓库里，本节贴的是关键片段，做了删节，行尾的注释是为了讲解加的：

```python
converter = Converter(settings)
converter.scan_scripts()     # 1. 扫描加工脚本：每张表的模式名、每张专题层表对应哪个脚本
converter.load_model()       # 2. 读模型元数据库：专题层的表和字段
converter.load_index()       # 3. 读索引库：整合层和贴源层的表和字段，以及业务库表到贴源层表的对应
converter.build_lineage()    # 4. 生成血缘：专题层 ← 整合层，整合层 ← 贴源层
converter.write(output_dir)  # 5. 写出三张清单、复制加工脚本、写转换报告
```

顺序有讲究：先有全部的表和字段（第 2、3 步），才能在生成血缘时（第 4 步）判断一个来源字段到底存不存在。

**`pair_sources`：配对的核心。** `columns_of` 是一个查询函数，给它表标识，它返回这张表的字段名集合；表不在清单里（结构未知）就返回 `None`。

```python
def acceptable(table: str, column: str) -> bool:
    columns = columns_of(table)
    return columns is None or column in columns

unique_tables = list(dict.fromkeys(tables))
external_tables = [table for table in unique_tables if columns_of(table) is None]
pairs: list[tuple[str, str]] = []
for position, column in enumerate(fields):
    if len(tables) == len(fields):
        candidates = [tables[position]]          # 规则一：按位置
    elif len(unique_tables) == 1:
        candidates = unique_tables               # 规则二：只有一张表
    else:
        candidates = []
    found = [table for table in candidates if acceptable(table, column)]
    if not found:                                # 规则三：到结构已知的表里找
        found = [table for table in unique_tables
                 if columns_of(table) is not None and column in columns_of(table)]
    if not found and len(external_tables) == 1:  # 规则四：唯一的外部表
        found = external_tables
    pairs.extend((table, column) for table in found)
return list(dict.fromkeys(pairs))
```

`dict.fromkeys` 在这里用来去重并且保持原来的顺序，相当于保序的 `DISTINCT`。

**`_add_columns`：登记字段时的清洗。** 三个判断对应三类问题，每一类都往报告里记一笔：

```python
for raw_name, cn, data_type, description in items:
    name = raw_name.lower()
    if not is_identifier(name):
        self.report.note("跳过的字段", f"{table_id}「{raw_name}」：不是字段名写法")
        continue
    if name in names:
        self.report.note("去掉的重复字段", f"{table_id}.{name}")
        continue
    if not cn:
        self.report.note("中文名缺失、用英文名代替的字段", f"{table_id}.{name}")
    names.add(name)
    self.column_rows.append([table_id, name, cn or name, data_type, "", description, ""])
```

转换完成后，结果就是一套标准格式的资料，用和模拟库完全相同的命令导入：

```bash
python data/real_mart/convert.py            # 转换，同目录下生成三张清单和转换报告
python -m metadata.importer data/real_mart  # 按标准流程导入
```

## ⚠️ 常见坑

1. **空值可能是字符串 `None`。** 资料经过程序导出再导入，空值会变成四个字母的文本 `None`，不处理就会被当成一张名叫 none 的表。`null`、`nan` 同理。
2. **分隔符不止一种。** 斜杠、分号、逗号、顿号，中英文混用。只按一种拆，剩下的会被当成一个很长的表名。
3. **同一张表，有的地方带模式名，有的地方不带。** 要先统一成同一个标识再比较，否则同一张表会被当成两张。
4. **重复登记的字段很多。** 不去重的话，导入校验会报一大串「字段重复」的错误。
5. **警告太多要汇总。** 第一次转换真实资料时，光「表没有主键」就有几百条警告，报告根本没法看。后来改成按层级汇总成一条、只举几个例子，才看得出真正要关注的问题。

## 面试话术

> 「真实的专题库资料是给人看的文档，很不规范。我没有放松导入校验，而是另写一个转换器做清洗，思路和数仓分层一样：整合层要干净，脏数据在进来之前处理。清洗规则来自对真实取值的统计，共十一条；每一处丢弃和修改都写进转换报告，等于给源系统的元数据做了一次质量检核。转换结果导入零错误。」

被追问时可以展开的三点：

- 最复杂的一条规则：并列写在一个单元格里的源表和源字段怎么配对。用了四条规则，配不上的宁可不生成血缘，也不生成错的。
- 为什么读元数据库而不读 Excel：Excel 是导出来给人看的，有合并单元格和排版，元数据库才是源头。
- 转换报告的价值：它是一份现成的问题清单，维护资料的人照着就能回去修设计文档。
