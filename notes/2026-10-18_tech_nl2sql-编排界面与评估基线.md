## 📖 讲透

### 1. 编排就是一张调度作业流，加两个有次数上限的回环

拿调度系统打比方：七个节点是七个作业，状态是作业之间传递的参数表。正常情况下顺着往下跑：

```
parse → recall → evidence → plan → generate → validate → output
```

有三处会拐弯，像调度里的条件分支和重跑：

- **plan 之后**：缺字段就回到 recall 上溯一层，最多 2 层；要反问或者做不到，直接去 output
- **validate 之后**：校验有错误就带着错误回到 generate 重写，最多 2 次
- **任何节点之后**：状态是 failed 就直接去 output，后面的作业不再跑

关键是**每个回环都有上限，每条路都收口到 output**。这和调度里「检核不过最多重跑两次，再不过就告警」是一回事：没有上限的回环会把额度和时间都吃光。

### 2. 节点永远不往外抛异常

每个节点套同一个包装：

- 接住「这一步做不下去」（模型调用失败、输出两次都不合格），状态置为 failed，记下停在哪一步
- 也接住没料到的程序错误，记为停在 internal
- 已经走过的轨迹和模型调用记录都留着，评估统计 token 时用得上

类比调度平台：一个作业失败只标红这个作业，不会把整个调度服务拖垮。评估一次跑 120 道题，哪一道崩了都不能让整批停下来。

### 3. 流水线不记事，会话在调用方手里

追问和反问的上下文（上一轮的完整需求、上一轮的反问）由调用方放进请求里：界面存在会话状态里，接口每次请求都带上。流水线本身每次都是从零跑。

这就像跑批作业不记得上一批跑过什么，批次日期这类参数都由调度传进来。好处是同一条流水线可以同时服务界面、接口、评估的 4 个线程，互不串数。

### 4. 首轮基线

模拟库 40 题，「今天」固定为 2026-10-13，deepseek-chat，4 个线程，3 分 11 秒跑完三组：

| 指标 | A 仅模型结构 | B 加血缘 | C 加血缘和样例 |
|---|:--:|:--:|:--:|
| 执行准确率 | 82.9% | 80.0% | **97.1%** |
| 候选召回率 | 100% | 100% | 100% |
| 选表准确率（完全一致） | 74.3% | 77.1% | 62.9% |
| 选表准确率（包含标准用表） | 80.0% | 91.4% | 94.3% |
| 字段准确率 | 82.9% | 91.4% | 94.3% |
| 反问准确率 | 95.0% | 95.0% | 97.5% |
| 平均每题 token | 1.5 万 | 2.6 万 | 2.8 万 |

怎么读这张表：

- **样例贡献最大**：执行准确率 C 比 B 高 17.1 个百分点
- **血缘的贡献在选表和字段上**：按「包含标准用表」算，选表准确率 B 比 A 高 11.4 个百分点；字段准确率 B 比 A 高 8.6。执行准确率 B 比 A 低 2.9，只差 1 道题，在题量的误差内，不能下结论
- **C 组「完全一致」的选表反而最低**：12 道题结果完全对，但 SQL 照着样例多关联了一张维表。内连接维表不会减少行，结果不变；但完全一致的口径要求用表一张不多，所以判错。终审时补了「包含」口径，用同一次的逐题记录重算，两个数一起看

真实库静态评估（C 组 11 题）：标准用表进候选 10/11，SQL 用的表包含标准用表 10/11，有 SQL 的 10 题校验全部 0 错误。

### 5. 评估前后修的两处

- **证据太长**：真实表动辄五六十个字段，加工脚本又长，原来的四级收缩做完还有 9.4 万字。在后面加了五级，11 题都压到了 4 万字以内。模拟库最长 3.4 万字，根本不触发收缩。这个问题只有拿真实数据量才看得出来
- **规则有歧义**：冒烟时，候选里已经有整合层的账户表，模型却连要三次「上溯」。原因是提示词只说「缺字段时用 need_upstream」，模型把「要用下层的表」理解成了「要求程序上溯」。规则改成先在全部候选表里找，只有都没有时才上溯。这一处是在首轮评估之前改的，评估之后没再调提示词

## 🔧 选型

| 决策 | 选了什么 | 没选什么 | 原因 |
|---|---|---|---|
| 编排 | LangGraph 条件边 | 手写 while 循环 | 回路和出口一目了然，`stream` 逐步给进度，界面直接用 |
| 节点名 | 步骤名加 `_node` 后缀 | 直接用步骤名 | recall、evidence、plan 同时是状态字段名，防以后版本冲突 |
| run 与 stream | 共用一条 stream 路径 | run 用 invoke | 两条路的结果必然一致，少一处出错的地方 |
| 取不到流水线 | 接口回 503 并写明原因 | 500 加堆栈 | 没导入元数据、没配 Key 是配置问题，不是程序崩了 |
| 评估并发 | 4 个线程，逐题追加 jsonl | 串行、跑完再写 | 120 次三分钟跑完；中断了可以接着跑 |
| 选表准确率 | 原口径（完全一致）不动，并列一个「包含标准用表」 | 直接改成「包含就算对」 | 看完数字再换口径，等于对着答案改尺子；两个口径并列，既保留原来的尺子，又能看出多关联了维表的写法 |

## 💡 可迁移

- **回环必须有上限，出口必须收口**：任何让模型自己循环的设计（反思、重试、工具调用）都一样
- **先冒烟再评估，首轮评估后不调提示词**：冒烟是验证管道通了，评估是量能力。量完再按错题调提示词，等于对着考卷调参，数字就不可信了
- **规模要在真实数据上量**：模拟库装得下，不代表真实库装得下
- **对照实验三组只差开关**：同一条流水线、同样的候选名额，A、B、C 只差 `use_lineage`、`use_examples`，差值才能算作血缘和样例的贡献

## 👨‍💻 代码

连线：除了 plan 和 validate，每个节点出来只有两个去向，「往下走」或「去 output」。

```python
for here, there in (("parse", "recall"), ("recall", "evidence"), ("evidence", "plan"), ("generate", "validate")):
    graph.add_conditional_edges(_node_name(here), _go_unless_failed(there), destinations(there, "output"))
graph.add_conditional_edges(_node_name("plan"), _after_plan, destinations("recall", "generate", "output"))
graph.add_conditional_edges(_node_name("validate"), _after_validate, destinations("generate", "output"))
```

逐步进度：`stream_mode="updates"` 每走完一个节点给出它改了哪些字段，从中取出轨迹，逐条交给界面。

```python
for chunk in self._app.stream(state, {"recursion_limit": RECURSION_LIMIT}, stream_mode="updates"):
    for update in chunk.values():
        for step in update.get("trace", ()):
            yield step
```

## ⚠️ 常见坑

1. **状态字段和节点同名**：LangGraph 1.1.3 实测不报错，但容易混。节点名加后缀，干净
2. **提示词的规则一字之差就会跑偏**：「缺字段时上溯」和「全部候选都缺时才上溯」，结果是三次无效上溯后失败
3. **码值写成中文名**：追问「只看制造业」时，模型生成了 `industry_cd = '制造业'`，执行 0 行。证据里没有码值说明的字段，模型会猜
4. **包的 `__init__.py` 连带导入旧模块**：旧的 `eval/__init__.py` 导入了旧评估和旧 LangGraph 图，脚本里先导入它再加载 BGE 会段错误。下线旧模块时重写后消失
5. **第一次查询很慢**：导入 `langchain_openai` 会连带加载 torch，召回第一次还要加载 BGE。界面的状态框会一直转，不是卡死

## 面试话术

> 「七个步骤用 LangGraph 串成一张图，三条回路：缺字段上溯、校验不过修正、口径分岔反问。每条回路都有上限，任何一步失败都收口到输出，流水线不往外抛异常。在模拟库上做了三组对照：只给表结构 82.9%，加血缘 80%，再加样例 97.1%。血缘的贡献主要在字段准确率上，加了以后从 82.9% 到 91.4%。」

被追问时可以展开：

- **为什么血缘没提高执行准确率**：差 1 道题，在误差内。字段准确率说明它让模型选对了口径字段；剩下的错在关联和过滤上，例如多加了机构层级条件
- **为什么评估后不调提示词**：调了就是对着考卷调参，基线就不可信了。只修程序错误；提示词的问题在冒烟阶段改，并在报告里写明
