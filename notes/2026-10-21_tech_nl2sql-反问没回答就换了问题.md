# NL2SQL：上一轮的反问没回答就问了新问题——① 多报一项「是不是在回答」，① ④ 按它决定能不能再反问

> 2026-10-20 讨论「会话里换话题」时记下的局限（`notes/2026-10-20_discuss_会话里换话题时上下文怎么处理.md`）：上一轮停在反问上，用户没回答就问了新问题，这一轮 ① 和 ④ 都不许反问。新问题自己要是也需要反问（口径有分岔、单个对象没说是哪个），系统只能按最常用的理解挑一个，写进假设。这次把它改掉。

---

## 📦 目标

- 上一轮的反问没回答、用户问了新问题时，新问题和单独问一样：该反问就反问（① 缺对象；④ 口径分岔、日均的统计区间）
- 真正的回答不能改坏：选项文字、「第一个」「选 2」、「含保证金的」、「按最常用的口径处理」「都行」、补上客户号，照旧不再反问，免得来回问
- 界面：有反问没回答时，提示也可以直接问新问题，给「开新会话」入口；旧反问下面的提示要说实话（没回答，还是回答过了）
- 用数字说话：改前改后对比（每种情形 3 次），模拟库 40 题回归

---

## 📖 讲透

### 1. 原来的规则把两件事画了等号

服务端从会话历史里算上下文：最近一个有完整需求的轮次停在反问上，就把这个反问带给下一轮（`nl2sql/history.py` 的 `_context_from`）。流水线拿到请求后是这么判断的：

```python
allow_clarify = request.prev_clarify is None      # parser.py 和 workflow.py 各有一处
```

意思是「上下文里有反问 = 这一轮在回答反问」。当初这么定是为了防止来回反问：用户刚回答完，④ 又挑出另一个分岔再问一遍。可用户没回答、直接问了新问题时，这条规则照样生效，新问题的 ① ④ 都不许问。

改前实测（见文末数字）：5 种需要反问的新问题，15 次全部没问就直接出了 SQL：口径分岔挑了最常用的一个，单个对象没说是哪个就列出全部。① 想反问的两种，每次都是先反问、被核对驳回、再重试，白花一次调用。最糟的一种：上一轮在问存款口径，用户问「看一下某个客户的贷款情况」，① 被驳回后照着驳回提示「按上一轮反问的第一个选项理解」，3 次都输出了上一轮的存款需求（各开户机构、不含保证金），用户问的贷款整个丢了。

ETL 类比：调度平台上一个作业停在「等人工确认」（比如数据质量检查报警，等运维确认放不放行）。原来的规则是：只要有作业在等确认，操作员提交的下一条指令一律当作对这个确认的回复。操作员想先跑另一个作业，也被当成回复；新作业自己的质量检查也不许再弹确认，只能按默认放行。

### 2. 改成：由 ① 判断这一句是不是在回答

是不是回答，得读懂这句话才知道。① 本来就在读上一轮的需求和反问、决定合并还是换成新需求，判断顺带就做了，不多一次模型调用。`ParsedRequest` 多一项：

```python
answers_clarify: bool = False   # 本轮输入是不是在回答上一轮的反问；没有上一轮的反问时一律为 False
```

| 上一轮 | ① 的判断 | ① 能反问 | ④ 能反问（含日均区间的兜底） |
|---|---|---|---|
| 没停在反问上 | 一律 false | 能 | 能 |
| 停在反问上 | 是回答（true） | 不能 | 不能 |
| 停在反问上 | 新问题（false） | 能 | 能 |

判断标准写在 ① 的系统提示词里（「追问与对反问的回答」一节）：

- **是回答**：选项的文字；「第一个」「选 2」「含保证金的」这样对照选项的说法；「按最常用的口径处理」「都行」这样让系统定的说法；补上反问要的东西（反问哪个客户，回复客户号）。回答时顺带改了别的（「含保证金的，换成 6 月末」）也算回答
- **不是回答**：本轮输入本身就是一个完整的查数需求（有指标有时间），或者要看的是另一个指标、另一类对象。**完整的新需求里恰好带了选项里的说法，也是新问题**（第一版提示词没写这条，见常见坑 1）

示例凑成一对，都是上一轮停在反问上：原有的「按最常用的口径处理就行」标上 answers_clarify 为 true（回答，按第一个选项）；新加一个「看一下某个合同的放款情况」，answers_clarify 为 false（新问题，照常反问是哪个合同）。

ETL 类比接着说：调度入口先看这条指令是「对确认的回复」还是「新作业」。是回复就按回复走，不再弹确认；是新作业就走它自己的检查，该弹确认照样弹。原来等确认的作业挂着，界面上标成「没确认，后面换成了新作业」。

### 3. 代码兜底三处

模型报的判断不能全信，`nl2sql/parser.py` 里补了三道关：

1. **必须写明**：上一轮停在反问上时，① 的输出里必须有 answers_clarify 这一项。用 pydantic 的 `model_fields_set` 区分「模型写了 false」和「模型没写、取了默认值 false」，没写就退回重试。默认值是 false，漏写会被当成新问题，用户回答完 ④ 又能再问
2. **自相矛盾就退回**：写了 true（在回答）又带了反问，退回重试。提示里给两条改法：去掉反问；或者这句其实是新问题，就把 answers_clarify 改成 false
3. **和上下文矛盾就改掉**：上一轮没停在反问上，模型写了 true 也改成 false（`parse_request`）。这样后面的步骤只看这一项就行

### 4. 上下文和界面

`history._context_from` 不用改：新问题出了结果，下一轮的上下文就是新需求、没有反问；新问题又反问了，上下文换成新的反问，旧反问的选项不能点了（`clarify_turn_id` 换成了新的一轮）。

界面三处：

- 输入框上方：「上一轮在等你确认：…… 点上面的选项或者直接写你的口径；不想回答，也可以直接问新的问题」，后面加「开新会话」按钮（以前只有追问时才有）
- 能点的反问卡片下面：同样提示可以直接问新问题
- 不能点的旧反问：以前一律写「这次反问已经回答过了」。现在看它后面第一个有完整需求的轮次（和服务端算上下文用同一个规则），那一轮的 answers_clarify 是 false，就写「这次反问没有回答，后面换成了新的问题」。早先存下的轮次没有这一项，按回答过了算

① 的运行过程摘要开头也会写明「回答上一轮的反问；……」或「上一轮的反问没有回答，按新问题处理；……」；新问题的假设里有一句「没有回答上一轮的反问，按新需求解析」，用户一眼能看出系统是怎么理解的。

## 🔧 选型

| 方案 | 做法 | 结论 |
|---|---|---|
| A（选了） | ① 多报 answers_clarify，按它放开 ① ④ | 判断放在本来就读上下文的那一步，不多调用模型；有代码兜底 |
| B | 规则匹配：本轮输入和选项文字对得上才算回答 | 「第一个」「都行」「C000015」「含保证金的」说法太多，匹配不全；新问题里也会带选项的词（「全行不含保证金的存款日均余额」），一匹配反而判错 |
| C | 单独加一次模型调用，专门分类「回答还是新问题」 | 多一次调用、多一两秒；① 本来就在读上一轮的需求和反问 |
| D | 去掉限制，任何时候都能反问 | 用户回答完，④ 可能挑出另一个分岔再问，来回反问 |

## 💡 可迁移

- **状态不等于意图**：「有一个待回答的问题」是状态，「用户在回答它」是意图。对话的状态转移要看这一句的意图，不能只看当前状态
- **顺带报告比单独分类便宜**：已经在读上下文的那一步多输出一个字段，比再加一次分类调用省时省钱
- **模型给的判断要有代码兜底**：要求明确写出（不靠默认值）、和上下文矛盾的值改掉、自相矛盾的输出退回重试并给出两条改法
- **防死循环的限制要绑在「真的在回答」上**，不要绑在「有待回答的问题」上，否则会误伤别的输入
- **判断标准里要写反例**：「带了选项里的词」不等于「在回答」，这条是对比实验暴露出来的。只写正例，模型会按字面匹配

`nl2sql/parser.py` 的核对：

```python
def check_parsed(parsed: ParsedRequest, *, pending_clarify: bool = False) -> list[str]:
    ...
    if pending_clarify and "answers_clarify" not in parsed.model_fields_set:
        problems.append("用户消息里有「上一轮的反问」，请在 answers_clarify 里写明本轮输入是不是在回答这个反问：……")
    if parsed.clarify is not None:
        allow_clarify = not (pending_clarify and parsed.answers_clarify)
        return problems + _check_clarify(parsed, allow_clarify) + _check_time(parsed.time)
```

allow_clarify = not state["parsed"].answers_clarify        # 以前是 request.prev_clarify is None

function clarifySkipped(turns: Turn[], index: number): boolean {

}

## ⚠️ 常见坑

1. **新问题里带了选项的词，被当成回答**：第一版提示词只写了「回答」「新问题」各是什么样。上一轮问「存款余额按哪个口径」，用户问「查 9 月末全行不含保证金的对公存款日均余额」，3 次都被判成回答（里面有「不含保证金」），日均的统计区间就没法再问了，悄悄按年日均出了 SQL。这道题单独问时（题库 A05）本来就该反问。补了一句「完整的新需求里恰好带了选项里的说法，也是新问题」，配一个不同的例子（前 10 名客户），之后 3/3。例子特意没用对比里的原题，免得测的是背答案
2. **默认值会掩盖漏写**：answers_clarify 默认 false。模型漏写这一项，回答就被当成新问题，④ 又能再问。所以上一轮停在反问上时要求必须写明，用 `model_fields_set` 区分写了 false 和没写
3. **测试造数**：`model_dump_json()` 会把默认值也写进 JSON，测「模型漏写」要用 `model_dump(exclude={"answers_clarify"})`。旧测试里「请求带了 prev_clarify 就等于在回答」，现在要在 ① 的回复里写明 answers_clarify 为 true，改了 4 处造数
4. **行为变了的一种情况**：反问没回答，用户只说「换成 6 月末的」。以前被当成「回答没说清」，按第一个选项（不含保证金）直接出 SQL；现在合并成 6 月末的需求，④ 再问一次口径。用户没回答，就不替他选
5. **把需求连同口径完整重述一遍，算哪种都行**：「查 9 月末各开户机构含保证金的对公存款余额……」3 次都判成回答，出 SQL 用全口径。判成新问题结果也一样：口径已经写明，④ 不会再问
6. **界面验证**：内置浏览器的窗格在后台时视口只有 400×225，按元素点反问选项会点偏、没反应；用 `resize_window` 调成 1280×900 再点就好
