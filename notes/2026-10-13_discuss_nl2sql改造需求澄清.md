# NL2SQL 改造：需求澄清记录

> 日期: 2026-10-13 | 类别: discuss | 状态: 需求已澄清，设计已成文
> 关联: [[2026-10-13_design_nl2sql专题库改造]]

---

## 背景

把 AgentFlow 从「通用 AI 助手（文档问答 + Text-to-SQL + 多 Agent 路由）」改造成
**「基于专题库模型结构 + 血缘关系的自然语言转 SQL 工具」**。

一句话需求：用户用自然语言描述查数需求，工具结合专题库的模型结构和血缘关系，生成数据查询 SQL。

---

## 现状与目标的差距

| 维度 | 现状（sql/agent.py） | 目标 |
|------|---------------------|------|
| 表结构来源 | 直连库实时读取（现翻 information_schema） | 数据字典导入（带中文名、口径说明） |
| 表间关系 | 无，靠模型猜 | 来自血缘和加工脚本里的关联条件 |
| 血缘 | 无 | 字段级血缘 + 加工逻辑 |
| 数据范围 | sample.db 3 张表 | 贴源层 → 整合层 → 专题层整条链路 |
| SQL 方言 | SQLite | GaussDB / PostgreSQL 系 |
| 质量把关 | 执行一下看报不报错 | 不执行的静态校验 |
| 输出 | SQL + 自然语言答案 | SQL + 口径说明 + 依据 |

仓库里目前没有任何专题库的模型结构或血缘资料，需要先造一套模拟的。

---

## 澄清结论

| # | 问题 | 结论 | 对设计的影响 |
|---|------|------|-------------|
| 1 | 给谁用、什么场景 | 两者兼顾：先用模拟专题库做通并出评估指标，之后可换真实专题库资料 | 需要一层**标准元数据格式**（相当于接口表），模拟库和真实库都往里灌，上层逻辑不变 |
| 2 | 真实资料的形态 | Excel/Word 数据字典 + ETL 加工脚本 + 现成的血缘清单 | 标准格式要能承接这三类资料；血缘不必全靠解析脚本得到 |
| 3 | 血缘起什么作用 | 四项全要：搞清字段口径、选对表、找关联路径、向上溯源查数 | 血缘是主线而非附加说明；查询范围从专题库扩大到整条加工链路 |
| 4 | 运行方式 | 先只生成不执行，执行层留扩展口 | 质量把关靠静态校验；执行层做成可插拔，模拟库上可执行用于评估 |
| 5 | SQL 方言 | GaussDB / PostgreSQL 系 | 生成和校验都按 PostgreSQL 方言；模拟库引擎要尽量贴近这个方言 |
| 6 | 主要需求类型 | 余额/规模统计（时点余额、日均、较年初/较上月增量） | 难点集中在口径：含不含保证金、是否折人民币、机构按哪个层级汇总、数据日期 |

## 设计阶段追加的决策

| # | 问题 | 结论 |
|---|------|------|
| 7 | 技术方案 | 元数据库 + 血缘图 + 分步流水线。否决了「元数据检索加一次生成」（血缘只能当文本用，口径和多跳溯源做不好）和「工具调用型 Agent」（路径不可控，不能保证每次都检查血缘） |
| 8 | 旧功能去留 | 下线替换：先打标签 `v1-agentflow`，新模块并排建设，评估后切换并删除旧模块 |
| 9 | 血缘清单粒度 | 字段级，不带加工逻辑。血缘边用清单，加工逻辑和过滤条件从脚本抽取 |
| 10 | 口径有歧义时 | 反问一次再生成 |
| 11 | 界面与接口范围 | 查数页 + 元数据页，4 个接口，元数据导入走命令行 |
| 12 | v1 追加范围 | 连续追问（合并进需求解析，流水线无状态）；历史 SQL 样例库（`.sql` 文件加注释头，导入时校验，与题库不重叠） |

## 拿到真实专题库资料之后

设计通过、第一份计划写好之后，用户提供了当前工作中真实专题库的三样资料：模型设计文档（及生成它的元数据库）、加工 SQL 目录、标准层与贴源层的索引库。只读调研之后的结论如下。真实资料的具体内容不记录在这里。

**与原先假设的差异**

| 发现 | 对设计的影响 |
|------|-------------|
| 业务领域与模拟库不同 | 之前按银行业务给出的需求类型选项不适用，真实库上的典型问题要另行收集 |
| 专题层的表是清空后全量重装的宽表，没有按日快照 | 表类型增加「全量表」；「快照表必须带日期条件」这条规则对它不生效 |
| 相当一部分标准层的表没有主键标记，一批字段没有类型 | 粒度字段、数据类型从必填改为选填，缺失时给警告并汇总 |
| 血缘单元格里并列写多张表、有占位说明、模式名时有时无 | 需要专门的转换器来清洗 |
| 约三成专题层字段没有记录标准层血缘，但加工脚本全部可以解析 | 「从脚本解析血缘」从不做改为第二份计划要做 |
| 表和字段的总量在千张表、近两万字段的量级 | 印证了必须先召回再生成 |
| 血缘里带加工说明，脚本头部注释里有详细的口径说明 | 口径证据比预想的丰富 |

**追加的决策**

| # | 问题 | 结论 |
|---|------|------|
| 13 | 真实库与模拟库的关系 | 真实库为主，模拟库保留。真实库本机没有数据，可执行的评估只能在模拟库上做，公开仓库里也只能放模拟库 |
| 14 | 真实资料怎么接入 | 专用转换器，读生成设计文档的元数据库而不是 Excel；转换器和转换结果都放在不入库的 `data/real_mart/`；标准模板放宽三处；清洗掉的内容全部写进转换报告 |

**验证结果。** 转换器在原型阶段已经用真实资料跑通：转换后按标准流程导入，0 错误。当前的加工脚本全部能被计划中的解析方案解析。

**保密边界。** 真实资料只读，只留在本机不入库的目录里。真实的表名、模式名、路径、单位名称不写进任何入库的文件。流水线运行时元数据会发给大模型，正式使用前需要用户确认单位是否允许，不允许则换成内网可用的模型。

## 沿用的假设

以下假设在讨论中提出过两次，没有被否定，设计按此进行：

- 使用者是懂 SQL 的数据开发人员，输出由人审核后再拿去执行（工具是副驾驶，不是自动驾驶）。
- 模拟专题库按「银行对公存贷款」业务来造，分贴源层、整合层、专题层。
- 真实元数据不进这个仓库；大模型地址可配置，将来换内网模型不用改代码。

---

## 数据安全提醒

真实专题库的表结构、血缘、加工脚本如果发给外部大模型（DeepSeek），需要符合行内数据安全要求。
现阶段只用模拟数据；接真实资料前要先确认能否外发，不能的话换内网可用的模型。
