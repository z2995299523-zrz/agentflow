## 📦 目标

模型写出来的 SQL，在执行之前先过一道**静态校验**。它就是上线前的脚本评审：不跑数，只看表名、字段名对不对，快照表有没有漏日期条件，关联键是不是已知的那几种，关联维表时主键带没带全。

在查询流水线里它是第 ⑥ 步：有错误就带着错误信息回到第 ⑤ 步让模型改（最多改 2 次）；导入样例库时也用它把关，没通过的样例拒收（W08）。

| 规则 | 查什么 | 级别 | 防什么 | 类比 |
|------|--------|------|--------|------|
| R1 | 按 PostgreSQL 能解析，且只有一条语句 | 错误 | 语法写错 | 脚本编译不过 |
| R2 | 只能是查询，语法树里不能有增删改、建表、`SELECT … INTO`、`FOR UPDATE` | 错误 | 写操作 | 查数账号只给 SELECT 权限 |
| R3 | 每张实体表都在元数据里 | 错误 | 编造的表 | 表名要在数据字典里 |
| R4 | 每个字段都在它所属的那张表里 | 错误 | 编造的字段、张冠李戴 | 字段要在 mapping 的那张源表里 |
| R5 | 快照表在所在的查询层带数据日期条件 | 错误 | 余额跨日累加 | 取快照表忘了限定数据日期 |
| R6 | 等值关联属于已知的关联关系 | 警告 | 乱关联 | 关联字段要对得上模型设计 |
| R7 | 汇总时被关联的表，粒度字段全部被等值约束 | 警告 | 发散、金额翻倍 | 关联维表没带全主键 |
| R8 | 用到的表和字段与查询方案一致 | 警告 | 写 SQL 时跑偏 | 开发结果和需求文档对不上 |

校验报告除了问题清单，还给出 SQL **实际用到的实体表和字段**（穿过 CTE、子查询追到实体表），评估时拿它算选表准确率和字段准确率。

数字指标：

- 单元测试 151 项（`tests/test_validator.py`），R1–R8 每条都有正例和反例，只用模拟库和手写的小 SQL，不调模型，2 秒跑完。
- 模拟库 35 道标准 SQL：0 错误；用表与标准用表完全一致，标准关键字段全部出现在「实际用到的字段」里。警告只有 R6 14 条，原因是关联推导还没做、模拟库目前只有 1 条手工关联。7 个模拟加工脚本的查询部分：0 错误（R6 警告 9 条，原因相同）。
- 真实专题库（只读验证，只记数字）：45 条加工语句的查询部分，R1、R2、R5 为 0；R3、R4 报出的全部是真问题（清单外的表、字段清单缺口），误报 0；单条平均约 75 毫秒。

## 📖 讲透

### 1. 错误和警告：哪些必须改，哪些给人看

- **错误**是「这条 SQL 在库里跑不了，或者跑出来一定是错的」：表不存在、字段不存在、写操作、快照表没限定日期。错误必须修，修不好不执行。
- **警告**是「可能有问题，但规则本身不够确定」：关联关系是推导出来的，可能不全（R6）；粒度字段可能没填（R7）。警告展示给人判断，不拦截。

顺序也有讲究：R1、R2 不通过直接返回；**R3 不通过时不报 R4**。表都是编造的，它的字段自然一个都对不上，把几十条字段错误一起扔给模型只会添乱。先把表改对，下一轮再查字段。类比数据质量检核：表级检核不过，就不再跑字段级检核。

### 2. R1、R2：为什么按语法树判断，不用关键词黑名单

旧版 SQL 模块按空白分词，看有没有 `DELETE`、`DROP` 这几个词。它有两头的毛病：

- **挡不住**：`(DELETE`、`;DROP`、`DELETE/**/FROM` 这种贴着符号写的，分出来的词不是 `DELETE`；`SELECT … INTO 新表`（建表）、`SELECT … FOR UPDATE`（加锁）、`COPY`、`GRANT`、`SET` 根本不在名单里；`WITH d AS (DELETE … RETURNING …) SELECT …` 开头是 SELECT，里面却在删数。
- **会误伤**：字符串 `'to delete later'`、不带别名的字段名 `update`，分词以后都是关键词。

新做法是先用 sqlglot 解析成语法树，再看两件事：

1. **根节点**必须是查询（`Select`、`UNION` 这类集合运算，或者外面包着括号的它们）。`INSERT`、`DO $$…$$`、`BEGIN`、单独的 `VALUES` 都不是。
2. **整棵树**里不能出现写操作、建表、`Into`（`SELECT … INTO`）、`Lock`（`FOR UPDATE`）、事务控制、`SET`、`GRANT` 这些节点。

语法树里，`is_deleted` 是一个字段节点，`'DELETE'` 是一个字符串常量节点，注释根本不进树，所以都不会误伤；`DELETE` 写在 CTE 里，它在树里就是一个 `Delete` 节点，藏不住。类比评审脚本：看的是这条语句的执行计划是什么类型的操作，而不是在文本里搜 `DELETE`。

R1 的两个细节：末尾的分号和分号后面的注释不算第二条语句（sqlglot 会返回空节点和分号节点，要去掉）；解析失败时给出 sqlglot 的原因和行列号，并去掉报错文字里的 ANSI 转义符（终端下划线），不然模型会看到一串乱码。

### 3. R3：在语法树里找实体表

遍历语法树里的表节点，排除 CTE 名（`WITH t AS (…) SELECT … FROM t` 里的 `t` 是临时中间结果，不是库里的表），剩下的逐个查元数据：

- 没带模式名：`FROM corp_cust_loan_bal_d` → 「应写成 ads.corp_cust_loan_bal_d」。多个模式下都有同名表时全部列出。
- 不存在：附上 difflib 算出的最接近的 5 张表。

sqlglot 的字段限定能查出不存在的字段，却查不出不存在的表（它把不认识的表当外部表放过），所以 R3 必须自己遍历表节点。

### 4. R4：为什么要按作用域查，不能只看「字段存不存在」

最省事的做法是：把 SQL 里出现的字段名拿去元数据里搜，搜得到就算对。这会放过最常见的一类错误——**张冠李戴**：

```sql
SELECT l.cust_nm
FROM ads.corp_cust_loan_bal_d l
JOIN dim.corp_cust c ON l.cust_no = c.cust_no
```

`cust_nm` 在客户维表里确实有，但 `l` 指的是贷款汇总表，那张表没有这个字段，PostgreSQL 会报错。所以 R4 要回答的是「**这个别名在这一层指的是哪张表，那张表有没有这个字段**」，和存储过程里同名变量在不同的块里指不同的东西是一回事。

具体做法（别名指向、作用域都来自共享的 `metadata/sqlscope.py`）：

1. 先按元数据限定字段（`qualify_with_catalog`）。「别名.字段」写法引用了字段清单里没有的字段，记为**字段清单缺口**，逐个报 R4；引用了 CTE 里不存在的输出列，sqlglot 会直接报错，这时报一条 R4 并跳过 R5–R7（作用域都建不起来，后面的规则没法查）。
2. 然后逐个查询层检查每个字段：
   - **带别名**：别名指向实体表，就查字段清单；指向 CTE、派生表，就查它的输出列（输出列里有没展开的 `*` 时不判）；本层没有这个别名就沿外层找（相关子查询可以引用外层的别名），还找不到就是「别名没有定义」。
   - **不带别名**：在本层所有来源里找。恰好一个来源有，就是它的；一个都没有，报错；两个以上，报「有歧义」（PostgreSQL 也会报 `column reference is ambiguous`）。`sysdate`、`current_user` 这类伪列放过。
   - **输出别名**：`ORDER BY`、`GROUP BY` 可以引用 SELECT 列表里的输出别名；`WHERE`、`HAVING`、`JOIN … ON` 不行，因为 PostgreSQL 处理它们的时候还没算 SELECT 列表。
3. 每条报错都附上最接近的字段名，别名指错了表时，再提示「哪个别名的表有这个字段」，方便模型自己改：

```text
表 ads.corp_cust_loan_bal_d 没有字段 cust_nm（写作 l.cust_nm）；最接近的字段：cust_no、…；c（dim.corp_cust）有这个字段
```

**实际用到的表和字段**在这一遍里顺带收集：字段指向实体表就记「模式.表.字段」；指向 CTE 的输出，就沿 CTE 追到实体字段。所以报告里永远是实体表的字段，不会出现 `c.bal` 这种 CTE 里的名字。

### 5. R5：快照表每一层都要带数据日期

快照表每个数据日期存一份全量。不限定日期就汇总，等于把每天的余额加在一起——银行里最典型的错账。R5 的规则：**每个查询层**里指向快照表的别名，它的数据日期字段要出现在本层的 WHERE 或某个 JOIN 的条件里。

- 宽松在「怎么写都算」：`= DATE '…'`、`IN (…)`、`BETWEEN`、`= r.data_dt`（跟另一张表的日期对齐）都算。
- 严格在「按层算」：日期条件写在 CTE 里，不能保护主查询里对同一张表的另一次引用；子查询里引用快照表，要在子查询里自己带日期。模型生成 SQL 时也被要求直接写在原表上，所以这里不做跨层放宽。
- 全量表、维表只有当前状态，不要求。

报错里直接给出可以照抄的写法：`l.data_dt = DATE '…'`。

### 6. R6：关联键要对得上已知的关联关系

关联条件里的「列 = 列」，两侧都穿过 CTE、子查询追到实体表的字段（由 sqlscope 的 `joins()` 完成），再和已知的关联关系比对：两张表之间任一方向、任一来源的关联，在同一位置有这对字段，就算对上。

- 方向无关：`b.org_no = o.org_no` 和 `o.org_no = b.org_no` 一样。
- 复合关联的一部分也放行：已知关联是（数据日期, 客户号, 机构号），SQL 只按客户号关联，R6 不管，会不会发散交给 R7。
- 对不上时列出这两张表已知的关联，直接是可以照抄的关联条件：

```text
关联条件 ads.org_corp_dep_bal_d.org_no = dim.org.lvl1_org_no 不在已知的关联关系里；这两张表已知的关联：ads.org_corp_dep_bal_d.org_no = dim.org.org_no（N:1）
```

R6 是警告不是错误：关联关系大部分是推导出来的，不保证全。

### 7. R7：汇总时关联维表要带全粒度

这是数仓里最常见的「金额翻倍」：汇总存款余额时关联汇率表，只按币种关联、没限定汇率日期，汇率表里每个币种每天一行，一条存款就关联出 30 行，余额翻了 30 倍。

```sql
SELECT a.ccy_cd, SUM(a.acct_bal) AS bal
FROM dwd.corp_dep_acct_d a
JOIN ods.exch_rate r ON a.ccy_cd = r.ccy_cd          -- 汇率表粒度是（数据日期, 币种），只带了币种
WHERE a.data_dt = DATE '2026-09-30' AND r.data_dt >= DATE '2026-09-01'
GROUP BY a.ccy_cd
```

R7 的规则：

1. 只看**含汇总的查询层**。`MIN`、`MAX`、`COUNT(DISTINCT …)` 不怕行数翻倍，不算；`SUM(…) OVER (…)` 是窗口函数，也不算汇总。
2. **被汇总的表**：聚合函数里出现的字段属于哪个别名，那张表就是被汇总的；只有 `COUNT(*)` 时取 FROM 的第一张表。被汇总的表本身不查。
3. 其余每张有粒度的实体表，它的**每个粒度字段**都要在 WHERE 或 JOIN 条件的 AND 子句里被等值约束：另一侧可以是别的表的字段、字面量、函数；只有一个元素的 `IN` 也算。`>=`、多个元素的 `IN`、`BETWEEN` 都约束不成单值，不算。缺任何一个就警告。

粒度字段没填的表无法判断，跳过。上面的例子会得到：

```text
汇总查询关联了 ods.exch_rate（别名 r），它的粒度是 (data_dt, ccy_cd)，其中 data_dt 没有用等值条件约束，一条记录可能关联出多行，汇总结果会重复计算（位置：主查询）
```

### 8. R8：与查询方案对比

传了期望的表，就对比两边的差集：方案里有、SQL 没用到的，和 SQL 用到了、方案里没有的，各报一条警告；传了期望的字段，就报其中没用到的。没传就不查。

## 🔧 选型

| 决策 | 选了什么 | 没选什么 | 原因 |
|------|----------|----------|------|
| 判断语句类型 | 语法树的根节点和全部节点 | 关键词黑名单 | 黑名单绕得过（贴着符号写、写在 CTE 里），又会误伤字段名和字符串 |
| 别名和字段归属 | 共享的 `sqlscope`（作用域、限定、追溯、关联键） | 校验器自己再写一套 | 加工脚本解析器也用同一套，两边对同一个字段的理解必须一致 |
| 字段检查 | 限定后逐个作用域检查每个字段 | 只看 sqlglot 限定时报不报错 | 关掉列校验后，不带别名的未知字段 sqlglot 不报错；有歧义的字段它也只是不限定 |
| 输出别名误用 | 在没限定的树上单独查 WHERE、HAVING | 只查限定后的树 | sqlglot 限定时会把 WHERE 里的输出别名悄悄换成原表达式，DuckDB 也能跑，但 PostgreSQL 会报错 |
| 索引 | 构造时建好「表 → 字段」「无序表对 → 已知关联」 | 每次 validate 现查元数据 | 生成回路里一条 SQL 可能校验好几次，索引只建一次 |
| 报错内容 | 附上 difflib 最接近的 5 个表名或字段名、可以照抄的写法 | 只说「不存在」 | 错误信息是给模型看的，要能直接拿来改 |
| 规则代码出错 | 记一条该规则的警告，校验照常结束 | 抛异常 | 校验器在导入和生成回路里跑，一条怪 SQL 不能把整个流程打断 |

## 💡 可迁移

**1. 先结构、后细节，避免错误连锁。** 表不对就先不查字段，作用域都建不起来就先不查关联。任何多层检核（数据质量规则、代码评审清单）都可以按这个顺序：上游检查不过，下游检查只会制造噪声。

**2. 给机器看的报错要「可执行」。** 报错里带上最接近的候选名、可以照抄的条件写法、出问题的位置（主查询、哪个 CTE）。给模型的错误信息越具体，修正一次成功的概率越高，和给开发同事写评审意见一个道理。

**3. 语义检查要基于语义结构，不要基于文本。** 关键词黑名单、全文搜字段名，都是在文本上做文章；换成语法树和作用域，才能区分「字段名里带 delete」和「真的在删数」，「客户名称这个字段存在」和「这张表有客户名称」。

## 👨‍💻 代码

下面的片段取自 `nl2sql/validator.py`，为了讲解做了删节。

**主流程（`validate`）。** R1、R2 不通过直接返回；R3 不通过就不报 R4；作用域建不起来就跳过 R5–R7：

```python
run = _Run()
statement = self._check_parse(sql, run)                          # R1
if statement is None or not self._check_query_only(statement, run):   # R2
    return run.report()
query = _unwrap_query(statement)
tables_ok = self._check_tables(query, run)                       # R3，顺带登记用到的表
analysis = self._check_columns(query, run, report=tables_ok)     # R4，顺带收集用到的字段
if analysis is not None:
    root, resolver = analysis
    self._guarded("R5", run, lambda: self._check_snapshot_dates(root, resolver, run))
    self._guarded("R6", run, lambda: self._check_relations(root, resolver, run))
    self._guarded("R7", run, lambda: self._check_fan_out(root, resolver, run))
self._check_plan(run, expected_tables, expected_columns)        # R8
return run.report()
```

**R4 不带别名的字段（`_check_unqualified`，删节）。** 输出别名只在 ORDER BY、GROUP BY 里放过；其余在可见的来源里找，恰好一个才通过：

```python
clause = _clause_of(column, scope.expression)                  # 字段在哪个子句：where、joins、order……
if clause in ("order", "group") and name in self._output_aliases(scope, resolver):
    return
owner_scope, owners, unknown = self._owners(scope, resolver, name)   # 本层找不到时，相关子查询再往外层找
if len(owners) == 1:
    run.used.update(resolver.resolve_column(scope, column).sources)  # 追到实体字段，记进「实际用到的字段」
    return
if owners:
    ...  # 有歧义
if name.lower() in PSEUDO_COLUMNS or unknown:                  # 伪列；或者来源里有不知道字段的表，不判
    return
if clause in _ALIAS_FREE_CLAUSES and name in _explicit_aliases(scope.expression):
    ...  # WHERE、HAVING、ON 里引用了输出别名
...  # 都没有：报错，附上最接近的字段
```

**R7 等值约束（`_equality_targets`）。** 一个 AND 子句能把哪些字段约束成单值：

```python
condition = condition.unnest()
if isinstance(condition, exp.EQ):
    for side, other in ((condition.this, condition.expression), (condition.expression, condition.this)):

            targets.append(column)                              # 另一侧不引用它自己的别名就算
if isinstance(condition, exp.In) and not condition.args.get("query") and len(condition.expressions) == 1:
    ...  # 只有一个元素的 IN 也算
```

**一次真实的运行（模拟库）。** 模型把字段名写短了、还漏了日期：

```python
validator = SqlValidator(store)
report = validator.validate("""
    SELECT o.lvl1_org_nm, SUM(b.dep_bal) AS bal
    FROM ads.org_corp_dep_bal_d b
    JOIN dim.org o ON b.org_no = o.org_no
    GROUP BY o.lvl1_org_nm""")
```

```text
R4 错误 表 ads.org_corp_dep_bal_d 没有字段 dep_bal（写作 b.dep_bal）；最接近的字段：dep_bal_rmb、dep_bal_tot_rmb、ytd_avg_bal_rmb、dep_cust_cnt、margin_bal_rmb
R5 错误 快照表 ads.org_corp_dep_bal_d（别名 b）没有数据日期条件，会把多天的数据加在一起；请在 WHERE 或关联条件里加上 b.data_dt = DATE '…'（位置：主查询）
R6 警告 关联条件 ads.org_corp_dep_bal_d.org_no = dim.org.org_no 不在已知的关联关系里，这两张表之间没有已知关联，请确认关联字段
```

R6 这一条是因为关联推导还没做，模拟库里只有 1 条手工关联；推导做完以后，同名粒度键会给出「机构汇总表.机构号 → 机构维表.机构号」，这条警告就会消失。

经过 CTE 的查询，报告里的用表和字段都是实体表的：

```sql
WITH c AS (SELECT b.org_no, SUM(b.dep_bal_rmb) AS bal
           FROM ads.org_corp_dep_bal_d b
           WHERE b.data_dt = DATE '2026-09-30'
           GROUP BY b.org_no)
SELECT o.lvl1_org_nm, SUM(c.bal) AS bal
FROM c JOIN dim.org o ON c.org_no = o.org_no
GROUP BY o.lvl1_org_nm
```

## ⚠️ 常见坑

1. **sqlglot 限定字段时会悄悄改写 SQL。** WHERE、HAVING 里引用 SELECT 的输出别名，它会换成别名对应的表达式；同一张表不带别名用了两次，它会把第二个改名成 `表名_2`。改完的 SQL 在 DuckDB 上能跑，在 PostgreSQL 上会报错。所以这两种情况要在没限定的原树上单独查。
2. **关掉列校验后，未知字段不会报错。** `validate_qualify_columns=False` 时，不带别名、哪张表都没有的字段，sqlglot 只是不给它加别名。必须自己逐个作用域检查，不能只看 `qualify` 有没有抛异常。
3. **sqlglot 的 `scope.columns` 会把相关子查询里引用外层的字段，同时算进外层。** 用它逐层遍历，同一个字段会被检查两次。要用 `scope.find_all(exp.Column)`，它只走本层、到子查询的边界就停。
4. **没带别名的表，限定以后别名就是表名。** 报错里的示例写法因此是 `corp_cust_loan_bal_d.data_dt = DATE '…'`，这在 SQL 里是合法的，可以照抄。
5. **difflib 在几百张表上取「最接近的 5 个」很慢。** `get_close_matches` 把门槛设成 0 时，要对每张表算一遍完整的相似度。先用便宜的 `quick_ratio`（它是相似度的上界）排序，算到上界追不上第 5 名就停，结果完全相同，算的次数少了七成多。
6. **R3 不通过会挡住 R4，统计时要算上被挡住的。** 真实库里有 1 条语句同时引用了清单外的表和清单缺字段的表，它的 8 处缺口这一轮不报。拿 R4 的数字和脚本解析算出的缺口核对时，差额要能用这些语句解释。
7. **R2 只管语句类型，管不了函数的副作用。** `nextval()`、`pg_sleep()`、`set_config()`、`dblink_exec()` 写在 SELECT 里，语法树上仍是一条查询。真要在真实库上执行，还得靠只读事务和语句超时兜底。
8. **R5、R7 都按查询层算，R7 只看实体表。** 日期条件写在 CTE 里保护不了主查询；被汇总的表去关联一个 CTE 时，CTE 那一侧会不会发散，R7 不管。

## 面试话术

> 「模型生成的 SQL 先过一道静态校验，相当于上线前的脚本评审：不跑数，用 sqlglot 的语法树判断只能是查询，取代关键词黑名单；按元数据查表名，按作用域查字段归属；快照表每一层都要带数据日期；关联键穿过 CTE 追到实体表再和已知关联比对；汇总时检查维表的粒度有没有约束全，防止金额翻倍。错误信息附上最接近的表名、字段名，让模型自己改。真实 45 条加工语句上零误报，单条平均 75 毫秒。」

被追问时可以展开的三点：

- 为什么不用关键词黑名单：分词能被 `(DELETE`、写在 CTE 里的 DELETE 绕过，`SELECT … INTO`、`FOR UPDATE` 不在名单里，还会误伤字段名和字符串；语法树上是什么操作一目了然。
- 为什么按作用域查字段：只看「字段存不存在」会放过张冠李戴，比如贷款表的别名后面跟了客户名称；要看这个别名在这一层指哪张表。
- R7 怎么判断发散：汇总查询里，被汇总表以外的每张表，粒度字段都要被等值约束，缺一个就可能一对多，金额翻倍。
