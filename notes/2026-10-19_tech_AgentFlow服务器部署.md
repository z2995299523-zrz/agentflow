## 📦 目标

将当前 React 前端、FastAPI 查询流水线、BGE 检索和 DuckDB 模拟执行一起部署成可访问的面试演示站。运行完整的模拟银行专题库，不上传真实专题库和本地会话记录。

用 ETL 上线作类比：需要发布的不是一段 SQL 文件，而是一整套能运行的批量，包括程序版本、依赖、输入字典、生成物、调度配置和验收结果。首页能打开只相当于调度平台能登录，不能说明这条查数链路已经跑通。

## 📖 讲透

复用同机已有网站的发布结构：本地测试与提交 → 推送 Git → 服务器拉取完整提交 → 独立环境测试与准备 → 原子切换 `current` → HTTPS 与业务验证。

| 对象 | 服务器位置 | 对应 ETL 概念 |
| --- | --- | --- |
| Git 对象 | `/opt/agentflow/repo.git` | 经过登记的脚本版本库 |
| 运行代码 | `/opt/agentflow/releases/git-<SHA>` | 每次发布单独落地的程序目录 |
| 活动版本 | `/opt/agentflow/current` | 调度当前指向的正式版本 |
| 分版本元数据与模拟库 | `/var/lib/agentflow/marts/<SHA>/build` | 与本次程序版本配套的可再生加工结果 |
| 会话历史 | `/var/lib/agentflow/history.db` | 需要跨版本保留的业务流水 |
| 模型缓存 | `/var/lib/agentflow/huggingface` | 可复用的运行资源 |
| 运行配置 | `/etc/agentflow/app.env` | 仓库外的连接配置，权限 root:agentflow 0640 |
| 会话备份 | `/var/backups/agentflow` | 一致性快照与恢复演练材料 |
| 发布证据 | `/opt/agentflow/deployments/<SHA>` | 本批次测试、版本、依赖和验收日志 |

前端由 Nginx 直接提供静态文件，浏览器的 `/api/` 请求转给 `127.0.0.1:8790`。新站只增加 8447 HTTPS 入口；同机其它站点和服务继续使用原配置。

这和数据库里区分“可重算的汇总表”和“不能覆盖的交易流水”一样：元数据、模拟数据可按版本重建，会话历史单独保存。因此更新或回退代码时，不会拿旧会话库覆盖用户新写入的记录。

SSE 在 Nginx 禁用缓冲，设置 600 秒代理读写超时。实际验证中，第一轮在 1.591 秒收到需求解析步骤，5.205 秒收到选表口径步骤，6.222 秒收到最终结果，证明进度在查询结束前已经到达浏览器侧。

## 🔧 选型

服务器实际为 Ubuntu 24.04、约 2 GB 内存，原站使用 Nginx、systemd 和独立 Python 环境，没有安装 Docker。本次延续已有方式，降低新增基础设施的资源开销。

- Python 3.12，单进程 Uvicorn；代码由 root 持有，应用以 `agentflow` 系统账户运行。
- 使用同机已有网站的 `uv` 工具，先核对登记的 SHA256，再建立本应用独立环境，不修改其它网站的依赖。
- 安装 CPU 版 torch，保留真实 BGE 检索；没有使用测试 HashEmbedder 替代线上向量模型。
- 直接依赖版本与本地对齐，实际 Linux 完整依赖清单保存在发布证据中。SQLGlot 同时安装 `rs` 扩展。
- 限制 CPU 线程数为 1，服务 CPU 配额为一个核心；内存软限制 800 MiB、硬限制 1100 MiB。这是资源边界，不是并发能力承诺。
- 前端在本机构建，包内绑定完整 Git 提交及六个文件的 SHA256，服务器解包时核验提交、路径和内容摘要。
- HTTPS 复用现有 IP 证书和原续期任务，系统证书校验与浏览器均未跳过证书错误。

预热和两轮问答后的一个资源快照：服务约 790 MiB，整机可用内存约 1.0 GiB，磁盘剩余约 4.5 GB。没有做并发压力测试，不据此推断最大用户量。

## 💡 可迁移

1. **程序版本和业务状态分开。** 如同 ETL 的加工脚本可以回退，而交易流水不能被旧脚本包中的数据库覆盖。
2. **运行环境也属于发布契约。** 相同 Python 包版本不代表扩展组件相同。本次本地启用了 Rust 分词器，Linux 只装 Python 分词器时，一个错误定位测试就会失败。
3. **准备阶段应独立于活动版本。** 先测试、导入、造数并检核，再切换。失败只留下准备目录和日志，原服务继续工作。
4. **检核业务结果，不能只测端口。** 通过独立标准 SQL 对平真实模型产生的结果，类似用总分核对判断 ETL 是否加工正确。
5. **备份必须能够恢复。** 用 SQLite 在线备份取得一致性快照，再恢复到临时目录，检查完整性和表行数。

## 👨‍💻 代码与验收

实现集中在 `deploy/`：

- `release.py`：按完整 Git 提交准备、切换、验证及后续版本回退；首次发布没有上一版时拒绝假装完成回滚。
- `package_frontend.py`：从已提交的前端源码构建，生成逐文件摘要清单与发布包。
- `agentflow.service`、`nginx.conf`：应用账户、资源限制、只读代码、HTTPS 和 SSE 转发。
- `backup_history.py`、备份 service/timer：每日在线备份及隔离恢复校验，不自动删除历史备份。
- `requirements-server.txt`：与当前本地环境一致的服务器直接依赖；torch 单独从官方 CPU 索引安装。
- `tests/test_deploy.py`：六项发布边界与备份测试。

## ⚠️ 常见坑和边界

**SQLGlot 可选扩展。** Linux 初次回归为 1557 通过、1 项失败：引号未闭合的错误缺少行号。本地使用 `sqlglotrs==0.3.0`，服务器缺少该扩展。改为 `sqlglot[rs]==25.34.1` 后完整通过；没有降低测试要求。

**测试生成目录。** 全套测试会在源码的 `data/mock_mart/build` 创建 root 所有的模拟库目录。如果仅判断“目录存在就不创建链接”，正式导入会没有写权限。发布脚本现在先把该目录移入本次证据目录，再连接应用账户可写的持久目录，不授予应用修改源码的权限。

**泛化输入与真正的业务口径反问不同。** “查一下明细”被现有解析步骤识别为非完整查数需求，返回请补充对象、时间和字段的说明，状态为 `failed` 且没有 SQL；本次未修改该既有行为。日均统计区间的业务反问独立实测为 `need_clarify`，并给出年日均、月日均选项。

**公开演示的访问边界。** 当前应用没有账号隔离，访问者共享会话列表，模型调用使用同一服务器配置。演示站只放模拟资料，不输入真实客户信息或单位需求；如需私密使用，应另行增加访问控制。

**手机验收范围。** 浏览器 390 像素宽度能展示查询，但测得页面宽度约 396 像素，存在约 6 像素横向溢出。未修改现有界面适配，未验证 iPhone/微信实机及用户移动网络。

**首次发布的回退边界。** 后续版本具备基于登记上一版的代码切换流程，但本次首次发布没有上一版，因此未做真实线上回滚演练。会话结构如有后续变化，应单独评估迁移与兼容性。

**协作改动。** 用户确认另一个窗口正在清理旧项目约定；保留 `.hermes` 本地归档和停止跟踪的整理，不重新将其提交。该目录已按用户确认加入整体忽略，避免后续误入库。此文只记录部署及实测结果。
