# AgentFlow 元数据更新机制设计

> 日期: 2026-10-23 | 类别: design | 状态: 已定稿（6 件事按推荐拍板，选方案 A）；第 1 块向量复用已实现，见第 13 节
> 关联: [[2026-10-13_design_nl2sql专题库改造]]（第 4 节元数据入库）、[[2026-10-14_tech_nl2sql-元数据层]]、[[2026-10-19_tech_真实模型服务器部署]]；部署手册 `deploy/CLAUDE_CODE_SERVER_DEPLOYMENT.md`

只写设计，不改代码。文中出现的表名都是模拟库或虚构的。

## 0. 结论

推荐方案：

1. **结构全量重建，向量按文本复用。** 校验、脚本解析、血缘合并、关联推导、样例校验在真实库上只要 5 秒左右，而且前后牵连，局部重算容易算错，所以每次全量算。向量按「向量器 + 文本」从上一版复用，全部命中时连 BGE 都不加载。
2. **导入只产出候选版本，过了关卡才切成活动版本。** 每次导入写进 `build/versions/<版本号>/`，从不碰正在用的库。活动文件仍是 `build/metadata.db`：切换就是把选中版本的库复制过去再原子替换，服务、打包、发布脚本一行不用改。回退就是再切回上一版。
3. **五道关卡。** G1 清单校验（硬关卡，导入失败）→ G2 样例逐条静态校验 → G3 差异报告（有需确认项就不自动切换）→ G4 零成本回归（题库静态核对、召回重放，不调大模型）→ G5 评估回归（调 DeepSeek，上服务器前跑）。
4. **服务换版本：本机后台装好再换，服务器重启切换。** 本机读新库、建血缘图都在锁外做，期间照常用旧版本。服务器内存紧，沿用「新快照目录 + 重启」，给 `release.py` 补一个只换资料的切换和回退入口（现在只换资料没有入口）。
5. **追问时先核对上一轮的 SQL。** 以上一轮 SQL 为底之前，先用当前版本的校验器过一遍；表或字段没了就不以它为底，按完整需求重新生成并说明原因。不增加模型调用。

要你拍板的 6 件事在第 10 节。

## 1. 现在怎么导入、怎么加载

| 环节 | 现在的做法 | 缺口 |
|------|------------|------|
| 导入 | `python -m metadata.importer`：读清单 → 校验 → 解析脚本、合并血缘 → 推导关联 → 收样例 → 算向量 → 写库。每次全量，先写 `metadata.db.tmp` 再 `os.replace` | 导入成功就直接替换正式库，没有「先看看再上线」这一步；旧库被替换掉，回退不了 |
| 导入报告 | 写 `build/import_report.md` | 导入失败也覆盖它，正在用的那一版的报告就没了 |
| 向量 | 每次为全部字段和样例重算 | 只改了一条血缘也要加载 BGE。模拟库 105 条文本要 61 秒，几乎全是冷启动加载模型 |
| 真实资料 | `convert.py` 把标准格式文件直接写回 `data/real_mart/` | 上一版的输入被覆盖，事后说不清两版之间资料变了什么 |
| 服务加载 | `service.get_metadata` 每次比对库文件的修改时间，变了就重读、清掉流水线，下次重新装配 | 重读在 `_LOCK` 里做（真实库约 4.5 秒），这段时间会话历史、元数据接口都在等这把锁 |
| 服务器 | 资料按快照目录安装、不覆盖；随代码发布 `prepare --mart-dir` → `activate`；`rollback` 回到上一版代码和资料 | 同一个提交第二次 `prepare` 会被拒绝，只换资料必须先有新提交；对当前提交再 `activate` 会把「上一版」记录改成自己 |
| 会话 | 追问时带上一轮的 `prev_sql`、`prev_tables` | 表删了：② 跳过这张表，但 ④ ⑤ 仍以旧 SQL 为底，容易照旧用它。④ 的方案过不了「表要在候选里」的核对要重试，⑤ 的 SQL 被 ⑥ 报 R3、R4 最多再修两次，最多多调三次模型；改了名时模型不知道新名字，多半修不好 |

本机实测（2026-10-23，只读：不算向量、不写库）：

| 项 | 真实库 | 模拟库 |
|----|--------|--------|
| 规模 | 833 表、22,730 字段、12,693 血缘、1,714 关联、45 条加工语句、0 样例 | 14 表、93 字段、70 血缘、41 关联、7 条语句、12 样例 |
| 读清单并校验 | 0.8 秒 | 0.01 秒 |
| 补全（脚本、血缘、关联、样例） | 4.1 秒 | 0.6 秒 |
| 算向量（取自上次导入报告，含加载 BGE） | 26 秒 | 61 秒 |
| 读库进内存 + 建血缘图 | 2.7 + 1.8 秒 | 0.1 秒 |
| 读进内存后的占用（Python 分配，读完 / 峰值） | 117 / 199 MiB | 约 1 MiB |
| 字段向量文本 | 22,730 条，去重后 19,776 条 | 93 条 |
| 元数据库文件 | 约 64 MB | 0.5 MB |

结构部分便宜，贵的是向量，准确说是加载 BGE（机械盘上冷启动要几分钟）。

## 2. 资料会怎么变、各影响什么

| 变化 | 元数据库里跟着变的 | 要重算向量吗 | 容易出的事 | 哪道关卡发现 |
|------|--------------------|--------------|------------|--------------|
| 新增表 | 表、字段，可能新增血缘、关联 | 新表的字段要算 | 同名粒度键有「一张表被超过 150 张表关联就整张跳过」的闸，新增一张表可能让某张维表越线，它原有的这类关联整批消失 | G3 |
| 删表 | 表、字段、相关血缘和关联 | 不用 | 引用它的样例被拒收（只是警告）；题库标准答案失效；会话追问失效 | G2、G3、G4 |
| 字段增删 | 字段，相关血缘和关联 | 新字段要算 | 同上 | G2、G3、G4 |
| 表或字段改名 | 标准格式里没有「改名」，表现为删一个、加一个 | 新名字要算 | 血缘清单没跟着改：M09、M10 错误，导入失败；脚本没跟着改：只有 W06 警告，口径证据悄悄变少；样例没跟着改：W08 拒收，悄悄少一条 | G1、G2、G3 |
| 表中文名、字段中文名改了 | 表、字段 | 这些字段要重算 | 召回排名变化 | G3、G4 |
| 口径说明、码值说明改了 | 字段 | 不用（向量文本只有表中文名和字段中文名） | 证据变化 | G3 |
| 血缘清单变了 | 血缘，连带关联（键域是直取血缘的连通分量） | 不用 | 键域合并或拆开，关联成批增减 | G3 |
| 关联关系清单变了 | 关联 | 不用 | | G3 |
| 加工脚本更新 | 脚本片段、逐字段表达式、脚本补的血缘、脚本关联、血缘传递 | 不用 | 原来能结构化解析的语句解析不了（W06），过滤条件、关联条件从证据里消失 | G3 |
| 样例增减 | 样例 | 新样例要算 | 样例编号是「文件名#文件内位置」，中间删一条，后面的编号都变 | G2、G3 |

两点结论：

- **结构部分前后牵连。** 脚本解析要用全库的字段目录给字段限定表；键域是全部直取血缘的连通分量；同名粒度键的扇入闸、键域大小闸都按全库计数；样例要在整库上过静态校验。改一张表可能牵动远处的关联，局部重算很难算对。
- **改名最危险。** 标准格式里没有改名，脚本和样例没跟上时只报警告，导入照样成功。所以差异报告要专门找「疑似改名」。

## 3. 两条更新路径

### 3.1 模拟库

资料文件在 Git 里，改动本身就有逐行记录。

```
改 data/mock_mart 下的清单、scripts、examples
  → python -m metadata.importer data/mock_mart     导成候选版本，过 G1–G4，没有需确认项就自动切换
  → python -m data.mock_mart.build_mock            清单或脚本变了才需要（装配流水线时 ensure_built 也会按指纹自动重造）
  → python run_tests.py                            题库标准答案能在模拟库上执行
  → /run-eval                                      G5：和上一份报告比执行准确率、选表准确率
  → 提交资料文件和题库的相应改动
```

- 模拟库的回退以 Git 为准：`git revert` 后重新导入（向量全部命中，几秒）。版本回退只作应急，否则元数据、资料文件、DuckDB 三者对不上。
- Docker 镜像构建时照旧全量导入（`--no-index`）。第一次导入没有基线，直接成为活动版本。

### 3.2 真实库

```
本机：三样来源资料（只读）→ convert.py → data/real_mart 下的标准格式 + 转换报告
  → python -m metadata.importer data/real_mart     导成候选版本（向量复用），过 G1–G4
  → 看差异报告；有需确认项时 python -m metadata.versions promote <版本> --accept
  → 真实库 11 题静态评估（G5）
  → python deploy/dataset.py package               资料包带上版本清单
服务器（按部署手册另行执行）：install 成新快照目录 → switch-data 切换 → 验收；有问题 rollback-data
```

- 转换器仍写回原地。上一版的输入已归档在版本目录的 `inputs/` 里，转换写坏了可以从那里拿回来。
- 转换报告一并存进版本目录。它是来源资料的质量检核结果，差异报告里顺带对比「跳过多少条、配不上多少条」。
- 打包时核对：资料目录里现在的清单和脚本，摘要要和活动版本登记的输入一致，否则拒绝打包。部署手册里「不要仅修改 CSV 就沿用旧元数据库」这条，从靠人记变成脚本把关。

## 4. 全量还是增量

### 4.1 推荐：结构全量重建，向量按文本复用

**结构全量。** 理由见第 2 节：便宜（真实库约 5 秒）、前后牵连、全量的结果可复现（同样的输入加同样的代码得到同样的库），差异报告才可信。

**向量复用：**

- 复用的键是「向量器名称、维度、文本」。字段文本是「表中文名 字段中文名」，样例文本是「需求 口径」，与现在的 `field_text`、`example_text` 一致
- 从哪里取：活动版本的 `meta_vector` 表本来就存着每条向量的原文，直接按文本查；再加上最近一个候选版本（刚导过一次、还没切换又改了资料的情形）。不另建缓存文件
- 全部命中：不加载 BGE。只改血缘、关联、脚本、口径说明的更新，真实库导入从「加载模型的一到几分钟」降到十秒以内（实测 6.4 秒，见 13.1）
- 有没命中的：加载 BGE，只算没命中的；同样的文本只算一次（真实库 22,730 条字段文本去重后 19,776 条）
- 导入报告的「向量」一节写明：复用多少条、新算多少条、加载了模型没有
- `--reindex` 强制全部重算，模型升级或怀疑向量有问题时用

**两点注意：**

- 模型文件换了、名字没变时，旧向量和新向量会混在一起。对策：这次导入加载了模型，就从命中的文本里抽 32 条重算比对，余弦都在 0.9999 以上才复用，否则全部重算；版本清单记下模型快照号（模型缓存目录里的提交号）
- 复用的向量和全部重算的相比，个别分量的末位可能不同（一批文本长短不同，补齐方式不同），对排名几乎没有影响；要逐位复现时加 `--reindex`

### 4.2 备选：真正的增量导入

只解析改过的脚本、只重推受影响的关联、只校验受影响的样例。最多省 5 秒，却要逐条算清「改一处牵动哪些」，扇入闸、键域闸这类全局计数一漏就静默出错。不推荐。

### 4.3 备选：不复用，每次全算

最简单，不用改代码。代价是每次都要加载 BGE（机械盘上几分钟）。资料一个月只变一两次也能忍，但「改完重导、看差异、不对再改」这个循环会因为慢而没人愿意走。

### 4.4 导入失败不影响正在用的版本

- 导入只写新版本目录，从不写活动文件。任何一步失败（包括中途 Ctrl+C、断电），活动文件都没被碰过
- 导入报告写进版本目录，不再覆盖活动版本的报告
- 切换是一次原子替换（先写 `metadata.db.next` 再 `os.replace`），服务读到的要么全旧、要么全新。Windows 上活动文件被其它程序（比如 SQLite 查看工具）打开着时替换会失败，沿用现在的提示，旧文件不受影响
- 服务读新库失败时继续用旧的（5.4 节）
- 服务器上快照目录只读、不覆盖，切换失败自动恢复原配置（第 7 节）

## 5. 版本与切换

### 5.1 版本目录

```
data/<资料>/build/
├── versions/
│   └── 20261023-1105/            版本号：导入时间到分钟，同一分钟再导加 -2
│       ├── metadata.db           这一版的元数据库（含向量），写完只读
│       ├── version.json          版本清单
│       ├── import_report.md      导入报告
│       ├── diff_report.md        与基线版本的差异报告
│       └── inputs/               这一版的输入副本：四张清单、scripts、examples；真实库另带转换报告
├── current.json                  切换记录：活动版本、上一个活动版本、切换时间
├── metadata.db                   活动版本的副本：服务、打包、发布脚本、Docker 照旧读它
├── import_report.md              活动版本的导入报告副本
└── history.db                    会话历史，不分版本
```

`version.json` 记这些：

| 项 | 内容 |
|----|------|
| version_id、created_at | 版本号、导入时间 |
| status | failed（G1 没过或中途失败，只有报告）、candidate、active、retired |
| baseline | 导入时的活动版本，差异报告和它比 |
| inputs | 每个输入文件的 SHA256 和合计摘要 |
| code | 导入时的 Git 提交，以及有没有未提交的改动 |
| embedder | 向量器名称、维度、模型快照号；复用、新算的条数 |
| counts | 与 `MetadataStore.counts()` 相同的各类数量 |
| gates | G1–G5 各自的结果（G5 由评估脚本回填） |
| confirm_items | 需确认项清单；accepted 记有没有人确认过、什么时候 |

版本号也写进元数据库的 `meta_info`（`version_id`），服务读库时就知道自己用的是哪一版，`/health` 报出来。

- **资料没变就不出新版本**：输入合计摘要、代码提交、向量器都和活动版本相同时，提示「资料和代码都没变」，不生成新版本（代码有未提交改动、或加 `--force` 时照样生成）。做法和模拟库造数的输入指纹一样
- **旧库的接手**：第一次用新导入器时，把现有的 `build/metadata.db` 登记成 `versions/legacy-<修改时间>/`，作为基线和向量来源，也能回退到它

### 5.2 切换和回退

```
python -m metadata.importer [资料目录] [--no-index] [--reindex] [--no-promote] [--force]
python -m metadata.versions list                  # 以下都可以加 --mart 资料目录，默认 MART_DIR
python -m metadata.versions diff <版本A> <版本B>
python -m metadata.versions promote <版本> [--accept]
python -m metadata.versions rollback
python -m metadata.versions prune [--keep 5] [--yes]
```

- **切换**：把版本的 `metadata.db` 复制成 `build/metadata.db.next`，再原子替换 `build/metadata.db`，然后更新 `current.json`。以活动文件 `meta_info` 里的版本号为准，`current.json` 只是切换记录，两者不一致时以库为准并修正记录
- **为什么复制而不是改指针**：读活动文件的有服务、打包脚本、发布脚本的资料契约、Docker 和测试。复制一份（真实库 64 MB，一两秒）换来这些地方一行不改，服务器上的快照格式也不变。不用硬链接：活动文件万一被人改了，会连带改坏归档
- **回退**：`rollback` 切回 `current.json` 记的上一个活动版本；也可以 `promote` 任何一个 candidate 或 retired 的版本
- **自动切换**：G1–G4 都没有需确认项就自动切换；有需确认项就停在候选，打印报告位置，等 `promote --accept`。`--no-promote` 只导成候选
- **并发**：切换时独占创建 `build/.promote.lock`，防止两个切换同时进行
- **保留**：最近 5 个版本，加上活动版本和上一个活动版本；失败的导入记录只留最近 3 次。`prune` 先列出要删的，加 `--yes` 才删。真实库每版约 70 MB，保留 7 份约 0.5 GB

### 5.3 备选：指针文件

不复制，读库的地方都先读 `current.json` 再去版本目录找库。省掉复制，但服务、打包、资料契约、Docker、测试都要改，服务器的快照目录也要换格式。不推荐。

### 5.4 正在运行的服务怎么换上新版本

**本机（开发、演示）：后台装好再换。** 和「装配不占元数据的锁」是同一个原则：

1. 仍然每次取元数据时看一眼活动文件；版本键从「修改时间」改成「路径、修改时间、大小」
2. 发现变了：起一个后台线程读新库、建血缘图（用单独的换版本锁保证同一时间只有一个），不占 `_LOCK`；这期间所有请求照常拿旧版本，会话历史、元数据接口不用等。进程里还没有任何版本时（刚启动）照旧同步读
3. 读好后在 `_LOCK` 里换掉引用（瞬间），清掉流水线缓存；可以顺手在后台线程里把流水线也装配好，切换后的第一个查询不用等
4. 读失败（文件坏了、旧格式）：继续用旧版本，记日志，`/health` 报出原因；同一个版本键不反复重试
5. 正在跑的查询拿着自己那份元数据跑完，一次查询里不会前后版本混用（现在就是这样）
6. 换的那几秒内存里有新旧两份，真实库多约 200 MiB 峰值，本机可以接受

`/health` 加 `metadata_version`。

**服务器：重启切换，不热切换。** 服务器内存约 2 GB、和其它服务共用，本应用约 800 MiB、硬限制 1100 MiB，热切换多出的约 200 MiB 峰值贴着上限。快照目录本来就按目录分版本，切换就是改 `MART_DIR` 再重启，和现在一样，见第 7 节。

## 6. 差异报告与关卡

### 6.1 关卡在哪一步

| 关卡 | 在哪一步 | 查什么 | 不过时 | 调大模型吗 |
|------|----------|--------|--------|------------|
| G1 清单校验 | 导入第一步 | `metadata/checks` 的 M01–M14 | 导入失败，只留导入记录 | 否 |
| G2 样例静态校验 | 补全阶段，逐条 | 每条样例在新版本上过静态校验 | 只拒收这一条（W08）。上一版收下、这一版拒收的记为「失效样例」，是需确认项 | 否 |
| G3 差异审核 | 写完候选版本后 | 与基线版本逐项比较（6.2） | 有需确认项就不自动切换 | 否 |
| G4 零成本回归 | 切换前 | 见下 | 变差的记为需确认项 | 否 |
| G5 评估回归 | 本机切换后，上服务器或提交前 | 模拟库 `/run-eval`，真实库 11 题静态评估，都和上一份报告比 | 不发布、不提交，本机回退 | 是（现有的评估流程，不是产品里新增的调用） |

G4 有三项：

- **题库静态核对**：每道题的标准 SQL 和登记的其它正确答案，在新版本上静态校验 0 错误，标准用表、关键字段都还在。真实库的题只登记了标准用表的，查表在不在。秒级，不加载模型
- **召回重放**：最近一次评估的逐题记录里存着 ① 的完整输出。拿它在新旧两个版本上各跑一遍 ②（C 组配置，从第 0 层起，不带上溯和追问），比标准用表进没进候选、排第几。两边都是现跑的，差别只来自元数据。不调大模型，但要用 BGE 算检索词的向量：这次导入已经加载了模型就顺带跑，否则加 `--replay` 才跑
- **会话影响**：本机会话库里，有多少个会话的上一轮用到了被删的表。只报数，处理办法见第 8 节

### 6.2 差异报告怎么比

比两个元数据库（候选和基线），不比原始文件：比的是规范化、补全之后的结果，脚本补出来的血缘、推导出的关联的变化都看得见。

| 对象 | 按什么认同一个 | 比什么 |
|------|----------------|--------|
| 表 | 表标识 | 层级、表类型、粒度字段、数据日期字段、中文名、说明 |
| 字段 | 表标识 + 字段名 | 中文名、类型、主键、口径说明、码值 |
| 血缘 | 目标表、目标字段、源表、源字段 | 加工逻辑、来源（清单或脚本补的） |
| 关联 | 左表、左字段、右表、右字段 | 对应关系、来源 |
| 加工脚本 | 文件名 + 目标表 | 原文摘要、能否结构化解析 |
| 样例 | 需求和 SQL 的内容摘要（不按编号） | 收下还是拒收、拒收原因 |

- **疑似改名**：同一张表里一删一增，中文名相同（或类型和位置相同），记为疑似字段改名；一张表删、一张表增，中文名相同且字段重合八成以上，记为疑似表改名。只提示，不自动当改名处理
- **变化来自资料还是代码**：版本清单记了输入摘要和代码提交。两者都变时，差异分不清是谁引起的；需要分开看时，用新代码把上一版的输入（在 `inputs/` 里）重导一次，得到「只有代码变了」的基线

报告的章节：

1. 概要：版本号、基线、哪些输入文件变了、代码变没变、数量对比、向量复用情况
2. 需确认项（放最前面）
3. 表：新增、删除、属性变化、疑似改名
4. 字段：按表分组
5. 血缘、关联：按目标表汇总条数，变化多的在前，每张表只列前几条
6. 加工脚本：改了哪些文件，解析成败的变化
7. 样例：新增、删除、修改、失效（带拒收原因）
8. 影响面：G4 三项的结果

真实库的差异报告里有真实表名，只放在 `data/real_mart/build/versions/` 下（整个 `data/real_mart/` 不入库），不进资料包，不贴进笔记和提交说明。

### 6.3 需确认项（默认阈值）

- 删了表或字段（任何一个）
- 疑似改名
- 失效样例
- 题库静态核对不过，或召回重放里标准用表掉出候选
- 表、字段、血缘、关联、能结构化解析的语句，任何一项比基线少 5% 以上；或表、字段比基线多 20% 以上（来源资料格式变了、转换重复的信号）
- 基线有向量、这一版没有或不全（`--no-index`，或向量没算完）

## 7. 线上发布

在部署手册现有做法上改三处，其余不变。以下都是实施时的步骤，这次不碰服务器。

| 步骤 | 现在 | 改成 |
|------|------|------|
| 打包 | `dataset.py package` 打清单、脚本和元数据库 | 另带 `version.json`（只有版本号、数量、摘要、关卡结果，没有真实表名）；核对输入摘要与活动版本一致；快照名用版本号，例如 `real-20261023-1105` |
| 安装 | `dataset.py install --id real-<批次>`，不覆盖 | 不变；允许的文件加 `version.json`（以后真实库有样例时再加 `examples/*.sql`） |
| 切换 | 只能随代码发布：`prepare --mart-dir` → `activate` | 新增 `release.py <当前SHA> switch-data --mart-dir <新快照>` |
| 验收 | `/health` 的数量等于资料契约 | 契约加 `version_id`，数量相同、内容不同的两版也分得出 |
| 回退 | `rollback` 代码和资料一起回 | 新增 `rollback-data`，只切回上一份资料；`rollback` 不变 |

`switch-data` 做的事（复用 `prepare`、`activate` 里已有的检查）：

1. 核对新快照：在 datasets 目录下，完整性检查、数量、BGE 向量齐全，`version_id` 与 `version.json` 一致；站点访问保护存在；`EXECUTOR` 仍是 `none`
2. 在线备份会话库
3. 把当前的资料配置记进 `deployments/<SHA>/data-switch-<时间>.json`，`rollback-data` 用它
4. 改运行配置里的 `MART_DIR`，重启本应用，按新契约做健康检查
5. 失败就恢复原配置并重启
6. 代码指针和 `previous.json` 都不动，所以代码回退和资料回退互不干扰

其它约定：

- **代码和资料都要更新时分两步**：先发代码（资料不变），验收后再 `switch-data`。出了问题知道是哪一步
- **会话库**：`history-real.db` 跨资料版本共用（现状），不随资料回退。资料换了以后旧会话的追问怎么办，见第 8 节
- **重启会打断正在跑的查询**（没跑完的这一轮不会落库）：切换安排在没人用的时候。用户少，先不做排空
- **旧快照不自动删**（现状）。人工清理时至少留当前和上一份
- **备选**：不加 `switch-data`，换资料继续随代码发布。不用改发布脚本，但每次都要一个新提交、一次完整的 `prepare`（建环境、装依赖、跑全部测试），而且同一个提交只能换一次资料

## 8. 对会话历史的影响

### 8.1 推荐：以上一轮 SQL 为底之前，先在当前版本上核对

放在流水线里，`/nl2sql/*` 和会话接口两个入口都受益。① 判断本轮是追问、要以上一轮 SQL 为底时，在 ② 之前先用当前版本的校验器把上一轮 SQL 过一遍（纯代码，毫秒级）：

- 0 错误：照旧，以它为底，带上一轮的表
- 有错误（典型是 R3 表不存在、R4 字段不存在）：这一轮不以它为底、不带上一轮的表，按 ① 合并好的完整需求重新召回、生成。结果里加一条说明：「元数据已更新，上一轮用到的 ×× 不在当前版本里，这一轮按完整需求重新生成」

模型调用和普通的一轮一样是三次，比现在可能多出的重试和修正（最多三次）还少。

另外：

- 每一轮的结果记下生成时的元数据版本号，放进存下的结果 JSON 里，会话表结构不用改；旧轮次没有这一项就当未知。界面可以在 SQL 旁边标「生成于版本 ××」（可选）
- 改名的情形不自动把旧名换成新名：疑似改名只是推测，换错了比重新生成更难发现

### 8.2 备选

| 做法 | 取舍 |
|------|------|
| 不处理，靠 ④ 的核对和 ⑥ 修正回路兜底 | 不用改代码；最多多花三次模型调用，改名时多半修不好，用户看到的是莫名其妙的失败 |
| 会话绑定版本（会话一直用它开始时的版本） | 内存里要同时放多个版本（真实库每份一百多 MiB，服务器上限 1100 MiB），而且用户本来就想用新资料。不推荐 |
| 换版本时清空所有会话的上下文 | 简单，但没受影响的会话也丢了追问 |

## 9. 方案对比与实施顺序

### 9.1 三个整体方案

| | A（推荐） | B 最小改动 | C 重 |
|---|---|---|---|

| 回退 | 任意保留的版本 | 只能回上一版 | 任意版本 |

### 9.2 A 的实施顺序（各块可以单独做、单独验收）

1. 向量复用：`metadata/index.py`、`metadata/importer.py`。单做也有收益

4. 服务换版本不占锁：`nl2sql/service.py`
5. 追问底稿核对、结果记版本号：`nl2sql/workflow.py`、`nl2sql/schemas.py`

测试照现有约定，不调模型、不加载 BGE：向量复用用一个会数调用次数的假向量器；版本切换、回退、保留在临时目录里测；差异报告用改过的小资料测；换版本不占锁用多线程测「换的期间会话接口不用等」；追问核对用 `ScriptedLLM` 测「底稿失效时不以它为底、调用次数不变」。第 5 块改了流水线，按约定跑一次 `/run-eval`。

## 11. 概念与 ETL 类比

| 概念 | 类比 |
|------|------|
| 候选版本 → 活动版本 | 数据先装进临时表，检核通过再做表交换 |
| 结构全量、向量复用 | 维表每天全量重算，但耗时的衍生字段按内容哈希缓存，内容没变就不重算 |
| 差异报告 | 新旧两版数据字典做全量比对（MINUS），出变更清单 |
| 需确认项 | 数据质量检核里的预警级规则：不让作业失败，但要人确认后才放行 |
| 召回重放 | 拿上次的入参，在新版本上重跑作业的前半段，比对输出 |
| 后台装好再换 | 新数据装进影子表，装完再把视图指过去，查询不停 |
| 只换资料的切换 | 只切数据源配置，不重新部署程序 |
| 追问底稿核对 | 跑增量作业前先核对依赖表还在不在，不在就改跑全量 |

## 12. 风险

| 风险 | 应对 |
|------|------|
| 复用的向量和模型版本不一致 | 加载了模型时抽样重算比对；版本清单记模型快照号；`--reindex` |
| 版本目录占空间 | 保留策略加 `prune` |
| 差异报告里的真实表名外泄 | 只放在 `data/real_mart/build/` 下；资料包只带不含表名的 `version.json`；保密钩子照常查入库文件 |
| 本机热切换的内存峰值 | 只在本机热切换；服务器重启切换 |
| 服务器重启打断正在跑的查询 | 空闲时段切换 |
| 资料和代码同时变，差异说不清来源 | 用新代码重导上一版的输入做基线 |
| 模拟库只回退了版本、没回退文件 | 模拟库以 Git 为准，版本回退只作应急 |
