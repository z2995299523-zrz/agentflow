# 主流 NL2SQL 方案与表召回准确率优化

> 调研日期：2026-10-28。依据本轮可访问的官方文档、原始论文和本地代码。
> 本次是方案调研和代码只读核对；没有修改流水线、提示词、模型配置或真实资料，没有重新调用模型评估，也没有部署。
> 文中的优先级、实验设计和目标均为对 AgentFlow 的建议，不是已经实现的效果；论文和厂商结果不等于本项目收益。

## 📦 目标：把“找到相关表”拆成可验证的几个问题

用户目标是提高自然语言问题与召回表的匹配准确率。对应技术问题叫 schema linking，即把问题中的业务对象、指标、维度、条件与表、字段、关联路径对齐。

用 ETL 开发类比：接到“上个月各机构贷款发生额”需求，要先区分发生额和月末余额，确认机构归属和时间口径，再选源表及 JOIN 键。表名或字段里出现“贷款”，只能证明有关系，不能证明适合回答需求。

需要分别衡量：

1. **问题理解**：对象、指标、时间、条件、排除范围有没有理解对。
2. **候选覆盖**：一套能回答问题的表是否全部进入候选，包含必要的桥表。
3. **候选纯度**：带入多少无关或口径相近但错误的表。
4. **最终选表**：模型最终选出的表集合、粒度、关联与指标口径是否正确。

建议主线是：补充可信业务语义，保留当前混合召回骨架，增加表级检索和表组判断，先用分阶段指标确认收益，再考虑换向量模型。

## 📖 讲透：主流方案在解决什么问题

下面按实现路线整理代表方案，不是市场占有率排名。工业产品、框架组件与研究方法的成熟度不同，不能把近期论文写成已被广泛生产采用的方案。

### 工业产品与工程框架

| 代表方案 | 已核对的核心机制 | 对问题与表匹配的帮助 | 对 AgentFlow 的适用边界 |
|---|---|---|---|
| Wren AI / MDL | 用模型、字段、计算字段、关系和视图表达业务语义；业务规则补标准表与适用场景 | 用户的业务概念先对应业务模型，再映射到物理表 | 借鉴表语义卡和可信关联；语义仍需业务审阅，不能靠 DDL 自动推断 |
| Snowflake Cortex Analyst | Semantic Views 定义维度、指标与关系；Verified Queries 提供已验证问答 SQL；支持值检索 | 约束同名指标的解释，并把自然语言中的实体值对齐到列与字面值 | 借鉴语义元数据、已验证样例和枚举映射；不是可直接安装到 PostgreSQL 的替换模块 |
| Databricks Genie Agents（原 Genie Spaces） | 精选主题表，提供表列说明、SQL expressions、示例 SQL、值匹配与明确澄清规则 | 明确业务概念怎样落到字段、过滤与计算表达式，减少同名对象混淆 | 借鉴结构化指标定义和错题驱动的维护；其产品表数限制不能照搬成我们的 TopK |
| Vanna 2.0 | 相似问题检索成功 SQL 与工具使用记忆，再利用上下文和工具处理问题 | 历史正确用表可作为独立候选来源 | 给现有样例增加业务审核与版本、粒度、口径兼容检查；SQL 能运行不代表口径正确 |
| AWS + Cisco 工程实践 | 先确定数据域，缩小结构范围，补域内业务规则、示例和实体 ID 解析 | 降低跨域同名表干扰，让问题在更合理的候选范围内匹配 | 做多域软路由，低置信时扩大范围；这项兜底是本项目建议，避免路由错误直接漏表 |
| LlamaIndex Text-to-SQL | 为表结构建立 TableIndex，按问题取表；还能提供行/列值检索器 | 展示表级召回、表说明与值证据的组合方式 | 借鉴独立表级索引；框架提供接口，不会自动补出正确业务口径 |

### 对召回特别有用的研究方法

| 方法 | 核心思想 | 对 AgentFlow 的启发 |
|---|---|---|
| CHESS | 实体值和上下文检索、schema 选择，与后续 SQL 生成/验证配合 | 问题中的值也是找字段和表的线索；只检索名称会漏掉这类证据 |
| RSL-SQL | 双向 schema linking，关注过早裁剪产生的漏项风险 | 重排后要检查是否仍覆盖全部关键需求；保留补召回路径 |
| LinkAlign，EMNLP 2025 | 分开定位数据库与库内表列对齐，根据未覆盖信息多轮补召回 | 复用已有缺失要素补召回机制，并检查问题改写是否偏离原需求 |
| Reverse Engineering 表获取，EMNLP Findings 2025 | 从表结构生成可回答问题，辅助召回与重排 | 为业务卡增加经过审查的典型问法；轻量应用不等于复现论文训练流程 |
| Rethinking Schema Linking，EACL 2026 Findings | 表先行再选列、列先行再归表，两条路线互补，并结合问题分解 | 在现有字段召回之外增加表级业务卡检索；两路合并后再判口径 |
| CORE-T，2026 年版本 | 离线生成用途元数据和表兼容缓存；高召回候选后选择可共同使用的表集合，再补回兼容表 | 多表题要判断表集合能否共同回答问题；可复用已有关联图，而不是只给单表排分 |
| Finding the Right Tables and Columns，2026-07 预印本 | 将表/列召回作为独立任务评估，研究语料适配的向量模型 | 通用检索榜分不能代替 schema 召回评测；先看本地难题，再决定换模型或训练 |

原始资料：[CHESS](https://arxiv.org/abs/2405.16755)、[RSL-SQL](https://arxiv.org/abs/2411.00073)、[双向检索论文](https://aclanthology.org/2026.findings-eacl.236/)、[CORE-T](https://arxiv.org/abs/2601.13111)、[表列检索专项评测](https://arxiv.org/abs/2607.13311)。

另两篇的正式来源：[LinkAlign](https://aclanthology.org/2025.emnlp-main.51/)、[Reverse Engineering 表获取](https://aclanthology.org/2025.findings-emnlp.425/)。

CORE-T 的官方摘要写明 2026-08-30 修订版本及 EMNLP Main 2026 接收状态；其研究是大表集合中的检索，并包含样例值等证据。AgentFlow 在只有元数据时可借鉴表组选择结构，但不能声称复现完整方法。上述论文的基准、数据库规模、模型、上下文和执行环境不同，不做跨论文准确率排名。

## 🔧 选型：先看当前项目真正缺什么

### 已有骨架，不重复建设

当前已经有结构化需求解析、关键词和向量双路召回、RRF 融合、血缘和关联路径、历史 SQL 样例、缺失要素补召回，以及生成前的计划裁剪。

关键词检索实际是中文二元组/英文词覆盖率，不是 BM25。每个要素两路各取前 30 个字段，RRF 参数为 60；字段分数按表聚合，指标/维度/过滤的角色权重是 1.0/0.7/0.5。标准候选最多 8 张，此外还会补非标准表、样例表、上溯表、上一轮表及关联中间表，所以最终候选数不一定是 8。

|---|---:|---:|---:|
| 最终候选完整覆盖正确表集合 | 37/37，100.0% | 37/37，100.0% | 37/37，100.0% |

### 建议的实施顺序

| 顺序 | 改进 | 为什么优先 | 如何验证 |
|---|---|---|---|
| P0 | 固定题集和分阶段埋点 | 先区分解析丢词、初始漏表、重排误删、最后选错 | 同时记初始、扩展、重排、最终四个阶段；重放时固定元数据和解析结果 |
| P1 | 短业务语义卡 + 完整需求约束 | 表名字段名不足以区分粒度、期间、含税/不含税、余额/发生额等口径 | 现有文本与审核过的短语义卡消融；看混淆题和多表题表现 |
| P2 | 表级和字段级双向混合召回 | 现有只有字段级向量再归表，补充按业务用途找表的能力 | 比较字段路、表路、合并三组的完整覆盖、纯度和候选数 |
| P3 | 表及表组重排 | 让完整问题与候选业务语义交互，并检查一套表是否覆盖需求 | 记录重排收益和必要表误删率；保护桥表和必需字段 |
| P4 | 已验证样例门控 | 相似问法也可能具有不同粒度、时间或过滤口径 | 对照无样例、现有样例、按口径兼容过滤后的样例 |
| P5 | 受控枚举/实体映射、跨域兜底、低置信反问 | 补问题中的值与字段映射，避免有歧义仍强行选表 | 值映射准确率、跨域完整覆盖率、必要反问正确率 |

可尝试的重排器包括 `bge-reranker-v2-m3` 和 `Qwen3-Reranker-0.6B`；两者均有官方多语言/重排说明。先固定候选集比较“无重排、专用重排器、DeepSeek 结构化表组选择”，同时测本机和部署机器的延迟、内存及成本，不能用通用检索榜单推断中文专题库一定更准。[BGE 官方说明](https://bge-model.com/bge/bge_reranker_v2.html)、[Qwen 官方说明](https://qwenlm.github.io/blog/qwen3-embedding/)。

若初始召回已足够完整，可先验证 P3，而不必等 P2 全面完成；若漏表主要来自解析，先修需求保真。上述优先级应服从错题分布。

## 💡 可迁移：把数据仓库知识写成机器能核对的证据

### 业务语义卡比堆加工原文更适合检索

下面仅是虚构的结构示例，不代表当前真实库定义：

| 语义项目 | 示例内容 |
|---|---|
| 业务对象 | 对公贷款账户 |
| 记录粒度 | 账户 × 统计日期 |
| 可回答问题 | 指定日期贷款余额、按当日归属机构汇总余额 |
| 不适用问题 | 期间贷款发放额、逐笔还款明细 |
| 指标 | 日终余额，币种与折算规则需另有定义 |
| 时间 | 统计日期代表快照时点，不是交易发生时间 |
| 维度 | 机构、产品、客户；是否直接具备以字段清单为准 |
| 关联 | 经确认的客户键、机构键与关系基数 |
| 术语 | 只登记已确认的内部缩写、历史别名和业务叫法 |
| 依据 | 模型说明或加工规则出处、审核状态、元数据版本 |

这对应 ETL 的“源表说明＋粒度定义＋指标口径＋关联约束”。未知项应保留未知，不能由模型凭表名填成确定事实。表的正向业务用途用于召回；排除项和约束单独保留给重排与校验，避免把“不支持发放额”中的“发放额”反而当作强召回信号。

### 表之间能 JOIN，不等于 JOIN 后业务正确

当前项目已能找路径和补中间表。下一步要把主外键/粒度键、关系基数、时间对齐、汇总层级和重复累计风险纳入表组判断；优先使用经确认的关联边。加工血缘说明数据来自哪里，查询关联说明数据怎样能合起来，二者不能混用。

### 样例和别名需要质量门槛

样例至少带问题、SQL、表集合、关键字段、口径、粒度、适用日期和元数据版本。自动静态校验通过只能说明结构规则满足；“标准答案”还要经过业务确认。

同义词优先补内部术语、缩写和历史名称，不盲目扩展一般近义词。Snowflake 当前最佳实践对通用 synonyms 的收益持保留意见，Databricks 则仍建议字段 synonyms，说明收益取决于模型、检索器和场景，需要本地消融。[Snowflake 最佳实践](https://www.snowflake.com/en/developers/guides/best-practices-semantic-views-cortex-analyst/)、[Databricks 最佳实践](https://docs.databricks.com/aws/en/genie-agents/best-practices)。

### 建议建立的数字评估

先从 100–200 道经过审核的问题起步，覆盖单表、多表、同名异义、时间口径、枚举过滤、跨层/跨域、连续追问、需要反问等类型。这个题量是实施建议，不是现有已完成资产。来自真实资料的题集留在既有私有资料范围；入库演示只用虚构或充分脱敏的名称。

| 模块 | 指标与读法 |
|---|---|
| 问题解析 | 对象/指标/维度/时间/过滤/口径要素准确率；对比人工解析与模型解析后的召回 |
| 表字段候选 | Table Recall@5/@8/@10、Precision@5/@8/@10；K 超过可用表数时报告实际候选数 |
| 多表覆盖 | CompleteSetHit@K：前 K 张里完整包含任意一套合法表集合的题目比例 |
| 排序 | best_group_rank：凑齐一套合法表集合所需的最小候选深度；单表题可加 MRR |
| 重排 | 重排前后纯度、完整覆盖差值、必要表误删率、平均候选数 |
| 关联补全 | 必要桥表/路径覆盖率、补入噪声表数量；分清查询 JOIN 和加工血缘 |
| 样例门控 | 引入正确/错误表的比例、合法表组覆盖和最终结果的增减 |
| 实体值映射 | 字段—值配对准确率，无法确认值时的澄清正确率 |
| 最终 SQL | 表集合精确匹配、包含率、关键字段准确率、执行结果或业务人工验收 |
| 成本 | 各阶段 P50/P95、LLM 调用次数、token、内存；同时统计反问率与必要性 |

对单一合法表集合 G 与实际候选 C，Recall = |G∩C|/|G|，Precision = |G∩C|/|C|。有多套合法答案时要按完整的一套一致评估，可用最高 F1 对应的合法组并保留各组分数；不能把互斥方案合并成一个大 gold，也不能为不同指标各挑一套有利答案。桥表应在相应合法组中标注角色。

初始第 0 层与扩展后的评估应分开：某题需要上溯才能回答时，可以衡量第 0 层的直接候选/上溯种子质量，但不能把第 0 层未出现上游明细表直接解释成整个系统漏表。

实验组建议按顺序增加一个变量：现有实现 → 业务语义卡 → 表路融合 → 表组重排 → 样例门控。另做单独的 embedding 与关键词/BM25 对照。冻结元数据、题目、解析输出和候选预算；涉及生成模型的方案至少重复运行以观察波动。

另外固定三种诊断对照：当前召回、预算允许时的全量 schema、人工给定的正确 schema。人工 schema 是诊断条件，不能计入正常成绩：如果人工给定正确表列后仍答错，需检查规划、口径或生成；如果只在当前召回下出错，才更支持召回/证据呈现是瓶颈。也可用人工解析对比模型解析，隔离输入要素遗漏。[Spider 2.0 官方说明](https://spider2-sql.github.io/)同样要求明确标注使用人工正确表的 oracle 条件。

验收先保持完整覆盖和最终正确率不下降，再争取候选纯度提高、上下文减少。具体提升多少、容许多少延迟，待基线和硬件测量后确定；本次没有证据承诺固定百分点收益。

## ⚠️ 常见坑

1. **只扩大 TopK。** 全部表都返回能让覆盖率很好看，但会掩盖排序和噪声问题。
2. **把向量相似度或 RRF 分数当正确概率。** 这些是相关性/排名信号，需要独立校准才能谈置信度。
3. **用一次最终 SQL 错误归因于召回。** 可能是解析遗漏、错误表组、口径误解或生成错误，需要中间记录定位。
4. **重排只看单表。** 桥表和维表可能与原问题字面不相似，却是完整回答所必需。
5. **业务域硬切、字段裁剪太早。** 保留多域与缺失要素补召回，裁剪前核对需求覆盖。
6. **把长加工原文全部加入 embedding。** 当前项目已记录这会引入噪声；新增的是审核后的业务语义。
7. **把历史 SQL 执行成功当成业务真值。** 必须核对口径、粒度和当前元数据版本。
8. **训练题与测试题只是换个问法。** 同源问题按业务模板分组切分，检查样例库与冻结测试集的近似泄漏。
9. **直接比较 BIRD、Spider、Spider 2.0 与本地报告的分数。** 数据规模、模型、是否执行、任务和分母不同。
10. **把通用大模型或向量模型升级当作确定收益。** 先固定输入证据和评估；本轮尚未验证任何模型替换。
