## 📦 目标

老手拿到候选表之后，不会直接写 SQL：先翻每张表的字段，顺着血缘看指标是怎么加工出来的，再核对几个「看着差不多」的字段是不是同一个口径，最后查这几张表怎么连。证据组装就是把这套动作做成确定性代码，模型只读结论、不自己推。

| 交付物 | 文件 | 作用 |
|--------|------|------|
| 证据组装 | `nl2sql/evidence.py` | 候选表、加工链路、同源对比、上下游、关联路径、上溯选项、样例 |
| 输出工具 | `nl2sql/output.py` | SQL 排版、校验与执行结果摘要、假设合并、两条失败提示语 |
| 召回扩展 | `nl2sql/retriever.py` | 全部层级一起排名（A 组）；多条语句写同一字段的排除规则 |
| 结构关联 | `metadata/relations.py` | `structural_relations`：只用表结构推得出的关联 |

数字指标：全量 1010 项测试通过，本篇新增 147 项。模拟题 35 道，标准用表全部进证据（A、B、C 三组都是 35/35）；35 道题的证据组装合计 C 组约 0.25 秒、A 组约 0.1 秒。6 个验收锚点全部成立；换哈希种子开两个子进程，35 道题的证据逐字相同。

## 📖 讲透

**1. 候选表。** 按召回的先后列出每张表的全部字段。说明按角色截断：命中的字段、粒度字段、数据日期字段、主键留 200 字，其余字段 60 字，码值一律 200 字，超出的用「…」。类比数据字典摘录：重点字段写全，普通字段一句话。

**2. 加工链路。** 命中指标检索词的字段（最多 12 个，按得分排），沿血缘往上走 3 跳。同一个目标字段的几个来源并成一步，每步带脚本表达式、过滤条件、关联条件。带条件是为了上溯到下层查数时能还原加工时的过滤，否则查出来的数对不上。来源字段不在字段清单里的标进 `unknown_sources`，SQL 里不能引用。

**3. 同源对比。** 同一个指标命中的字段两两比，判三类：`derived_from`（一个由另一个加工而来，方向看血缘不看得分）、`same_source_diff`（同源、口径不同）、`same_source_same`。类比两张报表都有「存款余额」，先看它们是不是取自同一批数，再看过滤条件一不一致。口径不同的字段即使没排进名额，也补上链路。

**4. 关联路径。** 候选表两两求最短路径，直连优先，最多经过一张中间表。中间表不在候选里就补进证据（`reason=join`，最多 3 张）：④ 的核对只认证据里的表，不补进去，模型用不了这条路径。

**5. 上溯选项。** 第 0 层列整合层的上游表，第 1 层列贴源层的，第 2 层不再列；维表不往上找。

**6. A 组的关联要重新推导。** A 组「仅模型结构」不能看到脚本推出的关联。库里每种映射只留优先级最高的来源，客户汇总表到客户维表按客户号的关联，库里记的是血缘传递（`lineage`），结构上它其实是同名粒度键（`grain_key`）。所以不能从库里按来源筛，要用 `structural_relations` 重新推一遍，建成只有表、字段、关联的 `structure_store`。

## 🔧 选型

| 决策 | 选了什么 | 没选什么 | 原因 |
|------|----------|----------|------|
| A 组的关联 | 重新推导，复用 `_Deriver` 的同名粒度键规则和上限 | 从库里按来源过滤 | 过滤会漏掉被顶替的映射；另写一套规则会和导入时漂移 |
| 同源判定顺序 | 先看上下游，再看口径 | 一律按口径判 | 机构表的字段由客户表加工而来，两者共同上游里就含对方，先判口径会把它们说成「同源不同口径」 |
| 中间表 | 补进证据 | 只在路径里提一句 | ④ 只能用证据里的表 |
| 说明截断 | 按角色分级 | 统一截断 | 命中字段的说明常常就是口径 |
| 上游链路 | 一份证据内缓存，每个字段只走一遍 | 每次比较重新走 | 一个字段要和另外 5 个各比一次，加上自己的链路，不缓存要走 6 遍，真实库上扇出更大 |
| 排序 | 得分、表先后、字段名，全序 | 听凭遍历顺序 | 同样的输入必然得到同样的证据 |
| 字段排除 | 多条语句写同一字段，全是空值或加工时间才排除 | 只看第一条 | 第一条可能只是占位的空值，后面才是真加工 |

## 💡 可迁移

**1. 事实由代码算，判断留给模型。** 血缘、对比、路径都是确定的图查询；让模型自己从字段名猜，既慢又不稳。

**2. 对照实验关掉一类证据，要连带关掉它的泄漏。** 只去掉血缘还不够，关联关系里也藏着脚本的信息，A 组才是真的「盲测」。

**3. 截断要说出来。** 限额是为了控制长度，超限不说，模型会把「没列出」当成「没有」。

## 👨‍💻 代码

同一个目标字段的几跳并成一步，以（深度，目标字段）为键：

```python
for hop in graph.upstream(table_id, column, LINEAGE_DEPTH):
    groups.setdefault((hop.depth, f"{hop.target.table}.{hop.target.column}"), []).append(hop)
```

上下游判定，方向看血缘，不看得分排名：

```python
for upstream, downstream, path in ((a, b, diff.path_b), (b, a, diff.path_a)):
    depths = [hop.depth for hop in path if hop.source == upstream.ref]
    if depths:
        return FieldComparison(..., a=upstream.field, b=downstream.field, relation="derived_from")
```

只用表结构的关联，手工加同名粒度键，合并和排序与完整推导共用一套：

```python
def structural(self) -> list[Relation]:
    return self._merge([*self._manual(), *self._grain_relations()])
```

## ⚠️ 常见坑

1. **库里的来源不等于结构上推得出。** 同一种映射只留最高优先级的来源，被顶替的在库里看不出来。
2. **同一目标字段的多个来源不并，条件就重复。** 客户汇总表的存款余额取自 `bal_rmb` 和 `is_margin` 两个字段，不并成一步，同样的过滤和关联条件就要写两遍。
3. **第一条语句不能定生死。** 多条语句写同一字段，先是空值占位、后面才是真加工的，按第一条排除会把字段丢掉。
4. **同分要有确定的先后。** 得分保留 10 位小数再比较（浮点误差会打乱同分），同分依次比表的先后和字段名；测试用两个哈希种子的子进程比对。
5. **排版会改写个别写法。** sqlglot 把 `DATE '2026-09-30'` 写成 `CAST('2026-09-30' AS DATE)`，语义不变；排版后让校验器再核一遍，错误变多就退回原文。
6. **血缘有一半是重复的。** 35 道题共 1264 步，同一份证据里去掉重复只剩 686 步（共用的上游字段出现在多个字段的链路里），渲染时可以合并。

## 面试话术

> 「NL2SQL 里我把模型要读的证据做成确定性代码：候选表、指标字段往上 3 跳的加工链路（带过滤和关联条件）、同源字段的口径对比、表间关联路径，全是图查询，同样的输入必然同样的输出。对照实验里 A 组不能看到脚本，所以它的关联路径不能从库里按来源筛，要按表结构重新推导，我给这条路径单独写了锚点测试。」

被追问时可以展开的两点：

- 为什么先判上下游再判口径：下游字段的共同上游里含上游字段，先判口径会误报成「同源不同口径」。
- 为什么库里不能直接筛：同一种映射只留最高优先级的来源，客户汇总表到客户维表在库里记的是血缘传递。
