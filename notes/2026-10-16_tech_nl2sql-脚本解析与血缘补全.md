# NL2SQL 加工脚本解析与血缘补全：分句与降级、按位置对应目标字段、临时表并入、清单优先脚本补缺

> 日期: 2026-10-16 | 类别: tech | 关联: [[2026-10-13_design_nl2sql专题库改造]]、[[2026-10-15_tech_nl2sql-SQL作用域解析]]

## 📦 目标

血缘清单相当于 ETL 项目里的 mapping 文档：目标表的每个字段来自哪张源表的哪个字段。真实资料里这份文档有两个毛病：

1. **缺行**：专题层 1667 个字段里，661 个一条血缘都没有。
2. **缺加工逻辑**：清单里「加工逻辑」一栏大多是中文说明，有的干脆空着。

加工脚本却是全的。这一步把加工脚本当成「第二份 mapping 文档」：从脚本里反推出每个目标字段的表达式和来源，补上清单缺的行和空着的加工逻辑，并且标明哪些是反推出来的。

做完之后，元数据库里多了三样东西：

| 产出 | 存在哪 | 给谁用 |
|------|--------|--------|
| 脚本片段：每条写数语句的原文、自包含的查询、各查询层的过滤条件和关联 | `meta_script` | 血缘图每一跳的「加工条件」、关联推导、校验器的误报测试 |
| 逐字段表达式：展开成实体表写法的表达式、来源字段、类别 | `meta_script_column` | 血缘图；召回时排除恒为空的字段 |
| 合并后的血缘：清单边加上脚本补的边，每条标明来源、是否直取 | `meta_lineage` | 血缘图；关联推导的键域 |

交付物是 `metadata/script_parser.py` 的四个公开函数：`parse_script_text`、`parse_scripts`、`merge_lineage`、`is_bare_reference`。导入时由 `enrich_mart` 依次调用，报告里多出「加工脚本」「血缘合并」两节。

数字指标：

- 单元测试 56 项（全量 360 项），只用模拟库和手写的小脚本，不调模型，1 秒内跑完。
- 模拟库 7 个脚本：7 条 INSERT 全部结构化解析，临时表并入 23 号脚本；56 个目标字段，直取 32、加工 24；70 条清单边全部回填了加工逻辑；没有警告。
- 真实专题库（只读验证，只记数字）：45 个脚本的 45 条 INSERT 全部结构化解析，W06、W07 都是 0；合并前没有血缘的专题层字段 661 个，脚本补上 249 个，剩下 412 个都能归类，说不清原因的只有 2 个；解析加合并约 3.6 秒。

## 📖 讲透

### 1. 一个脚本文件怎么切成语句

加工脚本不是一条 SQL，而是一串：先 `TRUNCATE` 或者按日期 `DELETE`，再 `INSERT … SELECT`，有的前后还包着 `BEGIN`、`COMMIT`、`DO $$ … $$` 块。切分分三层，越往下越宽容：

1. **整个文件交给 sqlglot 解析。** 绝大多数文件一次成功。
2. **整个文件失败时，自己按分号切开，逐条重试。** 切的时候要跳过注释、字符串和 `$tag$ … $tag$` 块里的分号：`DO $guard$ BEGIN PERFORM 1; END $guard$` 里的分号不是语句分隔。
3. **单条仍然失败时，只存原文。** 看起来是 INSERT 或建表语句的，用正则 `insert\s+into\s+(表名)` 取目标表，存下原文，报 W06；其它解析不了的语句（比如写坏了的 UPDATE）不涉及加工逻辑，直接忽略。

类比批量装载：整批失败时，不让整个作业退出，而是改成逐条装载，坏的那条进异常表，其余照常入库。

处理的只有两类语句：

| 语句 | 处理 |
|------|------|
| `INSERT … SELECT`、`CREATE TABLE … AS SELECT` | 结构化解析，每条成为一个脚本片段 |
| `TRUNCATE`、`DELETE`、`DROP`、`COMMIT`、`BEGIN`、`DO` 块、`ANALYZE` 等 | 忽略，不报警告 |

后一类决定的是「怎么装」（先删后插、全量刷新），不决定「装什么」，和字段口径无关。

### 2. 目标字段按位置对应，不按名字

`INSERT INTO t (a, b, c) SELECT x, y AS b, z FROM …` 里，第 1 列写进 `a`，第 2 列写进 `b`，第 3 列写进 `c`。决定写进哪个字段的是**位置**，和 SELECT 里写的别名无关，别名写错了数据库也不报错。所以解析器把第 i 个投影改名成第 i 个目标字段，再按目标字段名追溯。

测试里专门造了一条别名「故意写反」的语句：

```sql
INSERT INTO ads.corp_cust_loan_bal_d (cust_no, org_no, loan_bal_rmb)
SELECT l.org_no AS cust_no, l.cust_no AS whatever, SUM(l.bal_rmb) AS x
FROM dwd.corp_loan_duebill_d l
GROUP BY l.org_no, l.cust_no;
```

解析结果是 `cust_no` 的来源为 `org_no`、`org_no` 的来源为 `cust_no`，和数据库实际写入的一致。

几种情况：

- **写了列清单**：按列清单。列数对不上报 W06，这条语句的字段表达式跳过，过滤条件和关联照常记。
- **没写列清单**：按字段清单的顺序。查询的列比表少时，对应表的前几个字段，其余字段取默认值，和 PostgreSQL 的行为一样；比表多才报 W06。
- **建表语句**：目标字段就是查询的输出名。
- **WITH 写在 INSERT 前面**（`WITH x AS (…) INSERT INTO t SELECT … FROM x`）：sqlglot 把 CTE 挂在 INSERT 上，查询部分里没有。要先把 CTE 挪进查询，否则查询里的 `x` 会被当成一张不存在的表。真实脚本里有 7 条是这种写法。

**先限定，再改名。** 如果先改名，`GROUP BY br` 引用的输出别名 `br` 就悬空了。先让 sqlglot 按元数据限定字段，它会把 GROUP BY、HAVING 里引用的输出别名展开成表达式，之后再改名就不会出问题。

### 3. 临时表并入引用它的语句

模拟库 23 号脚本先建一张临时表，再从临时表汇总写入专题层：

```sql
CREATE TEMPORARY TABLE tmp_corp_loan AS
SELECT l.data_dt, l.cust_no, l.org_no, l.duebill_no, l.bal_rmb, l.is_npl
FROM dwd.corp_loan_duebill_d l
JOIN dim.corp_cust c ON l.cust_no = c.cust_no
WHERE l.data_dt = DATE '${data_dt}';

INSERT INTO ads.corp_cust_loan_bal_d (data_dt, cust_no, org_no, loan_bal_rmb, npl_bal_rmb, duebill_cnt)
SELECT t.data_dt, t.cust_no, t.org_no, SUM(t.bal_rmb), … FROM tmp_corp_loan t GROUP BY …;
```

如果两条分开处理，INSERT 的来源会停在 `tmp_corp_loan` 这张「表清单里没有的表」上，血缘就断了。做法是把临时表改写成 CTE，注入 INSERT 的查询：

```sql
WITH tmp_corp_loan AS (SELECT l.data_dt, l.cust_no, … FROM dwd.corp_loan_duebill_d AS l JOIN … WHERE …)
SELECT t.data_dt, t.cust_no, … FROM tmp_corp_loan AS t GROUP BY …
```

这样 `cust_no` 一路追到 `dwd.corp_loan_duebill_d.cust_no`，临时表里「关联客户维表」「按日期过滤」这两个条件也记在这个片段名下。类比：把作业里的中间落地表内联回主 SQL，血缘才是连续的。

规则：

- **什么算临时表**：同一个文件里，带 `TEMP`/`TEMPORARY` 的建表语句，或者目标表不在表清单里的建表语句。后者是工作表，可能带模式名，比如 `work.tmp_b`，注入时去掉模式名，引用它的地方一并改名。
- **被引用才并入**：后面的语句引用到它，就把它连同它依赖的更早的临时表注入成 CTE。片段原文 `sql_text` 前面拼上建表语句的原文；`select_sql` 存注入之后的自包含查询。被并入的建表语句本身不单独成条。
- **没被引用的**单独成条，因为目标表不在表清单里，报 W07。

### 4. 每条语句记下什么

- **逐字段表达式**：追溯和展开调共享模块 sqlscope（见上一篇笔记）。每个目标字段得到展开成实体表写法的表达式、来源字段和类别：直取、加工、空值、常量、加工时间、追溯不到。
- **过滤条件**：每个查询层的 WHERE、HAVING 按 AND 拆开，一条一条记，字段换成实体表全名。查询层的名字：最外层叫 `main`，CTE 用自己的名字，UNION 的分支写成 `main#1`、`main#2`，其余子查询按书写顺序编号 `subquery1`、`subquery2`。
- **关联**：ON、USING，以及 WHERE 里两侧别名不同的等值（记为 `IMPLICIT`）。后者已经算作关联，就不再重复算作过滤条件。

为什么过滤条件要按查询层记：上溯到整合层查数时，必须把专题层加工时的条件一并带上，查出来的数才对得上；而写在 CTE 里的条件只约束那个 CTE，层次不能丢。

### 5. 血缘合并：清单优先、脚本补缺、标注来源

这是这一步的核心原则：

1. **清单优先。** 清单里有的边一条不动，写了的加工逻辑不覆盖。清单是人维护的正式文档，脚本反推的结果再准，也只是推断。
2. **脚本补缺。** 两处缺口用脚本补：
   - 清单边的加工逻辑是空的：用脚本里这个目标字段的表达式回填。
   - 清单里一条血缘都没有的字段：按脚本追溯到的每个来源补一条边。
3. **标注来源。** 补的边 `origin=script`，清单的边 `origin=list`。下游模块可以区别对待，人看报告时也知道哪些是反推的。

类比：mapping 文档缺了几行，从加工脚本里反推回来补上，并在备注栏写明「据脚本反推」；正式文档里写了的，哪怕和脚本对不上，也不擅自改，只在报告里列出来请人核对。

**直取标记**（`is_passthrough`，后面推导关联的键域要用）：

| 情况 | 什么时候算直取 |
|------|----------------|
| 这个字段在脚本里有表达式 | 脚本里是直取，并且这条边的来源在脚本的来源里 |
| 没有脚本表达式 | 目标字段和源字段同名、并且是唯一来源；或者清单的加工逻辑是对源字段的裸引用（`x`、`t.x`、`s.t.x`，不区分大小写） |

清单的加工逻辑多是中文说明，「取客户号」这类说明一律不算裸引用，只认规规矩矩的字段名。

**一个字段被几条语句写入**（比如两条 INSERT 分别从两个系统取数）：按 UNION ALL 合并，规则和 sqlscope 对 UNION 的处理一样：都直取才是直取，都为空才是空值，有直取或加工就是加工；表达式写成 `UNION(表达式1, 表达式2)`。

### 6. 没有上游的字段为什么值得单独记账

补完之后，真实库专题层还有 412 个字段没有血缘。如果报告只写「412 个字段没有血缘」，人看了不知道该不该处理。所以按原因分开：

| 原因 | 个数 | 含义 |
|------|------|------|
| 表没有脚本 | 189（8 张表） | 资料缺件，要去找脚本 |
| 脚本里没有上游 | 221 | 脚本里本来就是 NULL、常量、加工时间或 `COUNT(*)` 这类行计数，**本来就没有上游**，不是资料缺件 |
| 其它 | 2 | 两个加工时间字段，INSERT 没写，靠表的默认值填 |

第二类尤其值得记下来：

- **它把「资料缺件」和「本来就没有」分开了。** 221 个字段占了剩余的一半多，不分开的话，会被当成资料问题去追，白费功夫。
- **恒为空的字段要从召回里排除。** 真实库有 142 个目标字段在脚本里恒为 NULL，多是预留字段。它们的中文名可能很像用户要的指标，但数据里永远是空的。召回时排除掉，模型就不会选一个永远查不出数的字段。
- **常量和加工时间也是口径信息。** 「这个字段在脚本里固定写 '1'」「这个字段是跑批时间」，模型看到才不会把它当成业务字段。

类比：数据质量报告里，空值率 100% 的字段要单独列出来，因为它可能是预留字段，也可能是装载漏了，两种情况的处理完全不同。

### 7. 两份文档对不上时只计数

「清单与脚本不一致」指一个字段两边都有来源，但一个都对不上。真实库有 58 个，大致三类：清单写的是业务系统的源表，脚本读的是标准层的表（43 个）；同一张表但字段名不同，多是清单里的字段名过时了（7 个）；表和字段都不同（8 个）。

这些只进报告，不改清单：清单优先，判断谁对是人的事。

### 8. 名字的大小写

PostgreSQL 里，带引号的 `"CUST_NM"` 和不带引号的 `cust_nm` 是两个名字。真实资料的转换器把所有名字都转成了小写，元数据里只有小写的名字。真实脚本里有 22 处这种带引号的大写字段名（集中在 3 个脚本里），按数据库的规则追溯出来的来源是大写的，和清单对不上，血缘图里还会多出一个只差大小写的节点。

所以解析之前先把带引号的标识符转成小写（仍带引号），和元数据的约定一致；片段原文 `sql_text` 不动。这一条让「清单与脚本不一致」从 67 个降到 58 个，降下来的 9 个全是大小写造成的假不一致。

## 🔧 选型

| 决策 | 选了什么 | 没选什么 | 原因 |
|------|----------|----------|------|
| 切分语句 | 先整个文件解析，失败才自己按分号切 | 一开始就自己切 | 整个文件解析与 sqlglot 的切法天然一致；自己切只在降级时用，跳过注释、字符串、`$tag$` 块 |
| 解析不了的语句 | 只存原文，报 W06 | 丢掉 | 原文仍是证据，可以交给模型读，只是没有结构化的字段表达式 |
| 判断「像不像 INSERT」 | 只看开头的关键字 | 全文搜索 `insert into` | DO 块、函数体里写的 INSERT 会被误判 |
| 目标字段对应 | 按位置改名 | 按别名对应 | 数据库按位置写入，别名写错不报错 |
| 改名时机 | 先限定再改名 | 先改名再限定 | 先改名会让 GROUP BY 里的输出别名悬空 |
| 临时表 | 改写成 CTE 注入引用它的语句 | 当成独立的语句 | 独立处理时血缘停在临时表上；改成 CTE 后一路追到底 |
| 自包含查询 `select_sql` | 由 sqlglot 重新生成，去掉注释 | 拼接原文 | 注入 CTE 要改语法树，只能重新生成；它是给校验器测误报用的，不需要保留格式 |
| 合并原则 | 清单优先、脚本补缺、标注来源 | 脚本覆盖清单 | 清单是人维护的正式文档；脚本推断的结果标明来源，冲突只计数 |
| 多条语句写同一字段 | 按 UNION ALL 合并类别和表达式 | 只取第一条 | 多条 INSERT 写同一张表，语义就是 UNION ALL |
| 名字的大小写 | 带引号的大写名字转小写 | 照 PostgreSQL 区分大小写 | 元数据里只有小写名字，区分大小写只会制造假的不一致 |

## 💡 可迁移

**1. 正式文档优先，推断结果补缺，并标明来源。** 主数据、数据字典、指标口径，凡是「人维护的文档」和「从系统里反推的结果」并存的地方都适用：推断结果不覆盖正式文档，冲突列出来交给人；来源字段（这里是 `origin`）让下游能区分可信度。

**2. 缺口要按原因分类，数字才能变成行动。** 「412 个字段没有血缘」是一个吓人的数字；拆开是「8 张表缺脚本、221 个字段本来就没有上游、2 个说不清」，每一类都有明确的处理人。做数据质量报告时，不要只报缺失率，要报缺失的原因分布。

**3. 层层降级，宁可少一点结构，也不丢原文。** 整体失败就逐条，逐条失败就只存原文，每一步都留痕（W06）。下游拿到的永远是「尽可能多的信息，加上明确标出的不确定性」。

**切分：先整个文件，失败再逐段。**

```python
def _split_statements(text):
    spans = _split_sql(text)                      # 在注释、字符串、$tag$ 块之外按分号切
    try:
        trees = parse_statements(text)
    except Exception:
        trees = None
    if trees is not None and len(trees) == len(spans):
        return [_Piece(span.text, span.line, tree) for span, tree in zip(spans, trees)]
    pieces = []
    for span in spans:                            # 整个文件失败：逐段重试
        try:
            trees = parse_statements(span.text)
        except Exception as error:                # 这一段只存原文，记下报错原因和行号
            pieces.append(_Piece(span.text, span.line, None, _parse_error(error, text, span)))
            continue
        ...
```

**合并：清单边只回填空的加工逻辑，直取标记有脚本就看脚本。**

```python
for edge in mart.lineage:
    script = scripts.get((edge.target_table, edge.target_column))
    transform = edge.transform
    if not transform.strip() and script is not None and script.expression:
        transform = script.expression                         # 空的才回填，写了的不覆盖
    if script is not None:
        passthrough = script.kind == "passthrough" and source in script.sources
    else:
        passthrough = (same_name and only_source) or is_bare_reference(edge.transform, edge.source_column)
    edges.append(edge.model_copy(update={"transform": transform, "is_passthrough": passthrough}))
```

## ⚠️ 常见坑

1. **WITH 写在 INSERT 前面，CTE 挂在 INSERT 节点上。** 只取 INSERT 的查询部分会丢掉 CTE，查询里对 CTE 的引用就变成了「不存在的表」。要先挪过去。
2. **先改名再限定，GROUP BY 里的输出别名会悬空。** `SELECT SUBSTR(a.org_no, 1, 4) AS br … GROUP BY br`，把 `br` 改名成目标字段之后，`GROUP BY br` 就找不到了。先限定（sqlglot 会展开别名引用），再改名。
3. **按分号切分要跳过三种地方**：注释、字符串、`$tag$` 块。`'a;b'`、`/* 说明; */`、`DO $body$ … PERFORM 1; … $body$` 里的分号都不是语句分隔。
4. **判断语句种类只看开头。** DO 块的函数体里可能写着 INSERT，全文搜索会把整个 DO 块当成一条解析失败的 INSERT，平白多一条 W06。
5. **INSERT 没写列清单时，列可以比表少。** PostgreSQL 把查询的列依次写进前几个字段，其余字段取默认值，这不是错误；只有比表多才是。
6. **带模式名的工作表也是临时表。** `CREATE TABLE work.tmp_b AS …` 的目标表不在表清单里，同样要并入；注入成 CTE 时去掉模式名，引用它的地方一并改名。
7. **带引号的大写名字。** `c."CUST_NM"` 按数据库的规则不等于 `cust_nm`，而元数据里只有小写名字，不转小写就会制造假的不一致和重复节点。
8. **sqlglot 自带的遍历顺序不是书写顺序。** 解析器最后才把 WITH 挂上去，`walk()` 会把 CTE 排到最后。给子查询按书写顺序编号，要按各节点类型定义参数的顺序自己遍历。
9. **sqlglot 的报错信息带着 Token 的内部表示和终端颜色码。** 写进报告之前要清理，行号也要从「这一段的第几行」换算成「整个文件的第几行」。

## 面试话术

> 「血缘清单就是 mapping 文档，真实资料里专题层约四成字段没有血缘。我把加工脚本当第二份文档：用 sqlglot 解析每条 INSERT，按位置把投影对到目标字段，临时表改写成 CTE 并进来，一路追到实体字段。合并时清单优先、脚本补缺、标注来源：补上 249 个字段，剩下的按原因归类，说不清的只有 2 个。」

被追问时可以展开的三点：

- 为什么不让脚本覆盖清单：清单是人维护的正式文档，脚本推断的结果标明来源；冲突只计数，请人核对。
- 恒为空的字段为什么单独记：把「资料缺件」和「本来就没有上游」分开；召回时排除它们，模型不会选一个永远查不出数的字段。
- 临时表为什么改写成 CTE：分开处理时血缘停在临时表上；改写之后追溯一路到底，临时表里的过滤和关联也记在目标表名下。
