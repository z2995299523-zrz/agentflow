## 📦 目标

评估一条生成的 SQL 对不对，最可靠的办法是真的执行它，再和标准答案的结果比，就像新系统投产前要和老系统并行跑批、逐表对数一样。真实专题库在本机没有数据，表结构也不能公开，所以需要一套模拟专题库。

对这套模拟库的要求是**数据字典、血缘、加工脚本、数据，四者必须一致**。如果字典说「存款余额不含保证金」而数据里其实含了，评估结果就没有意义。

交付物分三块：

| 交付物 | 位置 | 内容 |
|--------|------|------|
| 资料 | `data/mock_mart/` | 四张清单（14 张表、93 个字段、70 条血缘、1 条关联关系）和 7 个加工脚本 |
| 执行层 | `nl2sql/dialect.py`、`nl2sql/executor.py` | 把 PostgreSQL 方言的 SQL 转成 DuckDB 方言并只读执行 |
| 造数 | `data/mock_mart/build_mock.py` | 建表、生成贴源层数据、逐日跑加工脚本、对平检核 |

数字指标：资料 7 项测试、执行层 14 项、造数 23 项，共 44 项。完整造一次库，库文件放在固态盘上约 15 秒，放在机械盘上约 87 秒（差距的原因见选型一节的实测结论）。各表的行数如下（造数完成后逐表查询得到）：

## 📖 讲透

### 1. 三层 14 张表

业务是银行对公存贷款，分层和真实数仓一样。

| 层 | 表 | 说明 |
|----|----|------|
| 贴源层 `ods` | 存款账户、贷款借据、对公客户信息、行业代码、机构信息、汇率、科目，共 7 张 | 源系统的原样数据。账户和借据是每日全量快照，含对公和个人 |
| 整合层 `dwd`、`dim` | 对公存款账户日快照、对公贷款借据日快照、对公客户维表、机构维表，共 4 张 | 存款只保留对公、状态正常的账户，贷款只保留对公、余额大于零的借据（五级分类全部保留），都折算成人民币；机构的上下级关系拉平成维表 |
| 专题层 `ads` | 对公客户存款余额日汇总、机构对公存款余额日汇总、对公客户贷款余额日汇总，共 3 张 | 按客户、按机构汇总好的指标，带年日均和月日均 |

### 2. 为什么只随机生成贴源层

造模拟数据有两种做法：

| 做法 | 问题 |
|------|------|
| 每一层的表各自随机生成 | 层与层之间对不上。专题层的余额不等于整合层明细的合计，沿血缘向上溯源查出来的数和专题层永远不一致 |
| 只随机生成贴源层，整合层和专题层用加工脚本真的跑出来 | 没有这个问题。上层的每一个数都是脚本算出来的 |

这里用的是第二种。这和真实数仓完全一样：**加工脚本就是口径的最终依据**。字典里写「存款余额」四个字，到底含不含保证金，要看脚本里那一行表达式。模拟库里的 7 个脚本既是给大模型看的口径证据，也是真正在库里执行的加工程序，两者是同一份文件，所以不可能不一致。

### 3. 逐日跑批，先删后插，可以重跑

带日期参数的脚本对每个数据日期各执行一次，和调度系统每天跑批是同一个过程。这些脚本都按数据日期先删后插（贷款汇总的脚本是先建一张临时表算好当天的数，再删、再插）：

```sql
DELETE FROM ads.corp_cust_dep_bal_d WHERE data_dt = DATE '${data_dt}';

INSERT INTO ads.corp_cust_dep_bal_d (...)
SELECT ...
WHERE a.data_dt = DATE '${data_dt}'
```

先删掉这一天的数据再插入，同一天重跑多少次结果都一样。这就是日常说的作业要支持重跑。

脚本按文件名的顺序执行，文件名的数字前缀就是依赖顺序：`01`、`02` 是维表，`11`、`12` 是整合层，`21` 到 `23` 是专题层。维表脚本里没有日期参数，只执行一次，做法是先清空、再全量重插。

### 4. 对平检核

造数的最后一步是对平检核，全部通过才算造数成功。它查两类问题。

**第一类：粒度字段是否真的唯一。** 表清单里每张表都登记了粒度字段，检核时按粒度字段分组，看有没有重复：

```sql
SELECT COUNT(*) FROM (
    SELECT data_dt, cust_no, org_no FROM ads.corp_cust_dep_bal_d
    GROUP BY data_dt, cust_no, org_no HAVING COUNT(*) > 1
)
```

这就是主键唯一性检查。它同时验证了字典里登记的粒度和库里的数据是一致的。

**第二类：各层之间的金额和行数是否对得上。** 一共 8 条，每条都是一句返回「不平的行数」的 SQL，结果为 0 才算通过：

| 检核 | 类比 |
|------|------|
| 整合层存款快照的行数 = 贴源层对公正常账户的行数 | 抽取前后的记录数核对 |
| 整合层贷款快照的行数 = 贴源层对公且余额大于零的借据行数 | 同上 |
| 客户存款汇总的全口径余额 = 整合层存款快照中有效客户的余额合计 | 总分核对 |
| 存款余额 + 保证金存款余额 = 全口径存款余额 | 表内勾稽关系 |
| 活期存款余额 + 定期存款余额 = 存款余额 | 表内勾稽关系 |
| 机构存款汇总 = 客户存款汇总按机构合计 | 汇总表之间的核对 |
| 客户贷款汇总的余额 = 整合层贷款快照中有效客户的余额合计 | 总分核对 |
| 月末的年日均 = 年初至当日每日存款余额之和 ÷ 天数 | 用另一种算法重算指标 |

### 5. 五类埋点

模拟库里刻意构造了五类容易写错的情况。没有这些埋点，随便写一条 SQL 都能答对，题库就测不出血缘有没有起作用。

| 类别 | 埋的是什么 | 数据上是怎么构造的 |
|------|------------|--------------------|
| 口径 | 「存款余额」不含保证金，「全口径存款余额」含保证金。字段清单里两者的口径说明都只写「折人民币」，区别只在加工脚本的表达式里 | 生成了一批保证金科目的账户，所以两个字段的数值确实不同 |
| 选表 | 各分行的余额，机构汇总表和客户汇总表都能回答；按行业统计，只有客户级的表加客户维表能回答 | 两张汇总表都真实存在，并且互相对得上 |
| 关联 | 按一级分行汇总要通过机构维表的层级字段。贴源层机构信息表的上下级关系用的是非同名键（上级机构号 = 机构号） | 机构有总行、一级分行、二级分行、支行四级，账户开在支行和二级分行 |
| 溯源 | 专题层已经折成人民币，没有币种、产品、五级分类这些字段，要查就得上溯到整合层，并且把加工条件还原回来 | 有外币账户；有几个账户的客户号在客户信息表里不存在；有销户账户和个人账户，它们只在贴源层有 |
| 日期 | 快照表必须带日期条件；较年初是当期对比上年末；日均要用现成的日均字段，不能对行求平均 | 数据从上年末 2025-12-31 开始，到 2026-09-30，每天一份 |

溯源这一类值得展开说。专题层的加工脚本关联了客户维表，把客户号无效的账户剔除了：

```sql
FROM dwd.corp_dep_acct_d a
JOIN dim.corp_cust c ON a.cust_no = c.cust_no
```

如果有人要按币种看存款余额，专题层没有币种字段，只能去查整合层。这时候如果不把这个关联条件带上，查出来的合计就会比专题层多出那几个无效客户的余额，和报表对不平。这正是实际工作中「上溯查数对不平」最常见的原因：上层的表多做了一步过滤，溯源的时候漏掉了。

### 6. 方言转换起什么作用

加工脚本和标准答案都是按目标库（GaussDB，PostgreSQL 系）的方言写的，这样它们和将来真实环境里的 SQL 是同一种写法。但模拟库的引擎是 DuckDB，两者有细节差异，所以执行之前要过一道方言转换。下面是用 `nl2sql.dialect.transpile_statements` 逐条转换得到的真实结果：

```text
PostgreSQL: DELETE FROM ads.corp_cust_dep_bal_d WHERE data_dt = DATE '${data_dt}'
DuckDB    : DELETE FROM ads.corp_cust_dep_bal_d WHERE data_dt = CAST('${data_dt}' AS DATE)

PostgreSQL: SELECT to_char(DATE '2026-09-30', 'YYYY-MM')
DuckDB    : SELECT STRFTIME(CAST('2026-09-30' AS DATE), '%Y-%m')

PostgreSQL: SELECT a::numeric(18,2), b::varchar FROM t
DuckDB    : SELECT CAST(a AS DECIMAL(18, 2)), CAST(b AS TEXT) FROM t

PostgreSQL: SELECT string_agg(cust_nm, ',') FROM dim.corp_cust
DuckDB    : SELECT GROUP_CONCAT(cust_nm, ',') FROM dim.corp_cust
```

第一条是加工脚本里的写法：日期参数 `${data_dt}` 写在引号里，转换之后原样保留，执行前再替换成具体的日期。第二条是最典型的差异，格式化日期的函数名和格式串在两个库里都不一样。后两条是类型名和聚合函数名的差异。

转换是自动做的，写脚本、写标准答案的人只需要会 PostgreSQL 的写法。

### 7. 输入指纹：要不要重新造数

完整造一次库少则十几秒，多则一分多钟，不能每跑一次测试都造一次。办法是给造数的输入算一个指纹：四张清单、7 个脚本、造数程序本身、日期范围、随机种子，拼在一起算一个哈希值，造数成功后写在库文件旁边。

下次要用库时先算当前的指纹：和记录的一样，直接复用；不一样，说明输入变了，重新造。

这和调度里「上游没变就不用重跑」是同一个思路，只不过判断依据不是时间戳，而是内容本身。算指纹之前会把换行符统一掉，否则 git 在 Windows 上转换换行符会让指纹无故变化。

目前有两样东西不在指纹里：方言转换模块，以及 sqlglot 和 DuckDB 的版本。它们一变，脚本转换出来的结果可能跟着变，这时要手工删掉 `data/mock_mart/build/` 下的库，让它重新造。

## 🔧 选型

| 决策 | 选了什么 | 没选什么 | 原因 |
|------|----------|----------|------|
| 模拟库的引擎 | DuckDB | SQLite | SQLite 不能建模式（schema），只能靠附加数据库来模拟，也没有真正的日期类型（日期是当文本或数字存的），离 PostgreSQL 太远，很多 SQL 转不过去。DuckDB 的语法本来就向 PostgreSQL 看齐。类比：在本机起一个语法兼容的开发库，用来验证要在生产库上跑的脚本 |
| 模拟库的引擎 | DuckDB | Docker 里的 PostgreSQL | PostgreSQL 最贴近目标库，但要装 Docker、起服务。DuckDB 是一个文件加一个 Python 包，测试和演示时零部署。类比：只是验证一段 SQL 的逻辑，用本机的轻量库就够了，不必先申请一套测试环境 |
| 方言转换 | sqlglot | 手工维护两套 SQL | 两套 SQL 一定会改漏。sqlglot 还能把 SQL 解析成语法树，后面的静态校验和脚本解析都要用它。类比：异构数据库迁移时用的 SQL 转换工具 |
| 装数方式 | 写成 CSV 再 `COPY` | 逐行 `INSERT` | DuckDB 是列式库，逐行插入非常慢，批量装载才是正确的用法。类比数仓装数用装载工具，而不是一条一条 insert |

三个实测结论，前两个和直觉相反，第三个是把代码搬进正式目录之后才发现的：

- **逐日跑批设成单线程更快。** 开发时在固态盘上测，约 16 秒降到 11 秒。逐日跑批是大量的小语句，每条语句处理的数据很少，多线程的调度开销比它带来的收益大。类比：一批很小的作业，串行跑反而比开很多并发更快，并发的调度和争抢开销比作业本身还大。
- **把整个跑批放进一个事务反而慢很多。** 同样的环境下约 70 秒。原以为少提交几次会更快，实测正好相反，所以保持每条语句自动提交。类比：几千步的批量不会放进一个大事务里一次提交，否则日志和回滚的压力都很大。
- **库文件放在哪块盘上，影响比前两条都大。** 同一份代码、同一台机器、同一时刻：库文件放在固态盘的临时目录里，造数用 14.7 秒；放在机械盘上的仓库目录里，用 86.9 秒。推测的原因是逐日跑批有几千条语句，每条语句自动提交时都要把日志落到磁盘上，这个操作在机械盘上慢得多。开发时一直在固态盘的临时目录里测，所以没有发现。

性能问题要量，不能猜；而且要在代码真正运行的位置上量。目前没有为此改代码：造好的库会被复用，一分多钟的代价只在清单、脚本或造数程序有改动时才付一次。如果以后觉得慢，可以改成先在系统临时目录里造库，造完再移到目标位置。

## 💡 可迁移

**1. 测试数据由真实的加工逻辑生成，而不是手工拼。** 手工拼的测试数据只能覆盖想得到的情况，而且各层之间很难保持一致。只造最上游，下游让真实的程序去跑，数据的一致性是由程序保证的。

**2. 把对平检核做成自动化测试。** 平时对平是出了问题才去查的。这里把 8 条核对规则写成 SQL，每次造数都自动执行，再用单元测试确认「故意把数据改坏时，检核确实会报出来」。

**3. 按输入是否变化决定要不要重建。** 类比调度里按上游是否变化决定是否重跑。适用于任何生成成本高的中间产物：向量索引、缓存、编译结果。

## 👨‍💻 代码

**造数的主流程（`build_mock.py` 的 `build`）。** 五步，顺序就是数据流的顺序。本节的片段取自仓库里的代码，做了删节；这一段里建表、造数、跑脚本、检核四行行尾的注释是为了讲解加的：

```python
con = duckdb.connect(str(db_path))
try:
    con.execute("SET threads TO 1")     # 逐日跑批是大量小语句，单线程比多线程快
    create_tables(con, mart)            # 按字段清单建表，物理表结构直接来自元数据
    generate_ods(con, dates, seed)      # 固定随机种子生成贴源层
    run_scripts(con, mart_dir / SCRIPTS_DIR_NAME, dates)   # 逐日执行加工脚本
    problems = verify(con, mart)        # 对平检核
finally:
    con.close()
if not problems:
    marker.write_text(fingerprint(mart_dir, start, end, seed), encoding="utf-8")
```

建表用的是元数据里的字段清单，而不是另外维护一份建表语句，这样字典和物理表不可能不一致。指纹只在对平通过之后才写，对不平的库不会被复用。

**日期参数的替换（`run_scripts`）。** 每个脚本只做一次方言转换，然后对每个日期把参数替换成具体的值再执行：

```python
for path in sorted(scripts_dir.glob("*.sql")):
    text = path.read_text(encoding="utf-8")
    statements = transpile_statements(text)     # 日期参数在引号里，转换后原样保留
    (daily if DATE_PARAM in text else once).append((path.name, statements))

def execute(name: str, statements: list[str], day: date | None) -> None:
    for statement in statements:
        sql = statement.replace(DATE_PARAM, day.isoformat()) if day else statement
        try:
            con.execute(sql)
        except duckdb.Error as error:
            when = f"（数据日期 {day}）" if day else ""
            raise RuntimeError(f"加工脚本 {name}{when} 执行失败: {error}") from error
```

报错信息里带上脚本名和数据日期，相当于调度日志里要能看出是哪个作业、哪个批次失败了。

**一条检核 SQL（`RECONCILE_CHECKS`）。** 机构汇总表要等于客户汇总表按机构的合计：

```sql
SELECT COUNT(*) FROM ads.org_corp_dep_bal_d org FULL JOIN (
    SELECT data_dt, org_no, SUM(dep_bal_rmb) AS dep, SUM(margin_bal_rmb) AS margin,
           SUM(dep_bal_tot_rmb) AS total, SUM(ytd_avg_bal_rmb) AS ytd
    FROM ads.corp_cust_dep_bal_d GROUP BY data_dt, org_no
) cust ON org.data_dt = cust.data_dt AND org.org_no = cust.org_no
WHERE org.dep_bal_rmb IS DISTINCT FROM cust.dep
   OR org.margin_bal_rmb IS DISTINCT FROM cust.margin
   OR org.dep_bal_tot_rmb IS DISTINCT FROM cust.total
   OR org.ytd_avg_bal_rmb IS DISTINCT FROM cust.ytd
```

两个写法上的要点。用 `FULL JOIN` 而不是内关联，是因为一边有、另一边没有的机构也算不平，内关联会把它们漏掉。用 `IS DISTINCT FROM` 而不是 `<>`，是因为它把空值也当成一个可以比较的值：一边是空、一边有数时，`<>` 的结果是未知，这一行会被悄悄放过。

**执行层（`executor.py` 的 `DuckDBExecutor.execute`）。** 先转方言，只允许单条语句，只读连接，任何失败都作为结果返回而不是抛异常：

```python
try:
    if not self.db_path.exists():
        raise FileNotFoundError(
            f"模拟专题库不存在: {self.db_path}。请先运行 python -m data.mock_mart.build_mock")
    statements = transpile_statements(sql, source=self.source_dialect)
    if len(statements) != 1:
        raise ValueError(f"只能执行单条语句，收到 {len(statements)} 条")
    # 只读只保护库文件本身；关掉外部访问，生成的 SQL 才读写不了本机的其它文件
    con = duckdb.connect(str(self.db_path), read_only=True,
                         config={"enable_external_access": False})
    try:
        cursor = con.execute(statements[0])
        columns = [item[0] for item in cursor.description or []]
        rows = cursor.fetchall()
    finally:
        con.close()
except Exception as error:  # noqa: BLE001 方言转换失败、SQL 报错、库不存在都归为执行失败
    return ExecResult(executed=False, error=f"{type(error).__name__}: {error}",
                      elapsed_ms=elapsed())
```

不抛异常是有意的。大模型生成的 SQL 执行失败是正常情况，评估时要把它记成「这道题没答对」，而不是让整个评估程序崩掉。类比：跑批时坏记录写进拒绝文件、作业接着跑，而不是整批中断。只读连接加上关掉外部访问，保证了生成的 SQL 再离谱，也改不了模拟库，读写不了本机的其它文件。

执行层是可插拔的：真实环境用的是不执行、只生成的那一个实现，模拟库上才用 DuckDB 这一个。上层代码只认同一个接口。类比：ETL 作业换数据源只换连接配置，作业逻辑不动。

## ⚠️ 常见坑

1. **数据区间短于 31 天时日期越界。** 造数时借据的结清日期和五级分类的降级日期，是从「区间内第 30 天之后」随机取的，区间不到 31 天就取不出来，程序直接报错。测试用的短区间把这个问题暴露了出来，已经处理。
2. **`${data_dt}` 必须写在引号里。** 写成 `DATE '${data_dt}'` 才是一条语法合法的 SQL，方言转换才解析得了；裸写 `${data_dt}` 会直接解析失败。
3. **长事务在 DuckDB 里更慢。** 见选型一节的实测结论。
4. **库文件被其它程序占用。** 开着数据库查看工具时无法重新造数。程序会提示「正被其它程序占用」，关掉工具重跑即可。
5. **2025-12-31 这一天的年日均不完整。** 数据从这一天开始，它的年日均只累计了一天，没有完整的 2025 年数据。题库不考 2025 年的日均。
6. **库文件所在的磁盘慢，造数会慢好几倍。** 见选型一节的第三条实测结论。库文件在机械盘上时，第一次跑测试要等一两分钟是正常的，之后会复用已经造好的库。

## 面试话术

> 「评估文本转 SQL 要比执行结果，所以我造了一套模拟专题库，三层十四张表。只随机生成贴源层，上层用加工脚本逐日真跑，字典、血缘、脚本、数据四者必然一致；跑完做对平检核。库里埋了五类易错点，比如余额含不含保证金只能从脚本里看出来。脚本按 PostgreSQL 写，用 sqlglot 转成 DuckDB 执行。」

被追问时可以展开的三点：

- 对平检核查什么：粒度字段是否唯一，加上八条总分核对和勾稽关系，全部通过才算造数成功。
- 溯源类的埋点：专题层的脚本关联客户维表剔除了无效客户，上溯到整合层查数时不还原这个条件就对不平。
- 性能上的实测结论：逐日跑批单线程更快；放进一个大事务反而慢；库文件在机械盘上比在固态盘上慢六倍，所以性能要在真实的运行位置上量。
